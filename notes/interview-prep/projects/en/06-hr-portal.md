# Interview Questions — 06-hr-portal

**Last banked:** 2026-09-27

Questions specific to the implementation decisions made in this project.
Use these alongside the topic-based files in `interview-prep/{LEVEL}/en/` and `es/`.

## Architecture & Patterns

**[06-hr-portal-001] Your HR portal splits `src/app` into `core/`, `pages/`, `shared/` and a top-level `models/`. What decides which folder a file goes into?** ⭐⭐⭐

I chose a Core/Feature/Shared layering: `core/` holds what must exist exactly once for the whole app — the guards, the auth interceptor and the four root services — and `pages/` holds one folder per feature route, each owning its own child components under `components/`. Only UI that more than one feature genuinely reuses goes to `shared/`, which in this project is just `ConfirmDialog` plus two small utils, and the domain interfaces sit in `models/` because all three layers import them. The test I used is deletion: I can delete a feature folder such as `leave-request-page/` without touching `core/` or `shared/`.

**[06-hr-portal-002] There is no `AppModule` in this project. How does the app boot and where do the app-wide providers live?** ⭐⭐

`main.ts` calls `bootstrapApplication(App, appConfig)`, and every app-wide provider is declared in the `providers` array of `app.config.ts` — the router, `HttpClient` with the interceptor, the native date adapter and the global error listeners. Every component is standalone and lists exactly what its template uses in its own `imports`, for example `MatTableModule`, `MatSortModule` and `DatePipe` in `EmployeeTable`. I decided on that because a component then declares its own dependencies, which is what makes a page lazy-loadable as a single unit with no module in between.

**[06-hr-portal-003] Walk me through `app.config.ts`. Why is `provideNativeDateAdapter()` registered there and not in the leave-request dialog that uses the datepicker?** ⭐⭐

It registers four things: `provideRouter(routes)`, `provideHttpClient(withFetch(), withInterceptors([authInterceptor]))`, `provideNativeDateAdapter()`, and `provideBrowserGlobalErrorListeners()` so uncaught errors and unhandled promise rejections reach Angular's `ErrorHandler`. The HTTP line is wiring for a backend this project doesn't have — no service injects `HttpClient` yet, so the interceptor is registered in its one place but never actually runs. I put the date adapter at the root because `MatDatepicker` fails at runtime without a `DateAdapter`, and one app-wide adapter means any future date field gets the same parsing and formatting without remembering a provider. Scoping it to `LeaveRequestDialog`'s `providers` would also work, but it would hide an app-wide choice — how dates are handled — inside one dialog.

**[06-hr-portal-004] `app.config.ts` imports `withEnabledBlockingInitialNavigation` but never passes it to `provideRouter`. What would it do, and should it be there?** ⭐

It makes the initial navigation finish before the app is considered bootstrapped, which matters for server-side rendering and hydration, where the server must not send a half-routed page. This app is client-side only and deployed as static files, so I don't need it, and the import is dead code left behind. In a code review I'd delete the import — an unused router feature in the one file that configures the router suggests a behaviour the app does not have.

**[06-hr-portal-005] Every route in your app uses `loadComponent` with a dynamic import. What does the browser download on first load, and what does an employee session never download?** ⭐⭐⭐

I decided to lazy-load every page, `login` included, so the initial bundle carries only the app shell — the toolbar, the sidenav and the `App` component — and each page is its own chunk fetched the first time its route is activated. The router runs `canActivate` before it loads a `loadComponent` chunk, so for an employee `adminGuard` stops `/employees` and `/departments` before their chunks are requested, and that admin-only code never reaches the employee's browser. That only holds because `provideRouter(routes)` configures no preloading strategy; adding one would fetch those chunks in the background anyway.

**[06-hr-portal-006] Your route table starts with `path: ''` using `pathMatch: 'full'` and ends with `path: '**'` redirecting to `login`. Why `full`, and why send unknown URLs to login instead of a 404 page?** ⭐⭐

The empty path matches the start of every URL, so with the default `prefix` matching the redirect would fire for every route; `full` restricts it to the literal root. I chose `**` → `login` because the app has no public content to show a 404 against, and for a logged-in user the redirect still ends up somewhere useful: `login` carries `noAuthGuard`, which bounces an authenticated session on to `/dashboard`. The trade-off I accepted is that a mistyped URL gives no feedback that it was wrong.

**[06-hr-portal-007] `departments/new` and `departments/edit/:id` are two routes that lazy-load the same `DepartmentForm`. How does the component know which mode it's in?** ⭐⭐

In `ngOnInit` it reads `this.route.snapshot.paramMap.get('id')`; if there is an id, it stores it in the `editId` signal, fetches the department synchronously with `getById` and `patchValue`s the form, and the template's `@if (editId())` switches the title, breadcrumb and button label. On submit, `editId !== null` decides between `editDepartment` and `addDepartment`. I chose the snapshot because the UI never navigates from one edit URL straight to another, so the component is always created fresh; one edge I'd still fix is an unknown id, which leaves the form empty but still in edit mode.

**[06-hr-portal-008] Departments are created and edited through a routed form, but employees and leave requests use a `MatDialog`. Why two different add/edit surfaces?** ⭐⭐⭐

I made it a deliberate choice: `CanDeactivateFn` is a route guard, and a dialog has no route, so the routed department form is the only place in this project where the unsaved-changes guard can be demonstrated. I gave it to departments because they have only two fields, so the extra navigation costs the least there, while the employee and leave-request dialogs keep the user on the table they were reading. Making all three the same would have cost the project either the guard or the dialog pattern; the dialogs got their own dirty-check confirmation instead (`EmployeeDialog.onCancel`).

**[06-hr-portal-009] After a successful save, `DepartmentForm` calls `markAsPristine()` right before `router.navigate(['departments'])`. What breaks if you remove that line?** ⭐⭐

The form is still dirty after the save, because saving doesn't reset the control state, and navigating away triggers the `deactivateGuard` on the route, so the user would be asked "discard changes?" about changes that were just saved. Marking the form pristine first tells the guard there is nothing left to lose, so a saved form leaves silently and only an abandoned one asks for confirmation. I placed it after the service call and the snackbar, so it only runs on the success path; a duplicate-name `return` above it keeps the form dirty.

**[06-hr-portal-010] Describe the app shell. Why does it live in the root `App` component rather than in a layout route?** ⭐⭐

`app.html` renders a `mat-toolbar` and a `mat-sidenav-container` whose `mat-sidenav-content` holds the single `<router-outlet />`, so every page renders inside the same frame. The sidenav's `[opened]` is bound to the `isLoggedIn` computed, and the logout button only renders when there is a session, so the login page shows the toolbar alone. I chose the root component because the app has one layout; a layout route with child routes would only pay off if some pages needed a completely different frame, and here login only needs the sidebar hidden, which one signal handles.

**[06-hr-portal-011] How does the sidebar decide which links to show, and does hiding a link protect the page?** ⭐⭐⭐

`App` keeps a static `navLinks` array where each entry has an `adminOnly` flag, and `filteredNavLinks = computed(() => this.isAdmin() ? this.navLinks : this.navLinks.filter(link => !link.adminOnly))` feeds the `@for` in the template. Because it's a `computed` over the session signal, the sidebar changes the moment someone logs in or out, with no manual refresh. Hiding the link is only UX — an employee can still type `/employees` — so the real enforcement is `adminGuard` on those routes; I decided to keep both, so the menu never offers a door the router will refuse.

**[06-hr-portal-012] How do you highlight the active link in the sidenav, and why the `#rla` template reference?** ⭐

Each `<a mat-list-item>` has `routerLinkActive="active"`, which adds the CSS class, and `#rla="routerLinkActive"` exports the directive so I can bind `[activated]="rla.isActive"` — the input Material's list item uses for its own activated styling. The class alone would only give me my CSS, not Material's state. I also had to override `a.active:focus:not(:hover)::before { opacity: 0 }` in `app.css`, because after a click the focused active link kept Material's hover wash; that selector hides the wash and leaves the focus ring visible.

**[06-hr-portal-013] How did you get a fixed toolbar and sidebar with only the content area scrolling?** ⭐

In `app.css` the toolbar is `position: sticky; top: 0`, and the `mat-sidenav-container` takes `flex: 1` with `min-height: 0`, so it fills the space left under the toolbar and is allowed to shrink instead of growing with its content. That only works because the global styles make the whole chain a fixed-height column: `html` and `body` get `height: 100%`, `body` and `app-root` are `display: flex; flex-direction: column`, and `app-root` has `overflow: hidden`, so the page itself never scrolls and only `mat-sidenav-content` does. Without `min-height: 0` a flex child refuses to shrink below its content height, and the whole window would scroll, taking the sidebar with it.

**[06-hr-portal-014] `isAdmin` is a `computed` in both `App` and `DashboardPage`, and `LeaveRequestPage` has its own `role` computed. Isn't the role check duplicated?** ⭐

The source of truth is single — every one of them derives from `authService.currentUser`, so they can never disagree about who is logged in — but the derivation is repeated in three components. I accepted it because each is one line reading the same signal, but the cleaner design would expose `isAdmin` as a `computed` on `AuthService` itself, so the sidebar, the dashboard and the guards all read one expression. That's the refactor I'd make if a third role appeared, because then the one-liners would start to drift.

**[06-hr-portal-015] Your employees and leave-request pages follow a coordinator pattern. What does the page own, and what do its children own?** ⭐⭐⭐

The page component is the coordinator: `EmployeePage` owns the filter signals (`searchTerm`, `selectedDepartment`, `selectedStatus`), the `filteredEmployees` computed, and every call to the service, the dialog and the snackbar. Its children — `EmployeeFilters` and `EmployeeTable` — are presentational: they receive data through `input()` and report user intent through `output()`, such as `searchChange` or the employee id to delete, and never inject a domain service. I chose it because all the state and side effects of the screen sit in one file I can read top to bottom, and the children are reusable and trivially testable, since they only map inputs to markup.

**[06-hr-portal-016] The filter inputs in `EmployeeFilters` have no `FormControl`. Where does their value live, and how does "Clear Filters" reset what the user sees?** ⭐⭐

I made them controlled components: the parent passes the current value down (`[value]="searchTerm()"`) and the child emits on change (`(input)="searchChange.emit(searchInput.value)"`, using a template reference variable). The page's signals are the only copy of the filter state, so `clearFilters()` in the page resets the three signals and the inputs re-render empty, because their `[value]` bindings follow those signals. Had the child kept its own form state, the parent would need a second channel to push the reset back down, and the two copies could disagree.

**[06-hr-portal-017] You use `input()`, `input.required()` and `output()` instead of `@Input()`/`@Output()`. What did that buy you in this project?** ⭐⭐

Signal inputs are read like any signal, so a child can build `computed()` values on top of them: `LeaveRequestTable.displayColumns` is a `computed` over the `role()` input, and the tables push their `requests()`/`employees()` input into the data source from an `effect()`. `input.required()` on `StatCard` and `DashboardPanel` means a missing `label` or `link` is a compile error in the parent's template, not a blank card at runtime. `output()` gives the same typed emitter as `@Output` without having to construct an `EventEmitter`.

**[06-hr-portal-018] `EmployeeFilters.statusChange` is typed `output<EmployeeStatusFilter>()`, not `output<string>()`. Why does the type matter at a component boundary?** ⭐

The page validates the `status` query param against the permitted list before it enters the `selectedStatus` signal, whose type is the `EmployeeStatusFilter` union. If the child's input and output were typed `string`, the value would widen back to any string at the boundary, and the union the page validated would no longer be guaranteed downstream. I typed the child's `selectedStatus` input and `statusChange` output with the domain union, so the compiler checks the contract in both directions.

**[06-hr-portal-019] In `EmployeePage` you write `employees = this.employeeService.employees`, without parentheses. What changes if you write `this.employeeService.employees()`?** ⭐⭐

Without the parentheses I store a reference to the service's signal, so every template read and every `computed` that calls `employees()` sees the current array and re-runs when the service updates it. With the parentheses I'd store the array as it was when the page was constructed — a snapshot that never updates, so a newly added employee would never appear in the table. I use the same rule in `DashboardPage` and `LeaveRequestPage`, and it's why an edit on one page is immediately reflected everywhere else, with no refetch.

**[06-hr-portal-020] Your tables keep a `MatTableDataSource` and update it from an `effect()`. Why not just bind the filtered array, or build the data source in a `computed()`?** ⭐⭐

The table receives an already-filtered array through an input, but sorting and pagination live inside `MatTableDataSource`, which is a stateful object that holds the `MatSort` and `MatPaginator` I attach to it. So I keep one instance for the component's lifetime, and `effect(() => { this.datasource.data = this.employees(); })` pushes each new array into it. A `computed()` returning a new `MatTableDataSource` would drop the sort and the paginator on every filter change; the effect updates data on an object whose configuration stays put.

**[06-hr-portal-021] Sort and paginator are attached in `ngAfterViewInit` through `@ViewChild`. Why there, and why not the signal-based `viewChild()`?** ⭐

`MatSort` and `MatPaginator` are elements in the component's own template, so the `@ViewChild` references are only populated after the view is created — `ngAfterViewInit` is the first hook where assigning `datasource.sort` and `datasource.paginator` is safe. I kept the decorator because this pattern comes straight from the Material table docs and I needed a one-off assignment, not a reactive value. With `viewChild.required(MatSort)` I'd do the same assignment inside an `effect()`, which would mix better with the signal inputs in the same class, and that's what I'd align it to in a refactor.

**[06-hr-portal-022] The leave-request table shows an email column and approve/reject actions only to the admin. How do you remove columns per role in a `mat-table`?** ⭐⭐

`displayColumns` is a `computed` over the `role()` input: the base list is `reason`, `startDate`, `endDate`, `status`, and the admin gets `employeeEmail` in front and `actions` at the end, and both `*matHeaderRowDef` and `*matRowDef` read `displayColumns()`. Every `matColumnDef` stays declared in the template; the list decides which ones render. I didn't wrap the column definitions in `@if` because the table registers its column definitions from its content, and a definition that comes and goes can leave a row definition naming a column the table can't find — keeping all definitions and switching the list is the pattern Material expects.

**[06-hr-portal-023] Admins and employees share the single `/leave-requests` route and the single `LeaveRequestPage`. Why not two pages?** ⭐⭐⭐

Both roles look at the same data — the `leaveRequests` signal in `LeaveRequestService` — and the difference is which rows they see and what they can do, so I modelled the role as a filter and a set of inputs, not as a second screen. The page's `role` computed decides the last step of `filteredLeaveRequests` (admin gets every request, employee only those whose `employeeEmail` matches the session), whether the filter bar and the "Submit leave request" button render, and it's passed down as `[role]` to the table so the table can choose its columns. With one page, an admin's approval updates the employee's view and the dashboard's pending count from the same signal, with no duplicated table or dialog code to keep in sync.

**[06-hr-portal-024] How are the filters combined in `filteredEmployees` and `filteredLeaveRequests`, and how do you tell "no data" from "nothing matches"?** ⭐⭐

On the employees page each filter is its own signal, `''` means "no filter", and one `computed` combines the name search (case-insensitive, trimmed, on first or last name), the department and the status with `&&`. On the leave page the filters run as a pipeline — status (with `'all'` as the no-filter value), then email search, then the role filter last — so an employee's view is always narrowed to their own rows whatever the filters say. On the employees page I pass a `hasActiveFilters` computed into the table, where it drives the `*matNoDataRow` text, so an empty table reads "No employees match your filters" rather than "No employees yet" when the filters caused it. The leave table doesn't receive it and always says "No requests yet", even when an admin's filter emptied it — a gap I'd close the same way.

**[06-hr-portal-025] On the leave-requests page the filter bar renders only for admins, yet `LeaveRequestFilters` also receives a `role` input and checks it. What is that check doing, and what happens if an employee opens `/leave-requests?status=pending`?** ⭐

Since the page already wraps `<app-leave-request-filters>` in `@if (role() === 'admin')`, the child's own `@if (role() === 'admin')` around the search field is always true — a redundant second gate I'd remove, keeping the role decision in the coordinator. The query-param case is a real gap: `ngOnInit` applies a valid `status` param without checking the role, so an employee who types that URL gets a filtered list with no visible filter bar and no "Clear Filters" button. The fix is either to read the param only for admins or to show employees the status filter too.

**[06-hr-portal-026] Clicking "Pending Leave Requests" on the admin dashboard opens the table already filtered. How does that work end to end?** ⭐⭐

The stat card and the panel pass `[queryParams]="{ status: 'pending' }"` alongside the `routerLink`, so the URL becomes `/leave-requests?status=pending`. The page reads `this.route.snapshot.queryParamMap.get('status')` in `ngOnInit`, and only sets `selectedStatus` if `isLeaveRequestFilter(initialStatus)` narrows the string to the permitted union — a query param is input the user can edit, so I validate it rather than casting it. The "Active Employees" card does the same with `status: 'active'` on the employees page.

**[06-hr-portal-027] You read the query param from `route.snapshot` once. When would that snapshot give the wrong filter?** ⭐

The snapshot is read once, when the component is created. If the admin is on `/leave-requests?status=pending` and clicks "Leave Requests" in the sidebar, the router keeps the same component instance for the same route, so `ngOnInit` doesn't run again and the filter stays on `pending` while the URL no longer says so. It also only works one way: changing the filter doesn't write back to the URL. I accepted that because the param is only an entry point from the dashboard; syncing both ways would mean subscribing to `queryParamMap` (or using `withComponentInputBinding()`) and navigating on every filter change.

**[06-hr-portal-028] When an admin clicks "Approve", which component does what until the snackbar appears?** ⭐⭐

The table renders Approve/Reject only for rows with `status === 'pending'`, and the click emits `statusChange` with `{ id, status: 'approved' }` — the table decides nothing. `LeaveRequestPage.onStatusChange` calls `leaveRequestService.updateStatus(id, status)`, which enforces the pending-only rule and returns whether it applied, and the page opens a snackbar with either `Leave request approved` or the refusal message. The service's signal update then re-runs `filteredLeaveRequests`, the table's effect pushes the new array into the data source, and the dashboard's pending count moves too, because it reads the same signal.

**[06-hr-portal-029] Your dialogs never save anything themselves. Who writes to the service when the user clicks "Add Employee"?** ⭐⭐⭐

I decided the dialog's job ends at `dialogRef.close(result)`: it collects and validates input and returns an `EmployeeFormResult`, or closes with nothing on cancel. The page, as coordinator, subscribes to `afterClosed()`, and only if there is a result does it call `employeeService.addEmployee(...)` and open the "Employee added" snackbar. That keeps every write and every piece of user feedback in the page, so the same dialog serves create and edit without knowing which service method follows. The only service calls it makes are reads: `emailExists` for the duplicate-email check and the departments list for its picker.

**[06-hr-portal-030] You call `this.dialog.open<EmployeeDialog, EmployeeDialogData, EmployeeFormResult>(...)`. What do the three type parameters give you?** ⭐⭐

They are the component, the `data` type and the result type, so `afterClosed()` is typed `Observable<EmployeeFormResult | undefined>` instead of `any`, and a `data` object that doesn't match `EmployeeDialogData` fails to compile at the call site. On the dialog side I inject `MatDialogRef<EmployeeDialog, EmployeeFormResult>` with the same result type, so `close()` can only be called with what the caller expects. Without them the page would read an untyped result, and a renamed field would only be caught at runtime.

**[06-hr-portal-031] The same `EmployeeDialog` handles both add and edit. How does it know which mode it's in?** ⭐⭐

It injects `inject<EmployeeDialogData | undefined>(MAT_DIALOG_DATA)`: `onEdit` opens it with `data: { employee }`, while `openDialog` passes no data, so the token yields `undefined`. In the constructor, if `data` is present I `patchValue` both form groups from the employee, and the template uses `@if (data)` for the title and the submit label. On submit, edit mode keeps the employee's original `startDate` while create mode stamps today with `toLocalDateString(new Date())`, so the one mode-specific rule sits in one branch instead of in two near-identical dialogs.

**[06-hr-portal-032] Why is the dialog's result typed `Omit<Employee, 'id'>`, and where does the id come back in edit mode?** ⭐

I derived `EmployeeFormResult` from the domain model rather than restating the fields, so a new field on `Employee` breaks the dialog at compile time instead of being silently dropped. The id is left out because create mode has none yet — the service stamps it — and edit mode already has it at the call site, so both modes close with the same shape and `onEdit` stamps it back with `{ ...updatedEmployee, id: employee.id }`. The weak spot inside the dialog is the `as string` casts on the form values, needed because its `FormBuilder` groups aren't `nonNullable` the way the login form's controls are.

**[06-hr-portal-033] A new leave request has an id, a status, an employee email, dates and a reason. Which part of your code fills in each field?** ⭐⭐

The dialog returns `LeaveRequestFormResult = Omit<LeaveRequest, 'id' | 'status' | 'employeeEmail'>` — only the dates, serialized as local `YYYY-MM-DD`, and the reason. The page adds `employeeEmail` from `currentUser()`, never from a form field, so an employee cannot file a request for someone else; the service stamps the `id` and the initial `pending` status. I split it that way so each field is set by the one layer that can be trusted with it: the user types the content, the session decides the owner, the service decides identity and the initial workflow state.

**[06-hr-portal-034] `openDialog` on the leave page uses `this.currentUser()!.email`. Why is that non-null assertion safe, and what does it depend on?** ⭐

The `/leave-requests` route carries `authGuard`, so the page never exists without a session, and the "Submit leave request" button only renders when `role() === 'employee'`, which already implies a user. The assertion therefore encodes an invariant the router guarantees, not a guess. It's still a coupling I'm aware of — if the guard were removed from that route, this line would fail with a runtime error rather than a compile error — so in a stricter version I'd guard it with an early return instead.

**[06-hr-portal-035] `ConfirmDialog` sits in `shared/`. How is it made reusable, and how does the caller read the answer?** ⭐⭐

It knows nothing about employees or departments: the caller passes a `ConfirmDialogData` object — `title`, `message`, `cancelLabel`, `confirmLabel` — and the dialog renders it. Confirm calls `dialogRef.close(true)`; Cancel uses `mat-dialog-close`, and Escape or a backdrop click close it too, so the callers test `if (confirmed)` and treat anything other than an explicit `true` as "no". It's used for the employee delete, the department delete and the employee dialog's discard prompt, which is exactly the "used by more than one feature" test for moving something into `shared/`.

**[06-hr-portal-036] The employee dialog is opened with `disableClose: true`, and its constructor subscribes to `backdropClick()`. Why both?** ⭐⭐

`disableClose` stops a backdrop click or Escape from closing the dialog on its own, so an accidental click can't throw away a half-filled two-step form. Subscribing to `backdropClick()` routes that click through `onCancel()`, which opens a nested `ConfirmDialog` if either form group is dirty and closes directly if not. It's the dialog equivalent of the `CanDeactivate` guard on the department form, since a dialog has no route to guard; the leave-request dialog doesn't do this and closes on a backdrop click, which I accepted for a three-field form.

**[06-hr-portal-037] How is the `MatStepper` in the employee dialog structured, and why do `onNext` and `onSubmit` receive the stepper as an argument?** ⭐⭐

It's a linear stepper with two steps, each bound to its own `FormGroup` through `[stepControl]` — `firstFormGroup` for personal info, `secondFormGroup` for job info — so `Next` is blocked until the current group is valid. The action buttons live in `mat-dialog-actions`, outside the `mat-stepper`, so I can't use the `matStepperNext` directive inside the steps; instead the template reference `#stepper` is passed into `onNext(stepper)` and `onSubmit(stepper)`, and the buttons switch on `stepper.selectedIndex`. That also lets `onSubmit` send the user back with `stepper.selectedIndex = 0` when the problem is in step 1.

**[06-hr-portal-038] `DepartmentList` sits in `department-page/components/`, but `DepartmentForm` sits directly in `department-page/department-form/`. Why isn't the form under `components/` too?** ⭐

Because the two are reached differently: everything under a page's `components/` folder — the lists, tables, filters, dialogs and dashboard cards — is rendered by that page's template and never routed to, while `DepartmentForm` is a routed entry of its own, lazy-loaded by `departments/new` and `departments/edit/:id`. I put it beside the page rather than inside `components/` to keep that rule true without exceptions, so the folder tree and the route table can be read against each other. It also reflects that `DepartmentForm` is not a child of `DepartmentPage` at runtime: the two are sibling routes, and the list page is destroyed when the form opens.

**[06-hr-portal-039] The dashboard shows totals to an admin and personal leave requests to an employee. Why one component with two template branches instead of two dashboards?** ⭐⭐

`/dashboard` is one route with `authGuard`, and `DashboardPage` renders `@if (isAdmin())` with four stat cards and two panels, or the employee's single card and panel. Both branches read the same four service signals, and the role-specific data is just `computed`s: `totalEmployees`, `activeEmployees`, `pendingLeaveRequests` for the admin, `myLeaveRequests` for the employee. Computed signals are lazy, so the branch that isn't rendered doesn't evaluate its computeds; two components would have meant two routes, or a routing decision by role, for what is really one screen with different content.

**[06-hr-portal-040] `DashboardPanel` receives its rows through `<ng-content>` instead of an input. Why?** ⭐⭐

The panels list different things — recent employees, pending requests, the employee's own requests — so a configuration input would have to know every entity shape and grow a field per shape. I chose content projection: the panel owns only the chrome (card, title and a "View all" link with optional `queryParams`), and the dashboard writes the rows itself with `@for` and `app-panel-item`, including its own `@empty` message. The shell stays closed to change while each caller decides what goes inside it.

**[06-hr-portal-041] Your stat cards wrap the whole `mat-card` in an `<a>`. Why not a `(click)` handler on the card?** ⭐⭐

`routerLink` only writes an `href` on an anchor, and the `href` is what makes the card a real link: it's reachable with Tab, announced as a link by screen readers, and can be opened in a new tab from the context menu or with a middle click. A click handler on a `mat-card` would give none of that, and I had to add a `:focus-visible` outline in `stat-card.css` because the wrapping anchor has no Material focus ring of its own. The toolbar title is the one place that doesn't follow this rule — it's a `<span routerLink="/dashboard">` — so it isn't keyboard-reachable, and I'd change it to an anchor.

**[06-hr-portal-042] `PanelItem` has an optional `status` input defaulting to `null`. How does the template use it?** ⭐

Only the employee's own leave requests carry a status badge; the recent-employees and pending-requests panels leave the input unset. The template uses `@if (status(); as value)` to render the badge only when there is a status, with `status-{{ value }}` picking the matching class in `panel-item.css`, which maps each status to its colour token pair from the global styles. I typed the input as `LeaveRequestStatus | null` instead of `string`, so the class name can only ever be one of the statuses the stylesheet defines.

**[06-hr-portal-043] `recentEmployees` is `computed(() => [...this.employees()].slice(-5).reverse())`. Why copy the array before reversing it?** ⭐⭐

`reverse()` mutates the array it's called on, and `this.employees()` returns the service signal's own array, so reversing it directly would reorder the service's state in place without the signal knowing — the employees table would suddenly render in reverse with no update having been signalled. Strictly speaking `slice(-5)` already returns a new array, so the spread is redundant here, but the rule it encodes is the important part: never mutate what a signal returns. `toReversed()` would express the same thing in one call.

**[06-hr-portal-044] How does the dashboard greet the user by name, given the session only stores an email?** ⭐

The `username` computed looks the session email up in the `employees` signal and returns `match?.firstName`, falling back with `??` to the part of the email before the `@`. The fallback is needed because a seeded login account doesn't have to exist as an employee record. I derived it rather than storing a display name in the session, so a rename on the employees page shows up in the greeting immediately.

**[06-hr-portal-045] The login page waits one second with `timer(1000)` and uses `takeUntilDestroyed(this.destroyRef)`. Why pass `DestroyRef` explicitly?** ⭐⭐

The timer stands in for the backend call a real login would make, and `takeUntilDestroyed` unsubscribes if the page is destroyed before it fires, so a login left in flight can't navigate an app that has already moved on. Called with no argument, `takeUntilDestroyed` injects `DestroyRef` itself, which only works in an injection context such as a constructor or field initializer; `onSubmit` is a plain method, so I inject `DestroyRef` as a field and pass it in. While it waits, `isLoading` disables the submit button, so the user can't fire a second login.

**[06-hr-portal-046] After login and logout, who navigates — `AuthService` or the component?** ⭐⭐

The components do. `LoginPage` calls `authService.login(email, password)`, then asks `authService.isLoggedIn()` and either navigates to `/dashboard` or shows the error; `App.logout()` calls `authService.logout()` and then `router.navigate(['/login'])`. I kept the `Router` out of the services, so `AuthService` only manages the session and the component that triggered the action decides where the user goes next — the same service could back a login dialog or a test with no navigation at all.

**[06-hr-portal-047] The login form's controls are created with `nonNullable: true`. What does that change?** ⭐

A normal `FormControl('')` is typed `string | null`, because `reset()` sets it back to `null`; with `nonNullable: true`, `reset()` restores the initial `''` and the type is plain `string`. That's what lets `onSubmit` destructure `getRawValue()` and pass `email` and `password` to the service without asserting `null` away. The contrast is visible in the employee dialog, whose `FormBuilder` groups are nullable and need `as string` casts — the login form is the pattern I'd move them to.

**[06-hr-portal-048] The department picker in the employee dialog and the department filter both use `dept.name` as the option value. What does that mean for the employee–department relationship?** ⭐

It means an employee references its department by name, not by id, and the filter compares `employee.department === selectedDepartment()` on that string. It's simple and reads well in the table, but `DepartmentService.editDepartment` doesn't update employees, so renaming a department leaves its employees pointing at a name that no longer exists, and they drop out of the filter's matches. With a backend I'd store the department id and show the name, and even here, storing the id would make a rename safe.

**[06-hr-portal-049] `deactivateGuard` lives in `core/guards/`, but it's typed `CanDeactivateFn<DepartmentForm>` and imports the form component. What does that do to your layering, and how would you fix it?** ⭐⭐

The guard reads `component.departmentForm.dirty`, so `core/` — the layer every feature is supposed to depend on — now imports from `pages/department-page/`, and the dependency points the wrong way: deleting the departments feature would break a core file, which is exactly the test I use for the Core/Feature split. I accepted it because the department form is the only guarded route, but it doesn't scale. The fix is to invert the dependency: declare a small contract in `core/`, such as `interface HasUnsavedChanges { hasUnsavedChanges(): boolean }`, type the guard as `CanDeactivateFn<HasUnsavedChanges>`, and have `DepartmentForm` implement it, so the guard knows a contract instead of a component and any future routed form can reuse it.

**[06-hr-portal-050] In `DepartmentList`, "Delete" emits a `delete` output to the page, but "Edit" is a `[routerLink]` right inside the list. Isn't the presentational child now making a decision?** ⭐⭐

I split them by what each action does. Delete changes state — it needs a confirmation dialog, a service call and a snackbar — so the list only emits the id and `DepartmentPage.onDelete` owns all three. Edit is pure navigation to `['/departments/edit', department.id]` and the routed `DepartmentForm` does the real work, so an output would only add a hop in which the page calls `router.navigate` with the same array; the price is that the list knows the edit URL, and I'd switch to an `edit` output the day it's reused under another route. What I'd still change is the element: it's a `<button>` with `routerLink`, which gets no `href`, so unlike the dashboard's stat cards it can't be opened in a new tab — an `<a mat-button>` would fix that.

**[06-hr-portal-051] Your dialogs hand their result back to the page, yet `DepartmentForm` calls `DepartmentService` itself. Why does the routed form save on its own?** ⭐⭐

A dialog has a caller — the page that opened it and subscribes to `afterClosed()` — so it can return a value and let that caller write. A routed component has none: the router creates it and nothing is waiting for a result, and `departments/new` is a sibling of `departments` in the route table, not its child, so `DepartmentPage` isn't even alive while the form is open. So I made `DepartmentForm` the coordinator of its own route: it checks `nameExists`, calls `addDepartment` or `editDepartment`, opens the snackbar, marks the form pristine and navigates back to `departments`. The rule is the same in both places — whoever owns the screen owns the writes — it just lands on a different component.

**[06-hr-portal-052] The leave-request status dropdown is rendered from `LEAVE_REQUEST_FILTERS`, while the employee status dropdown hardcodes its `mat-option`s. Which one is right?** ⭐

`LeaveRequestFilters` exposes `statusOptions = LEAVE_REQUEST_FILTERS` and renders it with `@for` and `titlecase`, so the options the user can pick, the `LeaveRequestFilter` union and the `isLeaveRequestFilter` check on the query param all come from one `as const` list — adding a status updates all three. `EmployeeFilters` writes `''`, `active` and `inactive` by hand, so a value added to `EMPLOYEE_STATUS_FILTERS` would be accepted from the URL and typed correctly, yet never offered in the dropdown. The difference has a cause: the leave filter's no-filter value is `'all'`, which `titlecase` renders as "All", while the employee one is `''`, which needs a label of its own — so I'd fix it with a small label map over the list, not by keeping the hardcoded options.

**[06-hr-portal-053] How is the app themed, and where do the status badge colours come from?** ⭐⭐

I theme through `mat.theme()` on `html` in `material-theme.scss` — azure primary, blue tertiary, Roboto, density 0, and `color-scheme: light` pinned — which generates the Material 3 `--mat-sys-*` variables every component reads, so I never override a component's internal CSS. The app's own colours are custom properties declared once in `styles.css` `:root`: neutral tokens like `--color-link` alias a `--mat-sys-*` variable so they follow the theme, and the status tokens are background/text pairs such as `--color-pending-bg` / `--color-pending-text`. Each component stylesheet only maps its classes onto those pairs — `.badge.pending` in the leave table, `.status-pending` in `PanelItem`, with `approved` reusing the active green — so a colour changes in one place. I pinned the light scheme because those pairs are fixed hex values that only had a contrast pass against a light surface.

**[06-hr-portal-054] Every `@for` in your templates tracks by a field — `employee.id`, `request.id`, `link.path` — never by `$index`. Why does that matter here?** ⭐

`track` tells Angular which DOM node belongs to which item, so when the array changes it moves, creates or destroys only the nodes whose key changed. These lists are re-derived from signals on every write — a delete shifts every later item, and the dashboard's recent employees are re-sliced and reversed each time one is added — so tracking by `$index` would make Angular reuse the node at a position for a different item and rebind every row after the change. The ids are stable UUIDs the services stamp, and where there is no id I track the value itself: `link.path` in the sidebar and the string itself for the status options.

**[06-hr-portal-055] `EmployeeTable`'s outputs are called `employeeId` and `updatedEmployee`, and they fire on Delete and Edit. What's wrong with those names?** ⭐

They name the payload, not the event, so the page reads `(employeeId)="onDelete($event)"` and `(updatedEmployee)="onEdit($event)"`, and nothing at the binding says what the user asked for; `updatedEmployee` is also misleading, because it emits the row as it is, before any edit has happened. An output should describe what the user did — `DepartmentList` gets it right with `delete` — so I'd rename them `delete` and `edit` and let the payload type (`string`, `Employee`) carry the data. In a coordinator pattern those names are the whole contract between the page and its children, so they're worth getting right.

## Security & Auth

**[06-hr-portal-056] Your guards are plain functions typed `CanActivateFn`, not classes implementing `CanActivate`. Why, and how does a function get hold of `AuthService` and the `Router`?** ⭐⭐⭐

I chose functional guards because a guard in this app is one decision — read the session, return `true` or a redirect — and a function states exactly that, with no `@Injectable` class around it; it's also the style Angular has recommended since v15. The router runs every guard inside the route's injection context, so the first two lines of `authGuard`, `adminGuard` and `noAuthGuard` can call `inject(AuthService)` and `inject(Router)` directly. Because they are just values, I can stack them in an array on a route, so authentication and authorisation stay two small composable guards instead of one class that has to know about both.

**[06-hr-portal-057] Admin routes carry `canActivate: [authGuard, adminGuard]`. Walk me through what happens when a logged-out user types `/employees`. Does the order in that array matter?** ⭐⭐⭐

`authGuard` sees no session and returns `createUrlTree(['/login'])`; `adminGuard` would get `undefined` from `getUserRole()` and return a tree to `/dashboard`. The router resolves the array by position — the first guard that returns something other than `true` decides — so the user lands on `/login` in one redirect. If I swapped the order, `/dashboard` would win, and then `authGuard` on `/dashboard` would bounce to `/login`: the same place, but by two redirects and by accident. I put `authGuard` first on purpose, because "who are you" has to be answered before "what may you do", and that's also why I kept them as two guards instead of letting `adminGuard` imply authentication.

**[06-hr-portal-058] Your guards redirect by returning `router.createUrlTree(['/login'])`. Why not call `router.navigate(['/login'])` and return `false`?** ⭐⭐

Returning a `UrlTree` hands the redirect to the router as the result of the guard, so it cancels the current navigation and starts the new one as a single decision, respecting the priority of the other guards on the route. Calling `navigate` inside a guard starts a second navigation while the first is still being resolved, and returning `false` cancels the first one — two navigations racing, and the outcome depends on timing rather than on the guard order. So all three of my `CanActivateFn` guards return `true` or a `UrlTree` and never navigate themselves.

**[06-hr-portal-059] When an employee opens `/employees`, `adminGuard` sends them to `/dashboard`, not to `/login`. Why?** ⭐⭐

The employee is authenticated, just not authorised, so sending them to `/login` would be wrong in meaning — and `noAuthGuard` would bounce them from there to `/dashboard` anyway, one redirect later. The dashboard is the one page every role can reach, so it's the safe landing. The gap I accepted is that the redirect is silent: the user gets no message saying why, so with more time I'd add a snackbar or a small "not allowed" page instead of a bare redirect.

**[06-hr-portal-060] `adminGuard` checks `getUserRole() === 'admin'`. Why that and not `getUserRole() !== 'employee'`?** ⭐⭐

I wrote it as an allow-list so it fails closed: `getUserRole()` returns `Role | undefined`, and anything that isn't exactly `'admin'` — no session, a missing role, a role added tomorrow — is denied. `!== 'employee'` would let every one of those through. The comparison is also type-checked against the `Role` union derived from the `ROLES` list, so a typo such as `'Admin'` is a compile error ("no overlap"), not a guard that silently never passes.

**[06-hr-portal-061] Nothing breaks if a logged-in user sees the login form, so what is `noAuthGuard` for?** ⭐⭐

It is a guest guard — `authGuard` inverted — on `login` only, and I added it because a logged-in user on the login form is an inconsistent state: they could log in as someone else over an active session, and the browser's Back button after logging in would put them straight back on the form. With `noAuthGuard`, `/login` for an authenticated session returns a `UrlTree` to `/dashboard`, so every path that leads to login — Back, a bookmark, the fallback redirects — ends on the dashboard instead. It's one line, and it makes "logged in" and "on the login page" mutually exclusive.

**[06-hr-portal-062] `canActivate: [authGuard, adminGuard]` is repeated on four routes in `app.routes.ts`. How would you stop the next admin route from forgetting it?** ⭐⭐

Right now each admin route — `employees`, `departments`, `departments/new`, `departments/edit/:id` — declares both guards itself, so a fifth admin route added without them would be open to every logged-in user, and nothing would warn me. The fix is to group them under a componentless parent route, `{ path: '', canActivate: [authGuard, adminGuard], children: [...] }`, so every child inherits the check by its position in the tree rather than by copy-paste. I could go one level further and put all authenticated routes under a parent with `authGuard`, nesting the admin ones inside with `adminGuard`; if a guard had to re-run on every move between siblings, `canActivateChild` is the hook for that.

**[06-hr-portal-063] You protect the admin routes with `canActivate`. When would `canMatch` have been the better choice?** ⭐

`canMatch` decides whether a route matches at all; if it returns `false`, the router skips the route and keeps matching, which here would reach `**`, redirect to `login`, and let `noAuthGuard` bounce the employee to `/dashboard` — the same end, but through two redirects nobody wrote on purpose. `canActivate` makes the refusal explicit, with the redirect in the guard. `canMatch` earns its place when one path should serve a different component per role, and I solved that case differently: `/dashboard` is one component branching on `isAdmin()`. Both keep the lazy chunk from being downloaded for a refused user.

**[06-hr-portal-064] `authGuard`, `adminGuard` and `noAuthGuard` are almost the same five lines. Would you merge them?** ⭐

They encode three different policies — logged in, admin, logged out — and each is readable in one line, so for two roles I kept them explicit. The day a third role appears I'd replace `adminGuard` with a factory, `roleGuard(...roles): CanActivateFn`, or a single guard reading the allowed roles from `route.data`, so the routes declare who may enter instead of the guard file growing per role. The `_route, _state` parameters are the CLI's generated signature, prefixed with `_` because none of these guards reads them.

**[06-hr-portal-065] A logged-in admin reloads the browser on `/employees`. Why doesn't `authGuard` bounce them to `/login` while the app is starting?** ⭐⭐

Because the session is restored synchronously: `AuthService` reads and validates the stored session in its field initializer, so by the time `authGuard` calls `inject(AuthService)` the `currentUser` signal already holds it, and `isLoggedIn()` answers correctly on the very first navigation. That's why my `CanActivateFn` guards can return a plain `boolean | UrlTree`. With a real backend, where the app would have to confirm the token with a request before trusting it, the guard would return an `Observable` of that decision and the router would wait for it — the same mechanism `deactivateGuard` already uses for its dialog.

**[06-hr-portal-066] A logged-out admin opens a bookmark to `/departments/edit/42`. Where do they land after logging in?** ⭐⭐

On `/dashboard`, not on the department they asked for: `authGuard` ignores its `_state` argument and redirects to a bare `/login`, and `LoginPage` always navigates to `/dashboard` after a successful login. It's a real usability gap for deep links. The fix is to carry the target in the redirect — `router.createUrlTree(['/login'], { queryParams: { returnUrl: state.url } })` — and have the login page `navigateByUrl` to it. The router only navigates inside the app, but I'd still accept only a path starting with a single `/`, so the parameter can never become an open redirect if a later version hands it to `window.location`.

**[06-hr-portal-067] Guards only run when a navigation happens. What does a second tab see if the user logs out in the first one?** ⭐

Nothing, until it reloads: each tab has its own `AuthService` instance with its own `currentUser` signal, and I don't listen for the browser's `storage` event, so the second tab keeps its in-memory session while localStorage already says `null`. Its guards keep letting it through, because they read the signal, not the storage, and only a reload re-reads the stored value and ends on `/login`. The fix is to listen for `storage` events on the session key in `AuthService` and set the signal from them, so a logout propagates to every open tab.

**[06-hr-portal-068] An employee opens DevTools, edits the stored session and sets the role to `admin`. What stops them from reaching `/employees`?** ⭐⭐⭐

Nothing, and I say so in PLANNING.md: a session edited to a valid shape with `role: 'admin'` passes the parser and `adminGuard`, because in this project every rule runs in the browser the user controls. The guards decide what the app routes to; they are not a security boundary — the data they "protect" is already in that same localStorage, and the seeded login accounts ship in the JavaScript bundle. Real enforcement needs a server that issues a signed token at login and checks the signature and the role on every request, which is exactly what project 07's Spring Security layer adds; on the client the guards would stay, as UX.

**[06-hr-portal-069] What exactly does the session you store in localStorage contain, and why not the `User` object that matched at login?** ⭐⭐

Only `email` and `role`: the login matches a seeded `User`, which includes the password, and `AuthService` passes it through a private `toSession({ email, role })` before it touches the signal, so the password never reaches `currentUser` or localStorage. I typed that as its own `SessionUser` model so the compiler stops a credential from creeping back into the session. The read-back path goes through the same `toSession`, so even a stored object with extra fields is trimmed to those two before the guards or the interceptor ever see it.

**[06-hr-portal-070] The stored session is read back through a shape check instead of `JSON.parse(raw) as SessionUser`. What would the cast have let through?** ⭐⭐

Two different failures, because the parse runs in a root service's field initializer. A truncated entry makes `JSON.parse` throw, and without the `try`/`catch` that exception escapes `AuthService`'s construction and breaks the app at bootstrap. Valid JSON of the wrong shape would be worse because it's silent: `as` checks nothing at runtime, so an object with no `role` becomes a non-null `currentUser`, `authGuard` reads it as logged in, and the user is inside the app with no role. So I parse into `unknown`, accept it only if `isStoredSession` confirms a string `email` and a role that `isRole` finds in `ROLES`, and return `null` otherwise — a bad entry just means "logged out".

**[06-hr-portal-071] You persist the session in localStorage. If this app had a real JWT, would you keep it there?** ⭐⭐

localStorage is what makes the session survive a reload, and here it holds nothing secret — an email and a role. A real token is different: anything in localStorage is readable by any script on the page, so one XSS bug hands the attacker the token. The alternative is an `HttpOnly` cookie set by the server, which JavaScript can't read at all, at the price of needing CSRF protection because the browser sends it automatically. Either can be defended if the trade-off is named; I'd keep the token in memory or in an `HttpOnly` cookie rather than write it to localStorage myself.

**[06-hr-portal-072] An admin has typed into the department form and clicks a sidebar link. What does `deactivateGuard` do, step by step?** ⭐⭐⭐

The router calls the guard with the `DepartmentForm` instance before leaving the route. If `component.departmentForm.dirty` is `false` it returns `true` and the navigation goes ahead; if it's dirty, the guard injects `MatDialog`, opens the shared `ConfirmDialog` with "Stay" and "Leave", and returns `dialogRef.afterClosed().pipe(map((result) => !!result))`. The router subscribes to that `Observable` and waits: "Leave" closes with `true` and the navigation continues, while "Stay", Escape or a backdrop click close without a `true` value, which `!!` turns into `false`, so the navigation is cancelled and the typed values stay. I return the `Observable` because the answer depends on the user, and a guard can't return a boolean it doesn't have yet.

**[06-hr-portal-073] If the user types a character into the department name and deletes it again, does the guard still ask?** ⭐

Yes, because `dirty` means "the user changed a value at some point", not "the value differs from what was loaded", and it stays `true` until `markAsPristine()` or `reset()`. The opposite direction works in my favour: in edit mode `patchValue` fills the form programmatically, which doesn't mark it dirty, so simply opening an existing department and leaving never asks. If the false prompt mattered, I'd store the initial `getRawValue()` and have the guard compare against it instead of reading `dirty`.

**[06-hr-portal-074] Does `deactivateGuard` protect the admin who closes the tab or presses F5 on a dirty form?** ⭐⭐

No. `CanDeactivate` only runs for navigations the Angular router performs; closing the tab, reloading, or typing another address in the URL bar unloads the page without the router ever being asked, and the typed values are lost. The browser's own hook for that is the `beforeunload` event — a `@HostListener('window:beforeunload')` on the form that calls `preventDefault()` while it's dirty — which shows the browser's generic "leave site?" prompt, since that one can't carry a custom message. I'd add it next to the guard so both exits are covered.

**[06-hr-portal-075] An admin with a dirty department form clicks "Logout" and then chooses "Stay" in the confirmation. What state is the app in?** ⭐⭐

An inconsistent one: `App.logout()` calls `authService.logout()` first and only then `router.navigate(['/login'])`, so by the time `deactivateGuard` asks, the session is already `null`. "Stay" cancels the navigation, so the admin form stays on screen with no session behind it — the sidenav closes and the logout button disappears because they follow `isLoggedIn` — until the next navigation hits `authGuard`. Awaiting the navigation before logging out doesn't work either, because `noAuthGuard` would bounce a still-logged-in user off `/login`. The clean fix is a `/logout` route whose guard clears the session and redirects to `/login`: the form's `canDeactivate` then runs first, and "Stay" leaves both the form and the session intact.

**[06-hr-portal-076] Why attach the token in an interceptor instead of adding the header in each service's HTTP call?** ⭐⭐⭐

I decided the header is attached in exactly one place, `authInterceptor`, which every request made through `HttpClient` passes through once it's registered with `withInterceptors([authInterceptor])`. That way no service can forget the header, and no service has to know where the session lives or what the token looks like — when the token changes from a placeholder to a real JWT, one file changes. Today no service injects `HttpClient`, since the data lives in localStorage, so the interceptor is the wiring a backend would plug into rather than code that runs on every screen.

**[06-hr-portal-077] Why a functional `HttpInterceptorFn` registered with `withInterceptors`, rather than a class registered under `HTTP_INTERCEPTORS`?** ⭐⭐

The app has no `NgModule` and configures `HttpClient` with `provideHttpClient(...)` in `app.config.ts`, where `withInterceptors([authInterceptor])` is the native way to add one; a class interceptor would need `withInterceptorsFromDi()` plus a multi-provider just to reach the same point. The array also makes the execution order visible in one line when a second interceptor arrives. Angular runs the function in an injection context, so `inject(AuthService)` works inside it, and because it reads `currentUser()` on every request, a logout changes the very next request's headers with no extra wiring.

**[06-hr-portal-078] Your interceptor does `req.clone({ setHeaders: { ... } })`. Why can't it just set the header on `req`?** ⭐⭐

`HttpRequest` is immutable in Angular — its `headers` are an immutable `HttpHeaders` too — so the only way to change a request is to build a new one, and `clone` with `setHeaders` copies the original and adds or replaces just that header. Immutability is what keeps a chain of interceptors predictable: each one passes a new request to `next`, and a request that gets retried is re-sent exactly as it was built, never as something an earlier interceptor mutated halfway. I pass the clone to `next` when there is a token and the untouched `req` when there isn't.

**[06-hr-portal-079] Your interceptor sends `Authorization: Bearer <the user's email>`. What's wrong with that as a token, and what changes with a real one?** ⭐⭐⭐

As a credential it proves nothing — it isn't signed, carries no expiry, and anyone who knows an email can type the same header — and I mark it in the file as a placeholder so nobody mistakes it for authentication; it exists only because there is no backend to issue a token. A real token is issued by the server at login, typically a JWT signed with the server's key and carrying the user's identity, role and an expiry, and the server verifies the signature on every request, so it can't be forged or edited on the client. I kept the `Bearer` scheme and the `if (token)` structure so the swap is one line: read the token the login response returned instead of `currentUser()?.email`.

**[06-hr-portal-080] The interceptor adds the header to every outgoing request. Is that a problem, and with a backend, why would the login request go out without it?** ⭐⭐

It would be the moment the app called a third-party API: the session's token would be sent to that host too. With a real backend I'd attach the header only when `req.url` starts with the API's base URL, or let a request opt out through an `HttpContextToken`. A login request would go out bare only because there is no session yet, so `currentUser()?.email` is `undefined` and the `if (token)` branch is skipped — a consequence of timing, not a rule, which is why I'd make the auth endpoints an explicit exclusion instead of relying on it.

**[06-hr-portal-081] What happens in your app when the API answers `401 Unauthorized`?** ⭐⭐

Nothing specific: `authInterceptor` only changes the outgoing request and returns `next(...)` untouched, so a `401` reaches the calling service as an `HttpErrorResponse` and the user keeps a session the server no longer accepts. With a real backend I'd pipe the response through `catchError`, and on a `401` call `authService.logout()`, navigate to `/login` and rethrow, so an expired or revoked token ends the session in one place. A `403` is different — the user is authenticated but not allowed — so it should show a message, not log them out.

**[06-hr-portal-082] No service in this app injects `HttpClient`. How would you prove the interceptor does what its comment says?** ⭐

With a unit test instead of the Network tab: configure `TestBed` with `provideHttpClient(withInterceptors([authInterceptor]))` and `provideHttpClientTesting()`, set a session on `AuthService`, fire a request through `HttpClient`, and assert with `HttpTestingController.expectOne(...)` that `request.headers.get('Authorization')` is `Bearer` plus the email. A second case with no session must see no header at all. The `auth-interceptor.spec.ts` in the project is only the CLI's "should be created" scaffold, so that test is still to be written — automated tests enter the roadmap at project 07.

**[06-hr-portal-083] `/leave-requests` carries only `authGuard`, yet only an admin can approve and an employee sees only their own requests. Where is that authorisation enforced?** ⭐⭐

Inside the page, because the route only answers "is there a session" and both roles are allowed in. The last step of `filteredLeaveRequests` returns every request only when `role()` is exactly `'admin'` and narrows anything else to the session's email, so it fails closed the same way `adminGuard` does, and the table drops the `actions` column from the employee's `displayColumns`. The weak spot is that `LeaveRequestService.updateStatus` enforces the state machine — pending only — but not who may decide, so the invariant lives in the service while the permission lives only in the template; I'd move the role check into the service too, and with a backend the server would check the role on the status endpoint itself.

**[06-hr-portal-084] `login()` and `logout()` only set the `currentUser` signal. How does the session reach localStorage, and what is stored after a logout?** ⭐⭐

I made the stored copy a consequence of the signal: an `effect()` in `AuthService`'s constructor writes `JSON.stringify(this.currentUser())` under the `currentUser` key whenever the signal changes, so a login, a failed login and a logout all persist without any of them remembering to. After a logout that writes the string `"null"` rather than removing the key, and the read path absorbs it: `JSON.parse` returns `null`, `isStoredSession` rejects it, and the app starts logged out. The cost is that an effect runs on Angular's schedule rather than inside the `set` call, so storage trails the signal briefly; nothing reads storage in between, and a `removeItem` branch for `null` would make "logged out" an absent key instead of a literal.

**[06-hr-portal-085] Your login shows one message, "Invalid email or password", whether the email is unknown or the password is wrong. Was that deliberate?** ⭐

Yes — `login()` looks the user up with a single `find` matching email and password together, so it can't tell the two failures apart, and the page shows the one `hasError` message. Saying "no account with that email" would let anyone probe which addresses exist, the first step of credential stuffing; with a real backend the server should keep the same rule and answer both failures alike. A failed attempt also sets `currentUser` to `null` instead of leaving whatever was there, a belt-and-braces reset behind `noAuthGuard`, so a wrong password can never leave an older session standing.

## Business Rules

**[06-hr-portal-086] Your leave requests go from `pending` to `approved` or `rejected` and never back. Why are both decisions terminal, and why does `LeaveRequestService.updateStatus()` enforce that when the buttons are already hidden?** ⭐⭐⭐

I decided a decided request is history: once an employee has been told yes or no, silently flipping it would change a decision people may already have acted on, so `updateStatus()` refuses any move out of a non-`pending` state and any move back into `pending`, and there is no re-open path. I put the rule in the service because that is where the status actually changes — the approve/reject buttons rendering only while `status === 'pending'` is presentation of the rule, and any future caller goes through the service, not through that template. It returns a `boolean` instead of throwing because a refused decision is an expected outcome the page reports, not a crash: `onStatusChange` turns `false` into "Only a pending request can be approved or rejected". From the UI in a single tab that branch should never fire, which is the point — it is the invariant, not the happy path.

**[06-hr-portal-087] `addLeaveRequest` builds `{ id: crypto.randomUUID(), status: 'pending', ...newLeaveRequest }`. Does the order inside that object literal matter?** ⭐⭐

Yes — later properties win, so the caller's spread comes after the two values the service is supposed to own. The parameter is typed `Omit<LeaveRequest, 'id' | 'status'>`, but TypeScript only rejects extra properties on an object literal written at the call site; a variable of a wider type, such as a full `LeaveRequest`, is still assignable, and its `status: 'approved'` or its `id` would overwrite the stamps at runtime. Today it is safe only because the page passes a literal with exactly four fields. `EmployeeService` and `DepartmentService` already write it the right way round — `{ ...employee, id: crypto.randomUUID() }` — and I'd move the leave stamps after the spread too, so "a new request is always pending" holds whatever the caller passes.

**[06-hr-portal-088] How does your leave-request dialog stop an end date that falls before the start date, and what happens if the user fixes it by changing the start date instead?** ⭐⭐⭐

I check it in `onSubmit`: once the required checks pass, `if (endDate < startDate)` sets `setErrors({ invalidDate: true })` on the `endDate` control and returns, and the template shows "End date must be after start date" — although the comparison is strict, so a one-day leave with equal dates is allowed and the message should say "on or after". The weak spot is that a manual `setErrors` only clears when *that* control re-validates: if the user moves the start date earlier, the range is now valid but `endDate` keeps its `invalidDate` error, the form stays invalid, and Submit does nothing while the end field keeps showing a message that is no longer true, until they touch the end date again. The fix is a cross-field validator on the `FormGroup`, which re-runs whenever either date changes, plus `[min]` on the end picker bound to the start date's value, so the calendar cannot offer an invalid day in the first place.

**[06-hr-portal-089] Both datepickers in the leave dialog carry `[min]="today"`. What does that forbid, and what does a user who types a past date by hand actually see?** ⭐⭐

I decided an employee requests leave ahead of time, so the calendar greys out every day before today — and because the date adapter compares by calendar day, today itself stays selectable even though `today` holds the current time. `[min]` also adds a `matDatepickerMin` validator to the input, so a past date typed by hand makes the control invalid, but my messages don't name that error: the start field has a bare `<mat-error>Start date is required</mat-error>`, which Material shows for *any* error, and the end field's `@if` only handles `required` and `invalidDate`, so it turns red with no message at all — the same happens with unparseable text (`matDatepickerParse`). I'd add a branch per error key, and I'd state the rule's cost openly: it excludes retroactive leave, such as a sick day registered afterwards, which a real HR system handles with an admin-entered request.

**[06-hr-portal-090] Can an employee submit two leave requests for the same days?** ⭐⭐

Yes — `addLeaveRequest` appends whatever it receives, and nothing compares a new request against the employee's existing ones, so two overlapping requests can both reach the admin and both be approved. I'd put the rule in the service, next to `updateStatus`, because the service is the one place that holds every request: take this employee's requests that are not `rejected` — a rejection shouldn't stop someone asking for those days again — and refuse when `start <= other.endDate && end >= other.startDate`, returning `false` so the page can show a snackbar exactly as it does for a refused decision. Because the dates are stored as `YYYY-MM-DD` strings, that comparison works directly on the strings. With a backend the check belongs in the server's service layer, since two open tabs could each pass a client-side one.

**[06-hr-portal-091] Only employees see "Submit leave request". Why can't an admin request leave, and where is that enforced?** ⭐⭐

I modelled the two roles as two jobs: the employee asks and the admin decides. If the admin could create a request, the only person able to approve it would be the admin themself, which breaks segregation of duties — nobody should approve their own leave — so I kept the admin's side of the page a pure review screen. It is enforced only by `@if (role() === 'employee')` around the button; neither `openDialog()` nor `addLeaveRequest` checks the role, so it is a UI rule, not an invariant. A real HR system would let an admin request leave and route it to a different approver, which needs a manager relationship this project doesn't model.

**[06-hr-portal-092] Your leave dates are stored as `YYYY-MM-DD` strings built by `toLocalDateString()`. Why not `date.toISOString()`?** ⭐⭐

`toISOString()` converts to UTC first, and the datepicker hands me local midnight, so in Spain (UTC+1 or +2) a leave starting on 10 March would be stored as `2026-03-09` — a whole day early. `toLocalDateString()` builds the string from `getFullYear`, `getMonth` and `getDate`, which read the local clock, so the stored day is the day the user picked; the same helper stamps a new employee's `startDate`. I chose a date-only string over a timestamp because a leave day is a calendar date, not an instant, and the format sorts alphabetically in chronological order, so `matSort` on the date columns works on plain strings. On the way back, the `DatePipe` reads a date-only string as a local date, so `dd/MM/yyyy` prints the same day that was stored.

**[06-hr-portal-093] The employee dialog checks for a duplicate email in `onNext` and again in `onSubmit`. Why isn't the check on `Next` enough?** ⭐⭐⭐

Because a linear `MatStepper` doesn't only move through its buttons: the user can click a step header, and the stepper allows the move to step 2 whenever step 1's `stepControl` is valid — and `required` plus `email` are all that group's validators know about. So a user can press Next with a unique email, go back, change it to one that already exists, and click the "Job info" header: `onNext` never runs. I decided to check the rule at the save exit, where every path ends: `onSubmit` calls the same private `hasDuplicateEmail()`, which flags `duplicateEmail` on the control, and sends the user back with `stepper.selectedIndex = 0`. The check in `onNext` stays as early feedback; the one in `onSubmit` is the rule.

**[06-hr-portal-094] How does `emailExists` decide that two emails are the same, and why doesn't editing an employee flag their own email as a duplicate?** ⭐⭐

I compare `toLowerCase().trim()` on both sides, because `Ana@Company.com` and `ana@company.com` are the same mailbox for any real purpose, and a user shouldn't get a second employee by changing the case. The second parameter, `excludeId`, is the edit-mode fix: the dialog passes `this.data?.employee.id`, so the employee being edited is skipped and saving without touching the email doesn't collide with itself; in create mode it is `undefined` and nothing is skipped. `DepartmentService.nameExists` applies the same rule to department names, with `editId() ?? undefined`. The inconsistency I'd fix is that the comparison normalises but the saved value doesn't, so a department saved as `"HR "` keeps its trailing space in the table and in every employee that picks it.

**[06-hr-portal-095] You flag duplicates by calling `setErrors({ duplicateEmail: true })` from a method, not with a custom validator on the control. What's the trade-off?** ⭐⭐

`setErrors` puts the error on the right control so its `mat-error` renders, and it clears itself the right way: the next keystroke re-runs the control's own validators, which replace the errors object, so the message goes away as soon as the user edits the email. The cost is that the rule isn't part of the control — between checks the control reports itself valid, which is exactly why the stepper header can skip past it and why I need the second check at the save exit. A synchronous custom validator — a factory closing over `EmployeeService` and the id being edited — would keep the control invalid for as long as the email is taken, so `[stepControl]` itself would block the header and the manual calls would go; the data is an in-memory signal so it needn't be async, but with a backend it would become an `AsyncValidator` with a debounce. `DepartmentForm` uses the same `setErrors` pattern for `duplicateName`.

**[06-hr-portal-096] Can an admin create a department whose name is three spaces?** ⭐⭐

Yes. `Validators.required` only rejects `null`, `undefined` and an empty string or array, and `"   "` has length 3, so it passes — and the same is true of an employee's first name, last name and position, and of a leave request's reason. `nameExists` trims when it compares, so a second blank name would be caught as a duplicate, but the first one saves and shows up as an empty row. I'd add a whitespace-rejecting validator such as `Validators.pattern(/\S/)` to those controls and trim the values when building the entity, so what is stored matches what the uniqueness check compared.

**[06-hr-portal-097] `Department.description` is optional in the model, but the department form makes it required. Which one states the rule?** ⭐

The form does: PLANNING.md lists `name` and `description` as required, and every department is created through `DepartmentForm`, which refuses an empty description. The model's `description?: string` is looser than the rule, so the type accepts a department the app never creates, and every reader has to handle an `undefined` that should not exist. I'd make the two agree — required in the interface, or, if a description were genuinely optional, drop `Validators.required` and the "Description is required" message together.

**[06-hr-portal-098] An admin deletes a department that still has employees. What happens to those employees?** ⭐⭐

Nothing, and that's the gap: `deleteDepartment` removes only the department, and its employees keep its name in their `department` field, because they reference it by name, not by id. The table still shows the old name, but the department filter is built from the departments list, so those employees can only be found under "All". Opening one in the edit dialog shows an empty department select — no option matches the value — yet the control still holds the old name, so `required` passes and saving keeps the orphan silently. The rule I'd add is the usual one — refuse to delete a department that still has employees and tell the admin how many — and with a backend a foreign key from employee to department makes the database enforce it.

**[06-hr-portal-099] What does an admin see if they click "Add Employee" before any department exists?** ⭐

The dialog opens and step 1 works, but the "Department" select in step 2 has no options, so its `required` validator can never pass and the save stays blocked behind "Department is required" — a message the user cannot act on from inside the dialog. On a first visit that is the normal state, because every collection starts empty. I'd make the dependency visible where it begins: disable "Add Employee" while `departments().length === 0`, with a hint and a link to `/departments/new`, rather than let the dialog reach a dead end.

**[06-hr-portal-100] An admin deletes the employee record of the person who logs in as `employee@hrportal.com`. Can that person still log in and request leave?** ⭐⭐

Yes. Employee records and login accounts are two separate things here: the records live in `EmployeeService`, the accounts are the seeded users in `AuthService`, and the only link between them is an email that happens to match, which the dashboard uses for its greeting and nothing else. Leave requests carry the session email, not an employee id, so deleting or re-emailing a record doesn't touch them, and the person keeps logging in and submitting. I accepted it because authentication is a stand-in in this project; with a backend the account would reference the employee by id, and I'd deactivate the employee instead of deleting them, so the history stays and access ends in one change.

**[06-hr-portal-101] Leave requests have a state machine, but an employee's `status` is a free choice between `active` and `inactive`. Why the difference, and what does `inactive` actually do?** ⭐⭐

I only drew a state machine where the transitions carry meaning: a leave decision is a one-way event made by someone else, so `pending → approved | rejected` is enforced, whereas an employee's status is a fact the admin records, so either value can be chosen at creation and changed at any edit, and the form requires an explicit choice instead of defaulting one. In this project `inactive` is informational only: it changes the badge, the "Active Employees" count on the dashboard and what the status filter returns — it doesn't block a login, since accounts aren't linked to records, and it doesn't stop leave requests. If it had to mean "no longer works here", it would need rules attached, such as refusing new leave requests, and at that point it would stop being a plain field.

**[06-hr-portal-102] Deleting an employee or a department asks for confirmation, but approving or rejecting a leave request doesn't. Is that consistent?** ⭐⭐

Not fully. I put a `ConfirmDialog` in front of both deletes because they are irreversible — the `effect()` writes the shortened array to localStorage straight away and the snackbar only offers "Close", not "Undo" — and a confirmation is cheaper than an undo that has to keep the removed entity and restore it. But approve and reject are just as irreversible, since both states are terminal, and a misclick on "Reject" is final with no confirmation at all. I'd either confirm the decision too or, because reviewing requests is frequent and frequent confirmations become reflex clicks, hold the decision until the snackbar's "Undo" window closes, so the state machine itself never needs a way back.

**[06-hr-portal-103] Your login form validates the email format and `minLength(8)` on the password. Should a login form enforce a password length?** ⭐⭐

The email check earns its place — it catches a typo before any attempt — but a length rule belongs to setting a password, not to logging in. At login the only real question is whether the pair matches: a length check there would lock out any account created under an older, shorter policy, and it answers a short password with "Password must have 8 characters" instead of the single "Invalid email or password" the page otherwise gives. It works today only because the seeded `admin123` happens to be exactly eight characters, and it is also drift from PLANNING.md, which only says both fields are required. I'd keep `required` and `email` on login and move the length rule to wherever passwords are created.

**[06-hr-portal-104] Your error messages sit inside `@if (control?.touched && ...)`, and every submit calls `markAllAsTouched()`. Why both, and are the `touched` checks needed?** ⭐⭐

The rule is that a message appears only once the user has reached the field, since `required` fails from the moment the form is built. Inside a `mat-form-field`, though, Material already applies it: `mat-error` only displays when the control is invalid and either touched or in a submitted form, which is why the department form's bare `<mat-error>Description is required</mat-error>` behaves correctly — so the `touched` in my `@if`s is redundant, and the `@if` is really choosing *which* message to show. `markAllAsTouched()` is the part that matters: the employee and leave dialogs put their buttons in `mat-dialog-actions`, outside the `<form>`, so the form is never submitted, and without it a user who clicks Save on an untouched form would see nothing happen and no reason why.

**[06-hr-portal-105] Every domain service builds its signal from `readStoredArray()`. What does it protect against, and what does it deliberately not check?** ⭐⭐

It survives two bad values in localStorage: a truncated or hand-edited entry, where `JSON.parse` throws, and valid JSON that isn't an array, such as `{}`, which parses without complaint and would then break every `@for` and `.filter()`. Both return `[]`, the same state as a first visit, and that matters because the call runs in a root service's field initializer, where an exception fails the whole bootstrap on every reload; the service's `effect()` then writes `[]` back, so the bad entry is replaced rather than hit again. It doesn't validate the elements — a stored `[{}]` renders as a blank row, and the name search then throws on `employee.firstName.toLowerCase()` — because that is a per-entity guard, and I wrote one only for the session, whose wrong shape opens the app with no role: a broken collection breaks a screen, not access.

**[06-hr-portal-106] An admin has `/leave-requests` open in two tabs, approves a request in one and rejects the same request in the other. What ends up stored?** ⭐

The rejection. Each tab loaded its own copy of the requests at bootstrap, so the second tab still holds the request as `pending`, its `updateStatus()` check passes against that stale copy, and its `effect()` writes its whole array to localStorage, overwriting the approval and any other request change the first tab made. The pending-only rule protects the state the service knows, not the state in storage. Here I'd reload the signal on the browser's `storage` event; with a backend the fix belongs on the server — an update that only applies `WHERE status = 'pending'`, or optimistic locking with a version column, answering the losing tab with a `409 Conflict`.

**[06-hr-portal-107] The employee form has no start-date field. Where does an employee's `startDate` come from, and what happens to it on edit?** ⭐

I decided the admin doesn't type it: in create mode `EmployeeDialog.onSubmit` stamps `toLocalDateString(new Date())`, and in edit mode it closes with `this.data.employee.startDate`, so an edit can never move the date and both modes still close with the full `EmployeeFormResult` shape. The cost is that the column means "the day this record was created", not the day the person started — onboarding someone who joined last month records today, and nothing in the UI can correct it. In a real HR system the hire date is business data the admin enters, usually in the past, so I'd add a required datepicker to the "Job info" step with no `[min]`, and keep a create-time stamp only as a separate audit field.

**[06-hr-portal-108] Once an employee has submitted a leave request, can they withdraw or change it while it is still `pending`?** ⭐⭐

No — the employee's table has no `actions` column at all, `LeaveRequestService` exposes only `addLeaveRequest` and `updateStatus`, and `updateStatus` only moves a pending request to `approved` or `rejected`, so a mistyped date sits in the admin's queue until they reject it. I kept the state machine to the one decision the project needed, but it is the first follow-up that diagram invites, because real employees change plans. I'd add a `cancelled` state, reachable only from `pending` and only by the request's owner, terminal like the other two so the admin's approve/reject can't touch it — a status rather than a delete, so the record of what was asked survives — and leave editing out, since cancel-and-resubmit keeps every filed request immutable.

**[06-hr-portal-109] Is there any limit on how many days an employee can request?** ⭐

None. The dialog checks that both dates exist, that neither is before today and that the end isn't before the start, so a request spanning the next two years, or one covering only a weekend, passes exactly like a two-day break. It isn't among PLANNING.md's rules, and it couldn't be without data this project doesn't model: an entitlement per employee, a working-day calendar, and a balance that approved requests draw down. If I added it, the day count would be working days between the two dates and the check would live in `LeaveRequestService` next to `updateStatus`, refusing a request that exceeds the remaining balance — and with a backend, in the server's service layer, because the balance is shared state two tabs could both spend.

**[06-hr-portal-110] Your duplicate check treats `Ana@Company.com` and `ana@company.com` as the same employee. Does the login agree?** ⭐

No. `AuthService.login` matches with `user.email === email`, so `Admin@hrportal.com` with the right password is refused as "Invalid email or password", and the dashboard's greeting looks the session email up in the employee records with the same exact `===`, so a record saved as `Employee@hrportal.com` is never found for that user. The rule "an email is case-insensitive" lives inside `emailExists` and nowhere else. I'd normalise once, at the edge — trim and lowercase the value when a form is read, before it reaches `login` or is stored — so every later comparison can stay a plain `===`; with a backend the API does the same, usually backed by a unique index on the lowered column.

## Technical Decisions

**[06-hr-portal-111] Your shared state is a handful of signals in root services. Why not NgRx, or a service built on `BehaviorSubject`?** ⭐⭐⭐

The app has four pieces of shared state — the session and three collections — each with exactly one owner and no asynchronous source, since everything lives in localStorage. I chose a `signal` per collection in a `providedIn: 'root'` service because it gives me synchronous reads, which is what lets `authGuard` return a plain boolean on the first navigation, `computed()` for every derived view (filters, totals, the role-aware sidebar), and `effect()` for persistence, with no subscriptions to manage in the components. A `BehaviorSubject` would give the same single owner but push every template onto the `async` pipe or manual subscriptions, and NgRx would add actions, reducers and effects around three arrays and a session. I'd reach for a store when several features coordinate complex asynchronous flows over the same state, or when I need its devtools; a backend alone wouldn't force it.

**[06-hr-portal-112] Type a search on the employees page, go to the dashboard and come back: the search is gone, but every employee is still there. Why do those two pieces of state behave differently?** ⭐⭐

Because I put them in different lifetimes on purpose. The filters — `searchTerm`, `selectedDepartment`, `selectedStatus` — are signals on `EmployeePage`, so they are created with the page and destroyed when the router swaps it out; the employees live in `EmployeeService`, a `providedIn: 'root'` singleton that lives as long as the app, so every page reads the same array. Filters are how one visit looks at the data, not data, so starting clean on each visit is the behaviour I wanted. If they had to survive, I'd move them into the URL as query params, which also makes a filtered view bookmarkable, rather than into the service, where UI state would get mixed with the domain data every other page reads.

**[06-hr-portal-113] `LeaveRequestService.leaveRequests` is a public `WritableSignal`, and `LeaveRequestPage` aliases it. What stops a component from calling `.update()` on it and approving a request without going through `updateStatus()`?** ⭐⭐

Nothing — only convention. The page's `leaveRequests` field is the service's own `WritableSignal`, so any component that injects the service could `set` or `update` it directly and skip the pending-only check that `updateStatus()` exists to enforce; the same goes for employees, departments and even `currentUser`. The fix I'd make is the idiomatic one — keep the writable signal private and expose a read-only view: `private readonly requests = signal<LeaveRequest[]>(...)` and `readonly leaveRequests = this.requests.asReadonly()`. Then the compiler makes the service's methods the only way to write, which is what turns the state machine into a real invariant instead of a rule every caller has to remember.

**[06-hr-portal-114] Your services always write `update(list => [...list, item])` or `.map()` / `.filter()`. Why not just `push` the new item into the array?** ⭐⭐

A signal decides whether it changed by comparing references with `Object.is`, so mutating the array it holds and handing the same reference back looks like "no change": the `computed()` filters and totals wouldn't re-run, the table's `effect()` wouldn't push new rows, the persistence `effect()` wouldn't write localStorage, and in a zoneless app the view wouldn't re-render at all. So I build a new array in every write — spread to add, `map` to edit, `filter` to delete — which is what makes each change visible to everything that depends on the signal. The same rule applies to the objects inside: `updateStatus()` replaces the matching request with `{ ...request, status: newStatus }` rather than assigning `request.status`.

**[06-hr-portal-115] There is no `zone.js` in this project. When the login timer fails and sets `hasError`, what makes the error message appear on screen?** ⭐⭐

The app is zoneless — Angular 21's default, and `package.json` has no `zone.js` — so nothing patches `setTimeout` or RxJS timers, and change detection runs only when Angular is told something changed. What tells it here is the signals: `hasError` and `isLoading` are read in the login template, so `hasError.set(true)` inside the `timer(1000)` callback schedules a render of that view. Had they been plain boolean fields, the assignment would happen and nothing would redraw until the user's next click or keystroke, leaving the disabled "Sign in..." button on screen after a failed login. Reactive-form state such as `touched` or `setErrors` isn't a signal either, but it always changes inside a handler bound in the template — an input, a blur, a click on Save — and those listeners schedule change detection by themselves, which is why keeping all state in signals was enough to make zoneless safe.

**[06-hr-portal-116] None of your components uses `ChangeDetectionStrategy.OnPush`. Would you add it, and what would it change?** ⭐⭐

Yes, and here it would be almost free. With the default strategy, every render Angular schedules re-checks every component in the tree; with `OnPush` a component is checked only when one of its inputs changes, an event fires inside it, or a signal its template reads changes. This app already meets those conditions — the pages read service signals, the presentational children receive everything through `input()` and report through `output()`, and nothing mutates a plain field from a callback — so the gain is that approving one leave request re-checks the page and its table, not the sidebar and the toolbar too. It doesn't matter at this size, which is why I left the CLI default, but I'd make it the default for new components, because it turns any plain-field mutation into a visible bug instead of one that happens to work.

**[06-hr-portal-117] Your components inject with `private employeeService = inject(EmployeeService)` instead of constructor parameters. Is that only style?** ⭐⭐

No — it's what lets `DashboardPage` declare `employees = this.employeeService.employees` and several `computed()` fields as field initializers, and `inject()` works there because field initializers run inside the injection context while the component is being constructed. With a constructor parameter property, the project's ES2022 target initialises class fields before the constructor assigns its parameters, so TypeScript rejects `this.employeeService` in a field initializer as used before its initialization, and every derived field would have to move into the constructor body. I chose it also because the same function works in the functional guards and the interceptor, so there's one injection style in the whole codebase — and the one rule it imposes is order: the `inject()` field has to be declared above the fields that use it.

**[06-hr-portal-118] Your tables sort and paginate in the browser through `MatTableDataSource`. When would that stop being acceptable, and what would you change?** ⭐⭐

It works because each collection is small and already entirely in memory: the page's `computed()` filters the full array, and the data source sorts and slices it for the paginator on the client. With a backend and thousands of employees, sending the whole table to the browser to show ten rows wastes bandwidth and memory, so I'd move paging and sorting to the server — the table would request `page`, `size` and `sort` from the API, the paginator's `length` would come from the total count in the response, and I'd listen to the paginator's `page` event and `matSort`'s `sortChange` to trigger each request. The filters would move into those requests as query params too, because filtering a single page on the client would only filter the ten rows it holds.

**[06-hr-portal-119] Your URLs are `/employees`, not `/#/employees`. What does the server have to do for a reload on `/employees` to work, and why not the hash strategy?** ⭐⭐

`provideRouter(routes)` uses the path location strategy with `<base href="/">`, so a reload sends `GET /employees` to the server, and a static host has no such file: without a fallback rule that serves `index.html` for every unknown path, the user gets the host's 404 before Angular even starts. Nothing in this project folder provides that rule — `public/` holds only the favicon — so it has to come from the host's own configuration, and I'd rather version it next to the code, as a `_redirects` file on Netlify or the equivalent elsewhere. `withHashLocation()` avoids the problem because the fragment never reaches the server, but it gives uglier URLs and is the older convention; I kept clean paths and accept that the host must know the app is an SPA.

**[06-hr-portal-120] You subscribe to `afterClosed()` at every dialog call site and never unsubscribe. Is that a memory leak?** ⭐

No, because those observables finish on their own: `afterClosed()` emits once, when the dialog closes, and then completes, so each subscription ends with its dialog. The same holds for the `backdropClick()` subscription in `EmployeeDialog`'s constructor, which completes when the dialog's overlay is disposed. That's the difference from the login page, where I pipe `timer(1000)` through `takeUntilDestroyed`: the timer completes too, so that one isn't about a leak, it's about not running a callback that navigates after the page is gone. An endless stream subscribed in a component — `valueChanges`, a route's `paramMap`, an interval — is where I'd always tie the subscription to `DestroyRef`.

**[06-hr-portal-121] Every page is its own `loadComponent`. When would `loadChildren` with a feature routes file have been the better choice?** ⭐

`loadChildren` lazy-loads a whole `Routes` array, so a feature owns its own route table: the three department routes would move into a `department.routes.ts` loaded from one `departments` entry, and `app.routes.ts` would stop knowing about `new` and `edit/:id`. I chose `loadComponent` because every area but departments has exactly one route, and a single flat table reads one-to-one against the routes table in PLANNING.md; the chunks come out the same either way, since `departments/new` and `departments/edit/:id` import the same `DepartmentForm` file and the bundler emits it once. I'd switch the day a feature grows several routes of its own, or when a team owns a feature and should be able to change its routes without touching the root file.

**[06-hr-portal-122] Whatever page you're on, the browser tab says "06HrPortal". How would you fix that?** ⭐

That's the `<title>` the CLI generated in `index.html`, and no route declares a `title`, so the router never changes it. I'd give each route in `app.routes.ts` a `title: 'Employees'`, which the router's default title strategy writes into the document on every successful navigation, and a custom `TitleStrategy` to append the app name everywhere, as in "Employees · HR Portal". It's more than cosmetic: the title is what browser history, bookmarks and open tabs show, and what a screen reader announces after a navigation in a single-page app, so with one fixed title every page sounds the same.

**[06-hr-portal-123] You configure `provideHttpClient(withFetch(), ...)`. What does `withFetch()` change, and what does it cost you?** ⭐

It makes `HttpClient` send requests through the browser's `fetch` API instead of `XMLHttpRequest`; the services and the interceptor don't see the difference, because they talk to `HttpClient` either way. I chose it because `fetch` is the modern browser API and the backend Angular's docs recommend once an app is server-rendered, so the configuration doesn't have to change if this one ever is. The cost is upload progress: with `withFetch()`, `reportProgress` can't report upload events, so a file upload with a progress bar would need the XHR backend back. Today no service injects `HttpClient` at all, so the choice has no runtime effect yet — it's configuration for the backend project 07 adds.

**[06-hr-portal-124] Your templates read controls through getters such as `get email() { return this.loginForm.get('email'); }`. What does that cost you compared with `loginForm.controls.email`?** ⭐

`get('email')` looks the control up by a string and returns `AbstractControl | null`, which is why every template check needs `email?.touched` and `email?.hasError(...)`, and a misspelled name would compile and just return `null`. `loginForm.controls.email` is typed from the form's definition — a `FormControl<string>` that is never null — so a typo is a compile error and the `?.` goes away. I already use that form in code, as in `departmentForm.controls.name.setErrors(...)`, so the getters are an inconsistency rather than a need. They also run on every change-detection pass, which is negligible here, but it's one more reason to bind to typed fields instead of lookups.

**[06-hr-portal-125] Every service persists to localStorage and none injects `HttpClient`, yet the project root holds a `db.json` with empty `employees`, `departments` and `leaves` arrays. Why localStorage instead of a mock REST API such as json-server, and what would switching cost?** ⭐⭐

I chose localStorage because the project was about Angular patterns — routing, guards, signals, coordinator pages — not persistence, and because it keeps every read synchronous: each service builds its signal from `readStoredArray()` at construction, so the guards can return a plain boolean and no page needs a loading or error state. The `db.json` is dead scaffolding — nothing reads it, `package.json` has no json-server script, and its `leaves` key doesn't even match the `leaveRequests` key the service stores under — so I'd delete it rather than let it suggest a backend the app doesn't have. Switching to HTTP would reach well beyond the services: every read becomes asynchronous, so the signals would be filled from a request, each page would need loading and error states, a write would wait for the server instead of being one `update()` call, and the synchronous session restore that `authGuard` relies on would become an observable decision the router has to wait for.

**[06-hr-portal-126] Every form in the app is a reactive form. Why not template-driven forms with `ngModel`?** ⭐⭐

Several parts of this project need the form to be an object on the class rather than something the template creates: `[stepControl]="firstFormGroup"` hands each `MatStepper` step a `FormGroup` to validate, `deactivateGuard` reads `component.departmentForm.dirty` from outside the component, and the duplicate checks call `controls.email.setErrors(...)` from a method. With template-driven forms the model lives in the `NgForm` and `NgModel` directives the template creates, so I'd have to reach it through `@ViewChild(NgForm)`, which only exists after the view renders, and the validators would be attributes scattered across the HTML instead of one declaration next to the model. I chose reactive forms for that — typed controls, validators beside the data, state readable from anywhere — and the price is more code on a two-field form like the department one, where `ngModel` would have been shorter. Angular 21's Signal Forms are the direction this is heading, but they are still experimental, so I kept a stable API for the whole app.

**[06-hr-portal-127] Your services stamp ids with `crypto.randomUUID()`. Why not `Date.now()` or an incrementing counter, and where can that call fail?** ⭐

I put id generation inside each service's add method so no caller builds its own, and chose a UUID because `Date.now()` returns the same value for two entities created in the same millisecond, while a counter would have to be persisted beside each collection and could still hand out the same number in two open tabs. A random UUID needs no shared state, and as an opaque string it doubles as the stable `track` key in the templates and as the `:id` in `departments/edit/:id`. The catch is that `crypto.randomUUID()` only exists in a secure context — HTTPS or `localhost` — so the deployed site and `ng serve` are fine, but opening the dev server from a phone over the LAN IP (`http://192.168.x.x:4200`) makes every "Add" throw `crypto.randomUUID is not a function`; `crypto.getRandomValues()` is available there if that case ever mattered.

**[06-hr-portal-128] Your templates use `@if` and `@for` everywhere, but the tables still use `*matHeaderRowDef`, `*matRowDef` and `*matNoDataRow`. Why the mix?** ⭐

I used the built-in control flow for my own branching and lists because it's compiled into the template: no standalone component has to import `NgIf` or `NgFor`, `@for` makes the `track` expression mandatory, and it gives me `@empty` and `@if (...; as value)`, which the dashboard panels and `PanelItem` rely on. The `*` in the tables is a different mechanism: `matHeaderRowDef`, `matRowDef`, `matCellDef` and `matNoDataRow` are Material directives that receive an `<ng-template>` for the table to stamp out per row, not control flow, so there is no `@` equivalent and they stay structural. The rule I follow is `@` for control flow, and `*` only where a library asks me for a template to fill.

**[06-hr-portal-129] The table status badges bind `[ngClass]="employee.status"`, `PanelItem` builds `class="status-badge status-{{ value }}"`, and the filter footer uses `[class.active]`. Which would you keep?** ⭐

They all work, but they're three spellings of one idea, and `[ngClass]` is the one I'd drop: for a single class name it adds a directive and an `NgClass` import to `EmployeeTable` and `LeaveRequestTable` where a native binding does the same job, and Angular's current best-practice guidance prefers `[class]` bindings over `NgClass`. I'd write `<span class="badge" [class]="employee.status">` — Angular merges the static class with the bound one — and keep `[class.active]` for the on/off toggle in the filter footer, which is exactly what the single-class binding is for. It's worth making consistent because those class names are the only link between a status value and its colour pair in `styles.css`, and one spelling makes a status without a matching class easy to spot.

**[06-hr-portal-130] What does the HR portal look like on a phone?** ⭐

Not great, and that was a decision: the dashboard card grid collapses at 1024px and 768px, but the data tables and the `MatSidenav` shell target desktop — the sidenav is `mode="side"` with a fixed 220px width and opens whenever there is a session, so on a phone it permanently takes a large slice of the screen while each table scrolls sideways inside its `overflow-x: auto` wrapper. I accepted it because an HR back office is a desktop tool and PLANNING.md records it as a deliberate scope limit for a demo. The fix is cheap and standard: the CDK's `BreakpointObserver` would switch the sidenav to `mode="over"` behind a menu button in the toolbar below a breakpoint, and on small screens I'd drop the less important columns through a `displayColumns` list, the same mechanism the leave table already uses per role.

## Testing

**[06-hr-portal-131] Your HR portal has 27 `.spec.ts` files. What do they actually test?** ⭐⭐⭐

Very little behaviour, and I say so up front: of the 28 tests, 27 are the CLI's `should create` / `should be created` checks, and the only real assertion is the app spec reading the toolbar title. Automated testing enters my roadmap at project 07, so PLANNING.md for this project carries no testing steps by design; what I did here was keep the generated suite green on `ng test` — the Angular CLI's Vitest builder in jsdom, which I left at its default — instead of deleting it. What the component and service specs do prove is that each unit can be built with the dependencies it injects and that its template compiles, which is how nine broken specs surfaced when I ran the suite. The behaviour tests — the leave-request state machine, the guards, the interceptor — are the ones I'd write first, and project 07 is where I write that kind of test for real.

**[06-hr-portal-132] `app.config.ts` already provides the router and the native date adapter. Why do your specs provide them again?** ⭐⭐

Because `TestBed` builds its own injector and never runs `bootstrapApplication(App, appConfig)`, so nothing in `app.config.ts` exists inside a spec. When I ran the suite, nine specs were red — every one missing a provider its unit or its template resolves, such as the `ActivatedRoute` that `routerLink` needs or `MatDialogRef`, and the app spec also still asserting the CLI's placeholder heading — and I fixed each one by supplying exactly what that unit injects: `provideRouter([])` for the shell and the pages, doubles for the dialogs, and `provideNativeDateAdapter()` only in `LeaveRequestDialog`'s spec, because its two `matDatepicker` inputs resolve a `DateAdapter`. The same rule works in the other direction: `LeaveRequestDialog` is always opened without `data` and never injects `MAT_DIALOG_DATA`, so its spec provides no data token at all. I didn't spread `appConfig.providers` into every `TestBed`, because that would pull the real routes, `HttpClient` with the interceptor and the global error listeners into every unit test and hide which dependency each unit really has.

**[06-hr-portal-133] The app spec, the page specs and two dashboard children provide `provideRouter([])`. Why a router at all, and why an empty route list instead of your real `routes`?** ⭐⭐

What those units need is `ActivatedRoute`, which `routerLink` injects and only `provideRouter` registers — the `Router` itself is `providedIn: 'root'`, which is why `LoginPage` injects `Router` and its spec stays green with no router provider, while the shell, the dashboard's `StatCard` and `DashboardPanel` and the department pages render `routerLink`, and the employee, leave-request and department-form pages inject `ActivatedRoute` directly. I passed an empty list on purpose, because none of these specs asserts navigation: the real `routes` would bring the lazy `loadComponent` imports and the guards into tests that never navigate. I used `provideRouter` rather than `RouterTestingModule` because that module is deprecated and `provideRouter` is the same provider the app uses. If I wanted to test navigation, I'd pass the real routes and drive them with `RouterTestingHarness`.

**[06-hr-portal-134] The app spec's second test checks that `.app-title` contains "HR Portal". What does it prove, and what doesn't it?** ⭐⭐

It proves the shell renders: the component is created, the template runs, and the toolbar title is in the DOM. I replaced the CLI's check for an `h1` reading "Hello, 06-hr-portal", which the real shell doesn't have, and kept the `await fixture.whenStable()` before the query, because the app is zoneless — the fixture renders through Angular's scheduler, and awaiting it is how the test knows the view is drawn. What it doesn't cover is the part of the shell with logic: the spec runs with an empty jsdom `localStorage`, so there is no session, and it asserts the one element that doesn't depend on one. The next test I'd write seeds `localStorage` with an employee session under the `currentUser` key before `createComponent` — `AuthService` reads storage when it's constructed — and asserts that no `/employees` link is rendered; I'd also target a `data-testid` rather than a styling class, so a CSS rename can't break the test.

**[06-hr-portal-135] `ConfirmDialog`'s spec provides `MatDialogRef` as a plain `{ close }` object and a typed `ConfirmDialogData`. Why doubles instead of opening the dialog with `MatDialog`?** ⭐⭐

`MatDialogRef` is created by `MatDialog.open()`, so mounting the component straight into a fixture leaves it unprovided; a `useValue` double stands in for it, so I test the component itself without the overlay machinery a real dialog brings. I typed the data object as the dialog's own `ConfirmDialogData`, with all four labels every caller passes, so a change to that contract breaks the spec at compile time instead of rendering `undefined`. The comment says `close()` can be observed, but no test observes it yet; the test it's set up for is `vi.spyOn(dialogRef, 'close')`, a click on the confirm button, and `expect(dialogRef.close).toHaveBeenCalledWith(true)`. Before adding that I'd build the double inside `beforeEach` rather than at `describe` level, so a spy or a recorded call can't leak from one test into the next.

**[06-hr-portal-136] Your `EmployeeDialog` spec's `MatDialogRef` double has a `backdropClick: () => EMPTY` next to `close`. Why, and why `EMPTY`?** ⭐⭐

A double has to answer every member the unit actually touches, and `EmployeeDialog`'s constructor subscribes to `dialogRef.backdropClick()`, so a bare `{ close }` throws before the component exists — the leave-request dialog's constructor reaches nothing but `close`, which is why its double is exactly that. `EMPTY` completes without ever emitting, which is the honest stand-in for a backdrop nobody clicks in this spec: the subscription runs and nothing fires. The limit is that the backdrop path is then untestable; to cover it I'd return a `Subject<MouseEvent>` instead, call `next()` on it with the forms still pristine, and assert that `onCancel()` called `dialogRef.close()` directly — the dirty-form branch opens a nested `ConfirmDialog`, so that case would also need a `MatDialog` stub.

**[06-hr-portal-137] The same spec provides `MAT_DIALOG_DATA` with `useValue: undefined`. Why provide a token just to give it no value?** ⭐⭐

The dialog injects `inject<EmployeeDialogData | undefined>(MAT_DIALOG_DATA)` without `optional: true`, so a token nobody provides is a `NullInjectorError`, not `undefined`. Providing it as `undefined` reproduces exactly what `MatDialog` gives the dialog when `openDialog` opens it without `data`, so the spec builds the create mode on purpose rather than by omission. The consequence is that edit mode — the constructor `patchValue`ing both form groups from `data.employee` — is not built by any spec. I'd cover it with a nested `describe` whose `beforeEach` calls `TestBed.overrideProvider(MAT_DIALOG_DATA, { useValue: { employee } })` before `createComponent`, and assert that the form groups hold that employee's values and that the edit title renders.

**[06-hr-portal-138] The `StatCard`, `DashboardPanel` and `PanelItem` specs call `fixture.componentRef.setInput(...)` before `whenStable()`. What happens without those lines, and why not assign the property?** ⭐⭐

Those children declare `input.required()`, and reading a required signal input that has no value throws `NG0950`, so the first render would fail and `should create` would go red. `componentRef.setInput` is the way to set inputs from outside a template: it goes through the same path a parent binding uses and marks the view for update. Assigning to the field doesn't work, because an `InputSignal` is read-only — there's no `set` to call. Each spec sets exactly the required inputs, with realistic values such as `'Total Employees'` and `'/employees'`, and leaves optional ones like `PanelItem`'s `status` at their default.

**[06-hr-portal-139] Why is the harness in `deactivate-guard.spec.ts` typed `CanDeactivateFn<DepartmentForm>` when the CLI generated `CanDeactivateFn`?** ⭐

The CLI can't know which component a `CanDeactivateFn` guards, so it generates the harness with the default `unknown`, but `deactivateGuard` is declared against `DepartmentForm` because it reads `component.departmentForm.dirty`. A harness forwarding an `unknown` component into a function that expects `DepartmentForm` doesn't compile, so I typed the harness to the same component the guard names. The cost is that the spec imports a page component into a `core/` test — the same wrong-way dependency the guard itself has. With the guard typed against a small `HasUnsavedChanges` contract instead, a behaviour test could pass a plain `{ hasUnsavedChanges: () => true }` stub and never touch the department feature.

**[06-hr-portal-140] Your guard specs end with `expect(executeGuard).toBeTruthy()`. Can that test fail?** ⭐⭐

Not in any way that involves the guard: `executeGuard` is the spec's own arrow function, so it is always truthy, and the guard itself is never called — the one thing the file checks is that the import compiles. It's the "test that always passes" an interviewer asks a candidate to spot, so I'd call it out myself. The wrapper is still the right starting point, because `TestBed.runInInjectionContext` is what lets the guard's `inject(AuthService)` and `inject(Router)` work outside the router. To test `adminGuard` I'd provide `{ provide: AuthService, useValue: { getUserRole: () => 'employee' } }` plus `provideRouter([])`, call `executeGuard({} as ActivatedRouteSnapshot, {} as RouterStateSnapshot)`, and assert that the result is a `UrlTree` which `router.serializeUrl` turns into `/dashboard`; then `'admin'` returns `true`, and `undefined` redirects too, which is what shows the allow-list fails closed.

**[06-hr-portal-141] `leave-request.service.spec.ts` only checks that the service is created. What is the first behavioural test you'd write in it?** ⭐⭐

The state machine, because it's the one workflow rule in the project, and the service is plain logic with no DOM, so it's the cheapest thing to test. I'd call `localStorage.clear()` in `beforeEach` before `TestBed.inject(LeaveRequestService)` — the service reads storage when it's constructed, and `TestBed` resets the injector between tests, not `localStorage` — then add a request, take its id from `leaveRequests()`, and assert that `updateStatus(id, 'approved')` returns `true` while a later `updateStatus(id, 'rejected')` returns `false` and leaves the status `approved`. The second test I'd add is "a new request is always `pending`": pass `addLeaveRequest` a variable typed as a full `LeaveRequest` with `status: 'approved'` and expect `pending`. That test would fail today, because the caller's spread comes after the service's stamps, and catching exactly that kind of bug is the reason to write it.

**[06-hr-portal-142] `DepartmentList` imports `RouterLink` and puts an Edit link on every row, yet its spec provides no router and passes. Why, and is that safe?** ⭐

It passes only because no row is ever drawn: the `departments` input defaults to `[]`, so the `matCellDef` holding `[routerLink]` is never stamped out and `RouterLink`, which injects `ActivatedRoute`, is never constructed — the only row the table renders is the `matNoDataRow`, which has no link. So it isn't safe: the first test that calls `fixture.componentRef.setInput('departments', [department])` fails with a missing-provider error for `ActivatedRoute`, an error about the spec's setup rather than the behaviour it was written to check. When I fixed the nine red specs I left this one alone because it was green, but its green comes from the empty branch, not from the component's real dependencies. Before writing a row test I'd add `provideRouter([])`, click the Edit button, and assert through `vi.spyOn(router, 'navigateByUrl').mockResolvedValue(true)` that the URL tree it receives serializes to `/departments/edit/<id>` — a button with `routerLink` writes no `href` to check.
