# Interview Questions — 05-task-manager

**Last banked:** 2026-09-15

Questions specific to the implementation decisions made in this project.
Use these alongside the topic-based files in `interview-prep/{LEVEL}/en/` and `es/`.

## Architecture & Patterns

**[05-task-manager-001] Task Manager is built around a coordinator pattern. What does `TaskPage` own, what do its children own, and why did you split it that way?** ⭐⭐⭐

I made `TaskPage` the coordinator: it holds the filter signals (`selectedStatus`, `selectedPriority`, `searchTerm`), derives `filteredTasks` and the stat counts with `computed()`, and is the only component that changes the tasks through `TaskService` or opens the add/edit dialog. `TaskFilters` and `TaskTable` only receive values through `input()` and report user actions through `output()` — the filters emit `status`, `priority`, `searchName` and `clearAll`, and the table emits `taskToEdit` and `taskId`. I chose this so every state change happens in one file I can read top to bottom, and so the children know nothing about where the tasks come from.

**[05-task-manager-002] Can you walk me through what happens, from the click to the re-rendered row, when a user edits a task?** ⭐⭐⭐

The Edit button calls `editTask()` in `TaskTable`, which only emits `taskToEdit`; `TaskPage.onEditTask()` opens `TaskDialog` with `data: { task }`, and the dialog's constructor pre-fills the form with `patchValue()`. On submit the dialog builds a new `Task` that keeps the original `id` and `createdAt` and closes with `dialogRef.close(task)`; the page's `afterClosed()` subscriber calls `taskService.editTask()`, which swaps the task in with `tasks.update()` and `map()`, producing a new array. That new reference recomputes `filteredTasks` and the stat signals, the table's `tasks` input changes, its `effect()` assigns `dataSource.data`, and `MatTableDataSource` re-applies the current sort and page before the row renders — while the service's own `effect()` writes the new array to `localStorage`.

**[05-task-manager-003] Why does `TaskDialog` hand the task back through `dialogRef.close()` instead of calling `TaskService` itself?** ⭐⭐⭐

I decided the dialog should only collect and validate input and return a result, and let whoever opened it decide what that result means. `TaskPage` opens the same dialog for add and for edit, and its `afterClosed()` subscribers are where it chooses `addTask()` or `editTask()`, so the dialog never needs to know which operation it is feeding. It also keeps cancelling trivial: a dialog that closes without a value leaves the page nothing to persist. `TaskDialog` does inject `TaskService`, but only to read the `members` list for the assignee select.

**[05-task-manager-004] You use one `TaskDialog` for both adding and editing. How does it know which mode it is in?** ⭐⭐⭐

Only `onEditTask()` passes `data: { task }`, while `openDialog()` passes no data, so I inject `MAT_DIALOG_DATA` and treat its presence as the mode flag. In edit mode the constructor calls `patchValue()` with the task's fields, the template's `@if (data)` switches the title and the submit button to "Edit Task", and `onSubmit()` reuses `data.task.id` and `data.task.createdAt` instead of generating new ones. I chose one component because the form, the validators and the layout are identical in both modes, so two dialogs would duplicate everything except those three branches.

**[05-task-manager-005] `ConfirmDialog` is used for two different things in this project. How did you make it reusable?** ⭐⭐⭐

I gave it no text of its own: it injects a `ConfirmDialogData` object — `title`, `message`, `cancelLabel`, `confirmLabel` and a `danger` flag — and renders those, with `[class.btn-danger]="data.danger"` switching the confirm button to the red style. `TaskTable` opens it to confirm a delete (`danger: true`, "Delete") and `TaskDialog` opens it to confirm discarding unsaved changes (`danger: false`, "Discard Changes"). It knows nothing about tasks or about what confirming triggers — each caller decides that in its own `afterClosed()` subscriber — so a third confirmation anywhere else is one more `open()` call with a different data object.

**[05-task-manager-006] Your table is a presentational component, but it uses `MatTableDataSource` and an `effect()`. Why is the effect there?** ⭐⭐⭐

`MatTableDataSource` knows nothing about signals — it has a plain `data` setter that re-runs its sort and pagination — while the table receives its rows through the signal input `tasks`. So I put an `effect()` in the constructor that assigns `this.dataSource.data = this.tasks()`, and every time the coordinator passes a new filtered array the data source is refreshed. That is what an effect is for: pushing signal state into an imperative API outside the signal graph; a `computed()` could only build a new data source each time, which would lose the sort and paginator I attach once in `ngAfterViewInit`.

**[05-task-manager-007] PLANNING.md says `MatTableDataSource` handles filtering, but you filter in a `computed()` in `TaskPage`. Why?** ⭐⭐⭐

I decided the filter belongs to the coordinator because the filtered result is needed outside the table: the "Showing X of Y" line reads `filteredTasks().length`, and the filter bar and the stat cards all write the same signals. Using `dataSource.filter` would hide that state inside the child and force the page to read `filteredData` back out of it. So `filteredTasks` is one `computed()` combining the status, priority and name matches, the table receives the already-filtered array, and `MatTableDataSource` only does what the page cannot — sort and page the rows it was given.

**[05-task-manager-008] Why does the task list live in `TaskService` while the filter state lives in `TaskPage`?** ⭐⭐

I split state by owner and lifetime: the tasks are domain data that outlive any one component and are persisted to `localStorage`, so they sit in one `signal<Task[]>` in a root service whose `addTask`, `editTask` and `deleteTask` are the intended way to change them. The filters only describe what this page is currently showing, so they are local signals of `TaskPage` and reset when the page is recreated. The page re-exposes the service signal as `tasks = this.taskService.tasks` and builds every derived value from it.

**[05-task-manager-009] `TaskService` exposes `tasks` as a public `WritableSignal`. What stops a component from calling `tasks.set()` directly?** ⭐⭐

Nothing in the type system — today it is only a convention that every change goes through `addTask`, `editTask` or `deleteTask`, and `TaskPage` even re-exposes that same writable signal to its template. The shape I would use now is a private `_tasks = signal<Task[]>(...)` with a public `tasks = this._tasks.asReadonly()`, so components can read and derive but the service stays the only writer. That matters as the app grows, because a stray `set()` from a component would bypass any rule the service later adds.

**[05-task-manager-010] The coordinator pattern says children only display and emit, yet `TaskTable` opens the delete confirmation dialog itself. Isn't that a violation?** ⭐⭐

It is a deliberate bend, and I can defend it while naming its cost. I kept the confirmation in `TaskTable` because it is part of the delete gesture on a row: `openConfirmDialog()` opens `ConfirmDialog` with the task's name as the title and only emits `taskId` once the result is truthy, so the page receives a delete that is already confirmed. The cost is that the table is no longer purely presentational — it injects `MatDialog` and depends on `ConfirmDialog` — and the two flows are inconsistent, since edit opens its dialog from the page and delete from the child; moving `openConfirmDialog()` into `TaskPage` would make them symmetric.

**[05-task-manager-011] `TaskDialog` injects `TaskService`. What does it use it for, and would you keep that dependency?** ⭐⭐

It only reads `members`, the hard-coded list of assignees (`'Ana'`, `'Carlos'`, `'María'`, `'David'`, `'Laura'`) that fills the assignee `mat-select`; every write still goes back through `close()`. I put the list in the service so any screen reads the same source. The trade-off is a dialog that depends on a stateful service just for a constant, so passing `members` through `MAT_DIALOG_DATA` from the page, or moving it to a constants file, would keep the dialog fully driven by its caller and simpler to test.

**[05-task-manager-012] Who creates the `id` and `createdAt` of a new task in your app, and why there?** ⭐⭐

`TaskDialog` does: in add mode `onSubmit()` uses `crypto.randomUUID()` for the id and a private `today()` helper for the date, and in edit mode it copies both from `data.task`. I put it there because the dialog is where the complete `Task` object is first assembled, so `TaskService` receives finished tasks and its methods stay plain array operations. The alternative — the dialog returning only the form values and the service stamping identity and date — puts that logic next to storage, which is where a backend would do it, and is the shape I would move to if the data came from an API.

**[05-task-manager-013] In `TaskDialog`, Cancel asks for confirmation when the form is dirty. How do the two dialogs interact, and can the user close it without that check?** ⭐⭐

`TaskDialog` injects both its own `MatDialogRef` and `MatDialog`; `onCancel()` checks `newTaskForm.dirty` and, if it is dirty, opens `ConfirmDialog` on top, and only when that second dialog returns a truthy result does it call `this.dialogRef.close()` on the task dialog — `MatDialog` stacks them, and each ref closes only its own dialog. The gap is that the check lives only on the Cancel button: I never set `disableClose`, so pressing Escape or clicking the backdrop closes `TaskDialog` directly and discards the edits without asking. Closing it means `disableClose: true` plus routing `backdropClick()` and the Escape key from `keydownEvents()` through `onCancel()`.

**[05-task-manager-014] How are `MatSort` and `MatPaginator` connected to the data source, and why in `ngAfterViewInit`?** ⭐⭐

I query them with `@ViewChild(MatSort)` and `@ViewChild(MatPaginator)` and assign `dataSource.sort` and `dataSource.paginator` in `ngAfterViewInit`, because a view query with the default `static: false` is only resolved once the view exists — in the constructor both are still undefined, which is why the fields carry the `!` definite-assignment operator. From then on the data source listens to sort and page events and re-applies both every time the effect replaces its data. Today I would use the signal query `viewChild.required(MatSort)`, which matches the `input()`/`output()` style the rest of the component already uses.

**[05-task-manager-015] Clicking a stat card filters the table. How does that stay in sync with the Status dropdown?** ⭐⭐

The stat cards are buttons that call `onStatusChange('all' | 'pending' | 'in-progress' | 'done')` on `TaskPage` — the same method the `TaskFilters` `status` output calls — so both controls write the one `selectedStatus` signal. The dropdown's value is bound to that signal through its `selectedStatus` input, and each card reads it for `[class.active]` and `aria-pressed`, so whichever control changes it, the other re-renders to match. I also chose to compute the card counts from `tasks()` rather than `filteredTasks()`, so they describe the whole list and do not drop to zero when a filter is applied.

**[05-task-manager-016] `TaskFilters` holds no state of its own. How does "Clear All" reset its controls?** ⭐⭐

I built it as a controlled component: each `mat-select`'s `[value]` and the search input's `[value]` are bound to inputs (`selectedStatus`, `selectedPriority`, `searchValue`) that the page feeds from its signals, and every change is only emitted upward. `clearFilters()` emits the `void` output `clearAll`, `TaskPage.onClearAll()` sets the three signals back to `'all'`, `'all'` and `''`, and the new input values flow down and reset the controls. Even whether the Clear All button is active comes from the page's `hasActiveFilters` computed, passed in as an input, so the filter bar can never disagree with what the table is actually filtering by.

**[05-task-manager-017] Your table shows two different empty-state messages. How does a component that only receives filtered tasks know which one to show?** ⭐⭐

It cannot tell from its rows alone — an empty `tasks` array means either "no tasks exist" or "none match the filters". So I added a `hasTasks` input that `TaskPage` fills with `totalTasks() > 0`, and the `*matNoDataRow` row uses it to choose between "No tasks yet" and "No tasks match your filters". I chose to pass one boolean rather than the full list, so the table still receives only what it renders plus the single fact it needs.

**[05-task-manager-018] Task Manager has a single page. Why does it have a router at all, and what happens on an unknown URL?** ⭐⭐

I kept the standard shell: `App` renders only `<router-outlet />`, `app.routes.ts` maps the empty path to `TaskPage`, and `app.config.ts` registers `provideRouter(routes)`, so a second page later — a task detail, for example — is a new route rather than a rework of the root component. The cost is that I never added a wildcard route, so a URL like `/tasks` matches nothing, the router logs a navigation error and the user sees an empty shell; a `{ path: '**', redirectTo: '' }` entry would fix it.

**[05-task-manager-019] `TaskPage` opens `TaskDialog`, but `TaskDialog` is not in the page's `imports` array. Why does that still work?** ⭐⭐

A standalone component's `imports` array is for what its template uses — `TaskPage`'s template renders `<app-task-filters>` and `<app-task-table>` and uses `matButton` and `mat-icon`, so those are what I imported. `TaskDialog` never appears in that template; the page creates it at runtime by passing the class to `this.dialog.open(TaskDialog, ...)`, so a TypeScript import is enough and `MatDialog` instantiates it. The same holds for `ConfirmDialog`, which `TaskTable` and `TaskDialog` open programmatically without listing it in their `imports`.

**[05-task-manager-020] Your service and child components live inside `pages/task-page/`, not in a `core/` or `shared/` folder. Why?** ⭐⭐

I organised by feature: everything that exists only for the task page — `task-filters`, `task-table`, `task-dialog`, `confirm-dialog` and `TaskService` — sits under `pages/task-page/`, while the `Task` model sits in `app/models/` because the service and every component import it. With a single feature, a `core/` and `shared/` split would only add folders holding one file each. The tension is `ConfirmDialog`, which is already generic and used by two components, and `TaskService`, which is `providedIn: 'root'`; if a second page needed either, they would be the first to move to `shared/` and `core/`.

**[05-task-manager-021] What would break if you removed `providedIn: 'root'` from `TaskService` and listed it in `TaskPage`'s `providers` instead?** ⭐⭐

`TaskDialog` would fail to open, because it injects `TaskService`, and a component opened through `MatDialog.open()` with no `viewContainerRef` or `injector` in its config gets an injector whose parent is the dialog service's own — the root injector — not `TaskPage`'s element injector; a page-level provider is invisible to it and injection throws `NullInjectorError`. The page would also get a fresh instance every time it is recreated. I chose `providedIn: 'root'` so there is exactly one task store that the page and every dialog resolve the same way.

**[05-task-manager-022] You inject `MAT_DIALOG_DATA` as `inject<{ task: Task } | undefined>(MAT_DIALOG_DATA)`. Why the type argument, and is that type accurate?** ⭐⭐

`MAT_DIALOG_DATA` is declared as an `InjectionToken<any>`, so without the type argument `data` would be `any` and nothing would check `data.task.id`; the generic tells TypeScript what I expect the caller to have passed. It is not a runtime check, and here it is slightly wrong: when `openDialog()` passes no data, `MatDialogConfig`'s default is `null`, not `undefined`. The code still behaves because every use is a truthiness check (`if (this.data)`, `@if (data)`), but the honest type is `{ task: Task } | null`.

**[05-task-manager-023] What type does `afterClosed()` emit in `TaskPage`, and why does `onAddTask(task: Task)` need an `if (task)` check?** ⭐⭐

Neither `this.dialog.open(TaskDialog, ...)` nor `inject(MatDialogRef)` inside the dialog declares a result type, so `afterClosed()` emits `any` and the compiler lets it flow straight into `onAddTask(task: Task)`. At runtime it is `undefined` whenever the user cancels, discards or presses Escape, so the `if (task)` guard — and the same check in `onEditTask`'s subscriber — is what stops that value reaching the service. The typed version is `inject<MatDialogRef<TaskDialog, Task>>(MatDialogRef)` in the dialog and a `Task | undefined` parameter in the page, which makes the guard something the compiler demands rather than something I remembered.

**[05-task-manager-024] You subscribe to `afterClosed()` three times and never unsubscribe. Is that a leak?** ⭐⭐

No: `afterClosed()` emits once, when that dialog closes, and then completes, so each subscription in `TaskPage`, `TaskTable` and `TaskDialog` ends on its own and nothing stays attached to the component. That is why I subscribed directly with a `next` handler instead of adding `takeUntilDestroyed()`. It would be different for a stream that does not complete by itself, such as a form control's `valueChanges` or an `interval`.

**[05-task-manager-025] When you open the edit dialog you pass the task object from the table row. Why doesn't typing in the form change that task before you save?** ⭐⭐

The dialog never binds the form to that object: `patchValue()` copies the task's field values into the `FormGroup`'s own controls, and `onSubmit()` builds a brand-new `Task` from `newTaskForm.value`. Until `close(task)` hands that new object back and `editTask()` swaps it in with `map()`, the original inside the `tasks` signal is untouched, so cancelling has nothing to roll back. I did it on purpose — mutating `data.task` in place would change the task without a new array reference, so neither the `computed()` signals nor the table's effect would notice, and a cancel could not undo it.

**[05-task-manager-026] Only Name, Assignee and Created At are sortable in your table. Why not Status and Priority?** ⭐⭐

I put `mat-sort-header` only on `name`, `assignee` and `createdAt`, because `MatTableDataSource`'s default `sortingDataAccessor` sorts the raw value, and for status and priority that is a string: `'high' < 'low' < 'medium'` alphabetically, which is not an order anyone means. Sorting them properly needs a custom `sortingDataAccessor` that maps each value to a rank (low 0, medium 1, high 2). Since the filters already let the user isolate a status or a priority, I decided that mapping was not worth it yet.

**[05-task-manager-027] `FilterStatus` is defined as `'all' | TaskStatus`. Why a separate type, and where does it stop protecting you?** ⭐⭐

I kept domain and UI apart: a task's status can only be `'pending' | 'in-progress' | 'done'`, but a filter also needs "no filter", so `FilterStatus` and `FilterPriority` extend the domain unions with `'all'` instead of letting `'all'` leak into the `Task` interface. Those types are the contract between `TaskPage`'s signals and `TaskFilters`' inputs and outputs, so a call like `onStatusChange('pendng')` is a type error. The protection stops at the `mat-select`: `(selectionChange)` gives `$event.value` as `any`, so a mistyped `<mat-option value>` would be emitted without the compiler noticing.

**[05-task-manager-028] In `ConfirmDialog` the confirm button calls `confirm()` but the cancel button uses `mat-dialog-close`. What does each one return?** ⭐

`confirm()` calls `dialogRef.close(true)`, so the confirm button is the only path that returns `true`; the cancel button carries a bare `mat-dialog-close` attribute, and because Angular fills a directive input from a static attribute of the same name, `MatDialogClose`'s result becomes `''` — Cancel closes with an empty string, while Escape or a backdrop click close with `undefined`. I decided callers should only test for a truthy result — `if (confirmDelete)` in `TaskTable`, `if (confirmed)` in `TaskDialog` — so both falsy values mean "no", where a check like `result === undefined` would have misread Cancel. `[mat-dialog-close]="true"` on the confirm button would work as well; I kept a method so the confirm path is explicit in the class.

**[05-task-manager-029] What does your `app.config.ts` register, and why is it so short?** ⭐

I register only `provideBrowserGlobalErrorListeners()`, which forwards uncaught window errors and unhandled promise rejections to Angular's `ErrorHandler`, and `provideRouter(routes)`. I bootstrapped the app standalone with `bootstrapApplication(App, appConfig)`, and I added no `provideHttpClient()` because the project has no API — the tasks live in a service signal persisted to `localStorage`. `MatDialog` and `LiveAnnouncer` are `providedIn: 'root'` services, so they need no entry here.

**[05-task-manager-030] Why does `TaskTable` inject `LiveAnnouncer`?** ⭐

Sorting reorders the rows silently, which a screen-reader user cannot see, so I bound `(matSortChange)` to `announceSortChange()` and use the CDK's `LiveAnnouncer` to read out "Sorted ascending", "Sorted descending" or "Sorting cleared". Each `mat-sort-header` also carries a `sortActionDescription` ("Sort by name", "Sort by assignee", "Sort by date") so the header buttons are labelled. I took the pattern from the Material sort documentation, and one line of the docs example came along too literally: `mat-paginator` still carries `aria-label="Select page of periodic elements"`, so a screen reader announces the wrong data set on the very control I was making accessible — it should read "Select page of tasks".

**[05-task-manager-031] Your confirmation dialogs are opened with `autoFocus: false`. What does that change?** ⭐

By default `MatDialog` moves focus to the first tabbable element, which draws a focus ring on a button the moment the dialog opens; with `autoFocus: false` focus goes to the dialog container instead, still trapped inside the dialog and restored to the trigger on close. I set it on both `ConfirmDialog` calls — delete in `TaskTable` and discard in `TaskDialog` — but not when opening `TaskDialog`, where landing on the first field is what the user wants. What I did not factor out is the rest of the config: all four `open()` calls in the app — the two in `TaskPage` and the two confirmations — repeat `width: '500px'`, which a shared config constant would remove.

**[05-task-manager-032] How do your status and priority badges get their colours?** ⭐

Each cell renders `<span class="badge" [ngClass]="task.status">` (and `task.priority`), so the CSS class is literally the union value — `pending`, `in-progress`, `done`, `low`, `medium`, `high` — and the component stylesheet can style each value by name. I chose it because the model's string unions are already valid class names, so no mapping object is needed. The coupling is that renaming a status value silently loses its colour, and since it binds one string, a plain `[class]="task.status"` binding would do the same job without `NgClass`.

**[05-task-manager-033] `TaskTable`'s delete output is called `taskId`. Why that name?** ⭐

I named it after its payload — it emits the id of the confirmed task and the page binds it as `(taskId)="onDeleteTask($event)"` — next to `taskToEdit`, which emits the whole `Task`. Read from the parent's template, though, `(taskId)` does not say what happened, where `(taskDeleted)` would; the same gap shows in `TaskFilters`' `status` and `priority` outputs. It is a naming choice I would change before the component was reused anywhere else.

**[05-task-manager-034] `ConfirmDialogData` lives in `task.model.ts`. Is that the right place?** ⭐

I put it there because `models/task.model.ts` was the project's only types file, and both `TaskTable` and `TaskDialog` build that object. But `ConfirmDialog` has nothing to do with tasks — it is the one component designed to be reused — so its contract belongs next to it, in `confirm-dialog.ts` or its own model file, so the dialog can move to a `shared/` folder without dragging the task model along.

**[05-task-manager-035] A user is on page 3 of the table and applies a filter that leaves four tasks. What does the paginator do?** ⭐

I rely on `MatTableDataSource` for it: when the effect assigns the filtered array, the data source updates the paginator's `length` and, if the current `pageIndex` is now past the last page, moves it back to the last valid one, so the user sees the four tasks instead of an empty page. I wrote no reset of my own. The trade-off is that the user lands on the last page rather than the first, which for a result that fits on one page is the same thing.

**[05-task-manager-036] `createdAt` is stored as a `'YYYY-MM-DD'` string. Why does sorting that column work, and why did you write `today()` instead of using `toISOString()`?** ⭐

A zero-padded year-month-day string orders alphabetically exactly as it orders chronologically, so `MatTableDataSource`'s default comparison sorts Created At correctly with no custom accessor, and `DatePipe` formats it for display. I built `today()` from `getFullYear()`, `getMonth()` and `getDate()` because `new Date().toISOString()` is in UTC: in Spain, a task created shortly after midnight would be stamped with the previous day's date.

**[05-task-manager-037] Your Name column is sortable. Would a task called "ana" sort next to one called "Ana"?** ⭐

No: `MatTableDataSource`'s default `sortData` compares the raw strings with `<` and `>`, which is code-point order, so every capitalised name sorts before any lowercase one and an accented initial like "Álvaro" lands after "Zoe". Assignees come from a fixed capitalised list, so that column is safe, but task names are free text. I would fix it by overriding `sortData` (or the `sortingDataAccessor`) to compare names with `localeCompare`, which handles both case and accents.

**[05-task-manager-038] Your templates use `@if` and `@for`, but the table uses `*matCellDef` and `*matRowDef`. Why the mix?** ⭐

I use the built-in control flow wherever I decide the structure — `@if (data)` for the dialog's add/edit text, `@for (member of members; track member)` for the assignee options. MatTable's `*matHeaderCellDef`, `*matCellDef`, `*matRowDef` and `*matNoDataRow` are not control flow: they are directives that hand the table an `<ng-template>` to stamp per row, with `let task` exposing that row's data, so they keep the structural-directive syntax. Building rows myself with `@for` would bypass MatTable's own rendering, and with it the sorting and paging of the data source.

**[05-task-manager-039] The search box in `TaskFilters` uses neither a `FormControl` nor `ngModel`. How does the text reach the filter?** ⭐

I bound the native `(input)` event to `searchChange($event)`, which reads `(input.target as HTMLInputElement).value` and emits it through the `searchName` output; the page stores it in `searchTerm`, and `filteredTasks` recomputes on every keystroke. I chose not to import a forms module for one field that has no validation. Filtering is an in-memory array filter, so there was no need to debounce; against an API I would switch to a `FormControl` with `debounceTime`.

**[05-task-manager-040] Your Delete buttons are red, but you never override Material's CSS. How did you theme them, and why does the confirm dialog's button pick up the same red?** ⭐⭐⭐

I set the theme once in `material-theme.scss`: `mat.theme()` on `html` with `mat.$blue-palette`, Roboto and density 0 emits the `--mat-sys-*` tokens that every Material component reads, and my own component CSS reads the same roles — the active stat card is `var(--mat-sys-primary-container)` — instead of hard-coded colours. For delete I included `mat.theme((color: mat.$red-palette))` a second time inside a `.btn-danger` rule, which redefines those tokens for that element only, so a `matButton` carrying the class takes its primary colour from red without me targeting internal selectors that change between Material versions. I kept that rule in the global stylesheet listed in `angular.json`, not in `task-table.css`, because emulated encapsulation would scope it to `TaskTable`'s own elements, and `ConfirmDialog` is rendered in the overlay container — global, the one class serves both the table's Delete button and the dialog's confirm button that `[class.btn-danger]="data.danger"` toggles.

**[05-task-manager-041] Nothing in `TaskPage` or the dialogs calls a save method. How do the tasks reach `localStorage`, and what does the first run of that mechanism do?** ⭐⭐

I made persistence follow the state instead of being a step each caller has to remember: `TaskService`'s constructor registers an `effect()` that reads `this.tasks()` and writes its JSON to `localStorage`, so `addTask`, `editTask` and `deleteTask` only update the signal, and any write path added later is persisted without touching the effect. The signal starts from `loadTasks()`, so storage is read once when the root service is created and written every time `update()` produces a new array. An effect always runs once on creation, so its first act is writing the loaded list straight back — harmless for valid data, but when `loadTasks()` falls back to `[]` because the stored text did not parse or was not an array, that first run replaces the corrupted value with `[]` before anyone could inspect it.

**[05-task-manager-106] If the tasks had to come from a REST API tomorrow, which files of Task Manager would change and which would stay as they are?** ⭐⭐⭐

The change concentrates in `TaskService`, because I made it the only place that knows where the tasks come from: `loadTasks()` and the `localStorage` effect would give way to `HttpClient` calls, `addTask`, `editTask` and `deleteTask` would update the signal once the server answers, and `app.config.ts` would gain `provideHttpClient()`. `TaskFilters`, `TaskTable` and `ConfirmDialog` would not change at all — they receive inputs, emit outputs and never touch the store — and `TaskPage` would keep its `computed()` filters over `tasks()` and its `afterClosed()` handlers. What the page would gain is what a synchronous `getItem()` never needed: a loading state while the list arrives and an error state when a save fails. That boundary is the payoff of the coordinator pattern — the data source changes in one service, not in five components.

**[05-task-manager-107] Adding and editing a task happen in a `MatDialog`, not on routed pages like `/tasks/new` and `/tasks/:id/edit`. Why, and what does that cost?** ⭐⭐

I chose a dialog because the form is short and belongs to the list the user is looking at: `TaskPage` stays alive underneath, so the filters, the sort and the current page are exactly as they were when the dialog closes, and the task is handed over as an object instead of being looked up again from an id in the URL. A routed form would destroy `TaskPage` on navigation, and since my filter state is that page's local signals — and sort and page live in its `TaskTable` child — the user would come back to an unfiltered, unsorted first page. The cost is everything a URL gives: an edit cannot be linked or bookmarked, and the browser's Back button does not step back from the form to the list — with no in-app history entry to return to, it leaves the app, unsaved edits included, where a routed form could have protected them with a `CanDeactivate` guard.

**[05-task-manager-108] The four stat cards are written out as four near-identical `<button>` blocks in `task-page.html`. Why not a `StatCard` component or an `@for`?** ⭐⭐

I built them inline in the step that added the `computed()` counts, when the four cards differed only in the status they set, their icon, their label and the count they read, and four copies were easier to see than an abstraction. The cost appears as soon as something changes: a new attribute or style has to be edited four times, and a new status means touching the card markup as well as the model and both selects. The two better shapes are a `computed()` array of `{ status, label, icon, count }` rendered with `@for (card of statCards(); track card.status)`, or a presentational `StatCard` with `label`, `icon`, `count` and `active` inputs and a `select` output — which fits the coordinator pattern, since `TaskPage` keeps the state and the card only displays and emits. With four fixed cards on one page I would start with the `@for`, and extract the component only once another page needed it.

**[05-task-manager-109] Why is `Task` a TypeScript interface and not a class?** ⭐⭐

Every task in the app is a plain object: `onSubmit()` builds it as an object literal, `editTask()` swaps objects in with `map()`, and `loadTasks()` gets them back from `JSON.parse()`, which never calls a constructor. An interface describes that shape at compile time and disappears from the bundle, whereas a `Task` class with methods would be a lie after every reload — the parsed objects would have none of its methods and `instanceof Task` would be false. The cost is that an interface checks nothing at runtime, so whatever `JSON.parse()` returns is trusted to have that shape; a class would not have fixed that either, because validating stored data takes an explicit check on the parsed value, not a type declaration.

**[05-task-manager-110] Status and priority are string-literal unions like `'pending' | 'in-progress' | 'done'`, not `enum`s. Why, and what did that leave you without?** ⭐⭐

I chose unions because the values are used as plain strings everywhere: they are stored in `localStorage` as they are, written as literal `value="pending"` in the templates, compared as `task.status === 'done'` in the stat computeds, and even reused as CSS class names by the badges. A union type-checks all of that and emits no JavaScript, while a string `enum` compiles to a runtime object that a component would have to expose as a field before its template could compare against `TaskStatus.Done`. What a union does not give me is a list of its values, so the statuses are typed out again in the status filter, in the dialog's select and in the stat cards — and the copies have already drifted: "In Progress" in the filter, "In progress" in the dialog. `const TASK_STATUSES = ['pending', 'in-progress', 'done'] as const` with `type TaskStatus = (typeof TASK_STATUSES)[number]` keeps the union and adds one array, plus a label map, for every select and card to loop over.

**[05-task-manager-111] Each filter in `TaskFilters` is an `input()` paired with an `output()` — `selectedStatus` with `status`, for example. Why not `model()`?** ⭐⭐

I wrote the pair by hand: the page passes `[selectedStatus]="selectedStatus()"` down and listens to `(status)="onStatusChange($event)"`, which sets that same signal. That round trip is exactly what `model()` packages — `selectedStatus = model<FilterStatus>('all')` in the child, `this.selectedStatus.set(value)` on `selectionChange`, and `[(selectedStatus)]="selectedStatus"` in the page binding its writable signal directly — which would remove `onPriorityChange()` and `onSearchName()` from `TaskPage`, while `onStatusChange()` stays because the stat cards call it. I kept the explicit version because every write to filter state then passes through a named method on the coordinator, which is easy to trace and is where a side effect such as resetting the paginator would go. My naming is the part that does not survive: banana-box syntax needs the output of `selectedStatus` to be called `selectedStatusChange`, so a `status` output could never be bound two-way, and `model()` enforces that pairing for me.

**[05-task-manager-112] `TaskTable` and `TaskDialog` each pass `ConfirmDialog` a data object. What checks that object against `ConfirmDialogData`?** ⭐⭐

Nothing at compile time. `MatDialog.open()` is declared `open<T, D = any, R = any>`, and because I call it without type arguments, `D` is taken from whatever object I wrote rather than checked against a type, so a caller that misspelled `confirmLabel` or forgot `danger` would compile; `ConfirmDialog`'s `inject<ConfirmDialogData>(MAT_DIALOG_DATA)` only asserts the type on the receiving side. At runtime the misspelled label would interpolate as an empty button, and a delete confirmation without `danger` would lose its red style. Writing `this.dialog.open<ConfirmDialog, ConfirmDialogData, boolean>(ConfirmDialog, { ... })` turns both mistakes into compile errors, and since both callers already repeat the same `open()`, `autoFocus: false` and `afterClosed()` subscription, I would move that into one typed `confirm(data: ConfirmDialogData): Observable<boolean>` helper so the check is written once.

**[05-task-manager-113] There are two `effect()`s in the app, one in `TaskService` and one in `TaskTable`. When does each one run, and when is each one destroyed?** ⭐

The service's effect is a root effect, because it is created in a `providedIn: 'root'` service: it runs before the component tree is checked and lives as long as the application, so it never needs cleanup. The table's effect is a component effect: it runs when change detection reaches `TaskTable`, before that component's template is refreshed, and it is destroyed with the component, so a table removed from the screen stops writing to its data source on its own. In one edit that order is what I rely on: the root effect saves the new list, `TaskPage`'s template hands `TaskTable` the new filtered array, and the table's effect assigns `dataSource.data` before the table's view is checked. Had I registered the storage effect in `TaskPage` instead, persistence would depend on that page being alive, which is the wrong lifetime for saving shared data.

**[05-task-manager-114] In `TaskPage`, adding uses `openDialog()` plus `onAddTask()`, while editing is the single method `onEditTask()`. Why the different shape?** ⭐

It grew that way rather than being designed: the header button binds `(click)="openDialog()"`, whose subscriber delegates to `onAddTask()`, while the table's `(taskToEdit)` event goes straight to `onEditTask()`, which opens the dialog and saves inline. So the `on` prefix means two different things in one class — `onEditTask` handles the user's request to edit, `onAddTask` handles a result the dialog has already returned — and `openDialog` does not say which dialog it opens, although the same class opens `TaskDialog` for editing too. I would make the two flows mirror each other as `openAddDialog()` and `openEditDialog(task)`, each calling the service from its own `afterClosed()` subscriber, and drop the public `onAddTask()`, which nothing but that subscriber calls.

**[05-task-manager-115] `TaskTable` declares its columns as `matColumnDef` blocks and again in `displayedColumns`. Why both, and why does the empty row bind `[attr.colspan]="displayedColumns.length"`?** ⭐

They do different jobs: each `matColumnDef` defines how one column renders its header and cells, and the `displayedColumns` array given to `*matHeaderRowDef` and `*matRowDef` decides which of those definitions appear and in what order. That split lets a column be hidden or reordered by changing the array alone, without touching the template. The `*matNoDataRow` row is a single cell outside those definitions, so I bound its `colspan` to the array's length instead of writing `6`, and it keeps spanning the whole table whatever the array holds. The gotcha runs the other way: a name in `displayedColumns` with no matching `matColumnDef` compiles and then throws `Could not find column with id` at runtime.

**[05-task-manager-116] Your page component is `TaskPage` in `task-page.ts`, with no `Component` suffix and no `standalone: true`. Isn't something missing?** ⭐

No — it is what this Angular version's CLI generates. Components have been standalone by default since v19, so `standalone: true` would be redundant, and the v20 style guide dropped the `Component` suffix from class and file names, which is why `ng generate component` produced `task-page.ts` with a class called `TaskPage`. The service keeps its suffix only because I wrote it into the command path (`task.service`); without it the generated class would be called `Task` and collide with the `Task` interface in `models/task.model.ts`. A reviewer used to older codebases expects `TaskPageComponent`, so I name the style guide rather than let the naming look like an oversight.

**[05-task-manager-117] `TaskDialog` binds `[errorStateMatcher]="errorMatcher"` on each of its four required fields. Why not provide the matcher once through the component's `providers`?** ⭐

Material's inputs and selects fall back to the `ErrorStateMatcher` their injector provides, so `providers: [{ provide: ErrorStateMatcher, useClass: SubmitOnlyErrorStateMatcher }]` on `TaskDialog` would give each dialog instance one matcher that every field in its template picks up, and the dialog could `inject(ErrorStateMatcher)` to flip `submitted`. I chose the explicit binding because the matcher is per-dialog state that `onSubmit()` mutates, and seeing it on each field tells a reader which controls follow that rule. The cost is repetition: a fifth required field that forgot the binding would show its error on Material's default touched-or-submitted rule instead, which the provider version rules out. The provider version pays the opposite price — the rule is invisible in the template, and `inject()` returns the base `ErrorStateMatcher` type, so reaching `submitted` needs a cast.

**[05-task-manager-118] Your stat cards are `<button type="button">` elements with `[attr.aria-pressed]`, not clickable `<div>` cards. Why?** ⭐

Clicking a card changes the status filter, so I treated it as a control: a native `<button>` is reachable with Tab, activates with Enter or Space and is announced as a button, all of which a `<div (click)>` would need a `tabindex`, a `role` and its own key handlers to imitate. `[attr.aria-pressed]` then makes each card a toggle — Angular writes `"true"` or `"false"` rather than removing the attribute — so a screen reader hears which card is active, the state the `.active` class only shows visually, and `type="button"` keeps a card from submitting a form if the row ever moves inside one. The price of a native button is undoing its browser styles, which is why `.stat-card` in `task-page.css` resets `border`, `font`, `color` and `text-align`. Strictly, exactly one card is pressed at a time, so the most accurate semantics would be a radio group — `role="radiogroup"` around `role="radio"` cards with `aria-checked` — but that pattern also expects arrow-key navigation, and four toggle buttons are still announced correctly without it.

**[05-task-manager-119] Your `mat-paginator` sets `[pageSizeOptions]="[5, 10, 20]"` but no `pageSize`. How many rows does the first page show, and is that choice remembered?** ⭐

Five: when `pageSize` is not set, `MatPaginator` takes the first entry of `pageSizeOptions` as its page size, so the order of that array is itself a setting, and I added `showFirstLastButtons` so a longer list can jump straight to its first or last page. I chose small sizes because the table sits below the header, the stat cards and the filter bar, so five rows keep the paginator close to the rows it controls. The choice is not remembered: page size and page index live in the paginator instance, so a reload brings back 5 rows and page 1 even though the tasks themselves survive in `localStorage`. Binding `[pageSize]="5"` would state the default instead of leaving it to the array order, and if a second table appeared, `MAT_PAGINATOR_DEFAULT_OPTIONS` would set the page size, options and first/last buttons once for every paginator in the app.

## Business Rules

**[05-task-manager-042] Which fields does your task form require, and why is Description the only optional one?** ⭐⭐⭐

I decided a task is not meaningful without a name, an owner, a status and a priority, so `name`, `assignee`, `status` and `priority` each carry `Validators.required`, while `description` is a plain `FormControl<string>('')` — the same split the `Task` interface makes with `description?`. Because `required` is the only rule on each field, each `mat-form-field` holds a single `<mat-error>` ("Name is required", "Assignee is required", …), and the three selects need nothing more because their options are a closed list. `onSubmit()` only builds and closes with a `Task` inside `if (this.newTaskForm.valid)`, so an incomplete task never reaches `dialogRef.close()`.

**[05-task-manager-043] Why did you write a `SubmitOnlyErrorStateMatcher` instead of using Material's default error behaviour?** ⭐⭐⭐

Material's default matcher shows an error when a control is invalid and either touched or its form submitted, so simply tabbing through an empty dialog would paint every field red before the user had tried to save. I wanted errors only after a save attempt, and the form's own `submitted` flag could not tell me that: the buttons sit in `<mat-dialog-actions>`, outside the `<form>`, and Add Task calls `onSubmit()` directly, so that click never sends the `FormGroupDirective` a submit event. So the matcher keeps its own `submitted` field, `onSubmit()` sets it to `true` before checking validity, and each field receives it through `[errorStateMatcher]`. Nothing resets it, so after one failed attempt the errors follow the fields live — clearing the name again shows its error at once, which is what I want once the user has been told what is missing.

**[05-task-manager-044] The Add Task button stays enabled while the form is invalid. Why not `[disabled]="newTaskForm.invalid"`?** ⭐⭐

A disabled button tells the user nothing: it cannot be clicked or focused, and it gives no hint which of the four required fields is still empty. I kept it enabled so the click itself is the feedback — `onSubmit()` flips the matcher's `submitted` flag and every missing field shows its `mat-error`, while the `valid` check still keeps the dialog open. The two choices depend on each other: with a disabled button `onSubmit()` would never run on an invalid form, so the submit-only matcher could never show an error at all.

**[05-task-manager-045] A user types a name in the dialog and presses Enter. Does the task get added?** ⭐

No, and nothing visible happens. The `<form>` has no submit button inside it and the name input is its only single-line text field, so the browser's implicit submission fires a `submit` event on the form; `FormGroupDirective` handles it, marks itself submitted, emits `ngSubmit` — which I never bound — and prevents the page reload. `onSubmit()` never runs, and because my matcher ignores the form's `submitted` flag, not even the errors appear. Binding `(ngSubmit)="onSubmit()"` on the form and linking the Add Task button to it with `type="submit"` and the `form` attribute would make Enter and the click one path.

**[05-task-manager-046] Can a user save a task whose name is only spaces?** ⭐⭐

Yes. `Validators.required` only rejects `null`, `undefined` and a zero-length string, so `'   '` passes, and `onSubmit()` copies `formValue.name` into the task without trimming it — the table then shows a row with a blank Name cell. Nothing limits the length either, since `required` is the only validator on the field. I would add a validator that fails when `(control.value ?? '').trim()` is empty, or `Validators.pattern(/\S/)`, plus `Validators.maxLength`, and trim the name when building the `Task`, so the rule lives in the form rather than in every place that later displays the name.

**[05-task-manager-047] `onSubmit()` builds the task with casts like `formValue.status as TaskStatus`. What makes those casts safe?** ⭐⭐

Only the `if (this.newTaskForm.valid)` around them, which the compiler cannot see. My controls are created without `nonNullable`, so `newTaskForm.value` is a partial object whose fields can be `null` or `undefined`, and `status` and `priority` can also hold the `''` they start with; each cast tells TypeScript to trust that `required` has already ruled those out, which is true at runtime only because the task is built inside the valid branch — move it outside and an empty status would be saved with no compile error. The casts also hide that an untouched Description is stored as `''` rather than left out, as `description?` suggests. `nonNullable: true` controls read with `getRawValue()` would remove `null` from the types, although the `''` placeholder of the selects would still need narrowing.

**[05-task-manager-048] Assignee is a `mat-select` over a fixed list. What does that forbid, and what happens when you edit a task whose assignee is not in the list?** ⭐⭐

I chose a select so a task can only belong to someone on the team: the options come from `TaskService.members`, there is no free text to misspell and no "Unassigned" option, so `required` plus the closed list is the whole rule. The edge case is edit mode: if I removed a name from `members`, `patchValue()` would still write the old assignee into the control, and `mat-select` would find no matching option and show an empty field — yet the control holds a non-empty string, so it is valid and no error appears. Saving without touching the field then silently keeps an assignee the form can no longer offer; a validator checking that the value is in `members` would surface it.

**[05-task-manager-049] Can a new task be created already Done, and can a Done task go back to Pending?** ⭐⭐

Yes to both — I deliberately gave status no lifecycle. The `status` control, like `priority`, starts as `''` with `Validators.required`, so the user must choose instead of getting a default `'pending'`, and the same three options are offered whatever status an edited task already has; `TaskService.editTask()` swaps the task in without comparing old and new status. For a small team board that is what I wanted, because reopening a finished task is a normal action. If the business needed a workflow — done only from in-progress, for example — I would put that rule in one function `editTask()` calls before accepting the change, not in which options the select happens to show.

**[05-task-manager-050] Your dialog treats a dirty form as unsaved changes. What does it actually count as a change?** ⭐

Only interaction through the view: `dirty` flips when the user types or picks an option, and the `patchValue()` that pre-fills edit mode does not mark the form dirty, so opening a task and pressing Cancel closes without asking — but the flag never resets on its own, so changing the priority and changing it back still triggers "Discard changes". Submit has the mirror gap: pressing Edit Task with nothing changed still builds a new `Task`, and `editTask()` replaces the old one with a new array, which re-renders the table and rewrites `localStorage`. Comparing `getRawValue()` with `data.task` would detect a real change in both places; I kept `dirty` because it is the built-in signal and its false positive costs one extra click.

**[05-task-manager-051] Can two tasks have the same name, and does that cause problems anywhere?** ⭐

Yes — neither `TaskDialog` nor `TaskService` checks uniqueness, because I identify tasks by their `crypto.randomUUID()` id, not by name. Edit and delete both travel by that id (`editTask()` matches on `task.id`, the table emits `taskId`), so the right task is always the one changed or removed. The weak spot is the delete confirmation: its title is `task.name`, so two tasks called "Deploy" produce identical dialogs and the user can only rely on which row they clicked.

**[05-task-manager-052] Once a user confirms a delete, can they undo it?** ⭐⭐

No. When `ConfirmDialog` returns `true`, `TaskTable` emits the id, `TaskPage.onDeleteTask()` calls `deleteTask()`, and its `filter()` removes the task from the signal; the service's effect then writes that list to `localStorage`, so there is no soft delete and nothing left to restore. I decided a confirmation step — the task's name as the title and the red `btn-danger` confirm button — was a proportionate guard for a local task list. The more forgiving Material pattern is to delete at once and show a `MatSnackBar` with an Undo action that re-adds the removed task, trading the modal interruption for a few seconds of reversibility.

**[05-task-manager-053] How does your name search decide whether a task matches?** ⭐⭐

In `filteredTasks` I lower-case both the name and the term with `toLocaleLowerCase()`, trim them, and test `includes()`, so the search is a case-insensitive substring match: "rep" finds "Weekly Report". It looks at the name only — never the description or the assignee — and it is combined with AND with the status and priority matches, so a task must pass all three to appear. It is not accent-insensitive: "reunion" does not find "Reunión", because `includes()` compares characters exactly after lower-casing; normalising both sides with `normalize('NFD')` and removing the combining marks would fix that.

**[05-task-manager-054] What happens if the user types only spaces into the search box?** ⭐

The filter and the "is anything filtering?" check disagree. `filteredTasks` trims the term to `''`, and every name includes the empty string, so every task matches; but `hasActiveFilters` compares the untrimmed `searchTerm()` with `''`, sees `'   '`, and returns `true`. The screen therefore shows the Clear All button and "Showing N of N" as if a filter were applied while nothing is filtered. I would derive one normalised term — `computed(() => this.searchTerm().trim().toLocaleLowerCase())` — and have both `filteredTasks` and `hasActiveFilters` read it, so they cannot disagree.

**[05-task-manager-055] A user has a High priority filter on and clicks the Total stat card. What happens to the table?** ⭐

Only the status filter changes: every card calls `onStatusChange()`, and Total passes `'all'`, so it clears the status and leaves `selectedPriority` and `searchTerm` as they were. The Total card highlights with the full count while the table still shows only the high-priority tasks. I scoped the cards to status because each one represents a status count; resetting everything is Clear All's job, and that button stays visible in this state because `hasActiveFilters` is still true.

**[05-task-manager-056] The Clear All button and the "Showing X of Y" line only appear while a filter is active. How do you hide them, and why not with `@if`?** ⭐

Both are always rendered: the template toggles a class from `hasActiveFilters()` — `[class.active]` on the Clear All wrapper, `[class.filter-text-active]` on the paragraph — and the CSS switches `visibility` between `hidden` and `visible`. I chose visibility over `@if` so the elements keep their space; with `@if`, picking the first filter would insert a line and push the filter bar and the table down under the user's cursor. An element with `visibility: hidden` cannot be clicked, reached with Tab or read by a screen reader, so the hidden Clear All button is genuinely unavailable, not just invisible.

**[05-task-manager-057] A user filters by Done and then adds a new Pending task. Where does it appear?** ⭐⭐

Nowhere on screen, because I decided filters survive adds and edits. `addTask()` appends to the signal, `filteredTasks` recomputes against the unchanged `selectedStatus`, and the new task fails the Done match, so the only visible traces are counts going up — the Total and Pending stat cards and the Y in "Showing X of Y"; by the same rule, a row vanishes when an edit moves its task out of the active filter. Even with no filter, the task is appended to the end of the array, so unless a sort brings it forward it can land on a later page of the paginator. I kept filters stable so saving never throws away the view the user built, but the missing piece is feedback — a `MatSnackBar` confirming "Task added" would stop the user thinking the save failed.

**[05-task-manager-058] `loadTasks()` checks that the stored value is an array. What does it not check, and what does that let through?** ⭐⭐

It checks the container, not the contents: `Array.isArray()` narrows the parsed `unknown` to `any[]`, which TypeScript lets me return as `Task[]` without looking at a single element. So a stored `[{"foo": 1}]` reaches the signal: the row renders with blank cells, and the first keystroke in the search box makes `filteredTasks` call `toLocaleLowerCase()` on an undefined `name` and throw a `TypeError`. Since the service's effect writes the list straight back, a reload does not repair it. The complete guard is a type predicate — `isTask(value): value is Task`, checking each field's type and that `status` and `priority` hold one of their union values — applied to every element before the array becomes state.

**[05-task-manager-059] With a filter on, your page says "Showing 12 of 20" while the paginator says "1 – 5 of 12". What does each number count?** ⭐

I made the line describe the filter, not the page: X is `filteredTasks().length` and Y is `totalTasks()`, the length of the whole `tasks` signal, so neither changes when the user moves between pages. The paginator's label comes from `MatTableDataSource`, which counts the rows the effect handed it — that same filtered array — and slices them into pages of 5, so its "of 12" always equals my X. The two therefore never contradict each other: the line answers how much the filter hid, the paginator where the user is inside what is left.

**[05-task-manager-060] Both confirmations throw something away, yet Delete's confirm button is red and Discard Changes' is not. Why?** ⭐

I reserved the danger style for losing saved data: confirming a delete removes the task from the signal and, through the service's effect, from `localStorage`, with no way back, so `TaskTable` opens `ConfirmDialog` with `danger: true`. Discarding only throws away what was typed into the open `TaskDialog` — the stored task, or for a new task nothing at all, stays exactly as it was — so `onCancel()` passes `danger: false` and the confirm button stays a plain outlined one. I kept red for the one irreversible action so it keeps meaning something; if every confirmation were red, the delete dialog would stop standing out.

**[05-task-manager-120] Every rule on a task is enforced by `TaskDialog`'s form. What does `TaskService` itself guarantee about the tasks it stores?** ⭐⭐

Nothing: I made the service a plain store that trusts its caller. `addTask()` appends whatever it receives without checking that the name is filled or that the id is not already in the list, and `editTask()` and `deleteTask()` given an id that matches no task change no task and report nothing — yet `map()` and `filter()` still return a new array, so the computeds recompute and the effect rewrites `localStorage` as if something had happened. The rules hold today only because `TaskDialog` is the one caller and it closes with a task only inside `if (this.newTaskForm.valid)`, over selects that offer closed lists. The shape I would move to is the one a backend forces: the service owns the invariants — rejecting a blank name or a duplicate id, and returning whether an edit or delete found its task — so a second caller, such as a quick status action in the table, cannot bypass rules that live only in one form.

**[05-task-manager-121] A user wants to see every task that is not Done yet, or only Laura's tasks. Can your filters do that, and what would adding it take?** ⭐

Neither: each filter `mat-select` has no `multiple`, so `FilterStatus` holds `'all'` or exactly one status, and although the table has an Assignee column and `TaskService` a fixed `members` list, there is no assignee filter — the filter model is one status, one priority and a name substring, which is what PLANNING.md's "Filter tasks by status and priority" asked for and what keeps each match a single equality check that the stat cards map onto one-to-one. A multi-status filter would make `selectedStatus` a `TaskStatus[]`, where an empty array means no filter and the match becomes `selected.length === 0 || selected.includes(task.status)`, removing the `'all'` sentinel — though the stat cards would then need a toggle rule rather than a plain `set()`. The gotcha is that a new filter is registered in three places in `TaskPage`: a clause in `filteredTasks`, a term in `hasActiveFilters` and a reset in `onClearAll()`, and each one forgotten fails differently — without the `hasActiveFilters` term, Clear All and the "Showing" line stay hidden while the table is filtered, and without the reset, clicking Clear All leaves that filter applied.

**[05-task-manager-122] How does a user mark a task as Done, and why is there no quick action for it in the row?** ⭐⭐

Only through the full form: the Actions column holds just Delete and Edit and the status badge is plain text, so the user opens Edit, changes the Status select and presses Edit Task. I kept a single write path so every change goes through the same validated form, the same `close(task)` and the same `editTask()` call. The cost is three interactions for the change a task board makes most often, a dialog that re-checks fields the user never touched, and — with a status filter active — a row that vanishes the moment the dialog closes. A quick action would put a `mat-select` or `mat-menu` in the status cell, have `TaskTable` emit a `statusChange` output carrying `{ id, status }`, and let `TaskPage` call `editTask({ ...task, status })`, so the table still only displays and emits and no form is needed, because the value comes from a closed list.

**[05-task-manager-123] The task form has a Description field, but the table has no Description column. Where can a user actually read a task's description?** ⭐

Only inside the edit dialog: `displayedColumns` lists name, status, priority, assignee, createdAt and actions, and the name search in `filteredTasks` never looks at `description`, so once a task is saved the text the user typed is invisible until they press Edit and find it pre-filled in the textarea by `patchValue()`. I kept the table to six scannable columns, because under `table-layout: fixed` a free-text column would get a sixth of the width to wrap whole paragraphs in. The cost is that reading means opening a form built for changing the task — closing it is harmless, since `patchValue()` leaves the form pristine and Cancel asks nothing, but one stray keystroke turns a read into a "Discard changes" prompt. A read-only view fits the rule better: an expandable detail row, which MatTable supports with `multiTemplateDataRows` and a second `matRowDef`, or one truncated line of description under the name in the Name cell.

**[05-task-manager-124] A user clicks the Pending stat card, then clicks it again. Does the second click turn the filter off?** ⭐

No. Every card calls `onStatusChange()` with its own status, so the second click sets `selectedStatus` to `'pending'` again, and a signal `set()` with an equal value notifies nothing — the table stays filtered. I made the cards select rather than toggle, so a card always means "show this status", and the way back to every task is the Total card, the Status dropdown's All option or Clear All. The gotcha is that the markup promises the opposite: `[attr.aria-pressed]` announces each card as a toggle button, and a screen-reader user who presses a pressed toggle expects it to release; a `toggleStatus(status)` method that sets `'all'` when `selectedStatus()` already equals `status` would make the behaviour match what is announced.

## Technical Decisions

**[05-task-manager-061] Your `package.json` has no `zone.js`. How does the table re-render when `TaskDialog` closes and `afterClosed()` calls the service?** ⭐⭐

Angular 21's `bootstrapApplication` is zoneless by default, so I load no `zone.js`, list no polyfill in `angular.json` and need no `provideZonelessChangeDetection()` in `app.config.ts`. Without Zone nothing tells Angular that an async callback has finished, so change detection is scheduled only when something notifies it — a template event listener, an input being set, `markForCheck()`, or a signal read by a template changing. The `afterClosed()` subscriber is an RxJS callback, not a template event, and it still renders because `taskService.editTask()` runs `tasks.update()`, and `TaskPage`'s template reads `filteredTasks()` and the stat computeds derived from that signal. That is why I kept every value a template shows in a signal: had that callback assigned a plain field instead, the screen would stay stale until some unrelated interaction triggered a check.

**[05-task-manager-062] None of your components sets `changeDetection: ChangeDetectionStrategy.OnPush`. Why not, and what would you check before switching?** ⭐⭐

I left Angular's default, which v21 names `Eager` (the old `Default` is now a deprecated alias): whenever a change-detection pass runs, every eager component in the tree is checked, while an `OnPush` one is skipped unless an input changed, an event fired in its template or a signal its template reads was updated. Being zoneless had already removed most of the unnecessary passes and the app is one page with a few dozen rows, so I decided the gain was too small to pursue yet. Most of the code already fits `OnPush`: the templates read signals and `input()`s, and the service replaces the array on every change, so each input receives a new reference. What I would test after switching is `TaskTable`, whose rows are not driven by a changing binding — `[dataSource]` stays the same object and `MatTableDataSource` renders from its own stream — so sorting, paging and filtering would each need checking.

**[05-task-manager-063] Your children use `input()` with default values, like `tasks = input<Task[]>([])`. Why signal inputs, and why not `input.required()`?** ⭐⭐

I chose signal inputs because `TaskTable` has to push each new array into `MatTableDataSource`, and with `input()` that is one `effect()` reading `this.tasks()`, where an `@Input()` would have needed a setter or `ngOnChanges`. They are also read-only inside the child — an `InputSignal` has no `set()` — so a child cannot rewrite state the page owns. The defaults are the weak half: forgetting `[tasks]` on `<app-task-table>` compiles and quietly shows "No tasks yet". Because `strictTemplates` is on, `tasks = input.required<Task[]>()` (and the same for `hasTasks`) would turn that missing binding into a template compile error, which is the honest contract for a table that means nothing without its rows.

**[05-task-manager-064] `TaskPage` declares `tasks = this.taskService.tasks` as a field. What makes that line work, and how could reordering the class break it?** ⭐

Field initializers run top to bottom before the constructor body, and `inject()` works inside them because they run in an injection context, so `private taskService = inject(TaskService)` has already resolved the service when `tasks = this.taskService.tasks` runs on a later line; `TaskDialog` relies on the same order for `members = this.taskService.members`. Move the `tasks` line above the `inject()` line and the build fails, because TypeScript reports `Property 'taskService' is used before its initialization` for a field initializer that reads a field declared after it. The version that compiles is the indirect one in `TaskService`: `tasks = signal<Task[]>(this.loadTasks())` reaches `this.STORAGE_KEY` through a method call the check does not follow, so declaring the constant after `tasks` would type-check and `getItem()` would look up a key literally named `"undefined"`. I chose `inject()` over constructor parameters so these derived values can be plain fields: with the project's `ES2022` target, class fields initialise before constructor parameter properties are assigned, so a field reading one is rejected with that same error.

**[05-task-manager-065] Why are `filteredTasks`, `hasActiveFilters` and the stat counts `computed()` signals rather than getters or methods called from the template?** ⭐⭐

A `computed()` is memoised: it recalculates only when a signal it read changes and otherwise returns the cached value, so `filteredTasks()`, read twice in the template — by the "Showing" line and by `[tasks]` — filters once. The cache matters more than the saving: a getter returning `this.tasks().filter(...)` would hand `TaskTable` a new array on every check, so the input would change on every pass, the table's effect would reassign `dataSource.data` each time, and in development the no-changes check would throw `ExpressionChangedAfterItHasBeenCheckedError`. The trade-off I accepted is that `pendingTasks`, `inProgressTasks` and `doneTasks` each walk the whole list, three passes where one `computed()` with a `reduce()` returning `{ pending, inProgress, done }` would do one; for a local task list that is not measurable, and separate signals keep each template binding a single named value.

**[05-task-manager-066] Why did you build `TaskDialog` with reactive forms instead of template-driven `ngModel`?** ⭐⭐

Every behaviour of that dialog is driven from the class: `patchValue()` pre-fills edit mode in the constructor, `onCancel()` reads `newTaskForm.dirty`, `onSubmit()` checks `newTaskForm.valid` and reads `newTaskForm.value`, and each validator is declared next to its typed `FormControl`. With reactive forms the `FormGroup` exists as soon as the class is constructed, so all of that is synchronous and lives in one file, whereas template-driven controls are only created by the `ngModel` directives once the view renders, and the validation rules move into attributes in the HTML. I chose reactive forms because this form has validation, an edit mode and a dirty check; the search box in `TaskFilters` has none of those, which is why that component imports no forms module at all.

**[05-task-manager-067] Your only route loads `TaskPage` with `component:` instead of `loadComponent:`. Why not lazy-load it, and which location strategy does the app use?** ⭐⭐

Lazy loading pays off for routes the user may never visit on the first load; `TaskPage` is the empty path, so `loadComponent: () => import(...)` would split it into its own chunk and then fetch that chunk immediately on start — one more request and no smaller first render. I decided to keep it eager, and the first secondary route would be the one to lazy-load. `provideRouter(routes)` uses the default `PathLocationStrategy` with `<base href="/">`, so URLs carry no `#`; its cost is that the host must serve `index.html` for paths it does not know, which only starts to matter once a second route exists, and `withHashLocation()` is the alternative for a host where that rewrite cannot be configured.

**[05-task-manager-068] `TaskService` calls `localStorage` directly, with the key `'tasks'`. What assumptions does that make?** ⭐

Two, and both hold only because this is a local, browser-only project. The first is that the code only runs in a browser: the project has no `@angular/ssr`, but under server rendering there is no browser storage to read, so `loadTasks()` would fail as soon as the root service was created, and the usual guard is `isPlatformBrowser(inject(PLATFORM_ID))`. The second is that `'tasks'` is mine: `localStorage` is shared per origin, every app served on `localhost:4200` during development is the same origin, and another project writing its own `'tasks'` array would be loaded here — straight through `loadTasks()`'s `Array.isArray()` check. A namespaced, versioned key such as `'task-manager:tasks:v1'` would isolate it and give a future change to the `Task` shape a key to migrate from.

**[05-task-manager-069] `loadTasks()` wraps parsing in `try`/`catch`, but the effect that saves has none. What can fail on the write side?** ⭐

`localStorage.setItem()` throws a `QuotaExceededError` when the origin's storage — around 5 MB — is full, and a browser set to block site data throws a `SecurityError` on any access to `localStorage`. The signal has already changed by then, so the new task shows in the table while the error thrown inside the effect only reaches Angular's `ErrorHandler` and the console: the user believes it is saved and loses it on reload. The same `SecurityError` would also escape `loadTasks()`, because its `getItem()` call sits above the `try`, and would stop the root service — and with it the page — from being created. I guarded the parse because stored text is the input I do not control and assumed the storage calls would succeed; the complete version puts both calls inside `try` and tells the user when saving fails, for example with a `MatSnackBar`.

**[05-task-manager-070] A user has Task Manager open in two tabs and adds a task in each. What ends up in `localStorage`?** ⭐⭐

Only the list from the tab that saved last. Each tab reads storage once, when its `TaskService` is created, and then keeps its own `tasks` signal, and the effect writes that tab's whole array — so tab B, which never saw tab A's new task, overwrites it on its next add, edit or delete. I accepted last-write-wins because the app is meant to be used in one tab. The fix is to listen for the `window` `storage` event, which the browser fires in the other same-origin tabs when one of them writes a key, and `set()` the parsed list into the signal so each tab works on current data before its next save.

**[05-task-manager-071] Why `crypto.randomUUID()` for task ids rather than an incrementing number, and where can it fail?** ⭐

A counter derived from the list, like the highest id plus one, would give the next new task the id of the newest task whenever that one had just been deleted, and would collide when two tabs add at the same time, and a separately stored counter is one more piece of state to persist; a random UUID needs no state and does not collide in practice. The limit is that `crypto.randomUUID()` exists only in a secure context: HTTPS and `localhost` work, but opening the dev server from a phone at `http://192.168.x.x:4200` leaves it undefined, so Add Task throws a `TypeError` inside `onSubmit()` and the dialog stays open, while editing still works because it reuses `data.task.id`. For that case I would fall back to building the id from `crypto.getRandomValues()`, which is available outside secure contexts.

**[05-task-manager-072] PLANNING.md lists Angular Material v19, but your buttons use `matButton="filled"` and nothing provides animations. Which version is this, and what changed?** ⭐

The project runs Angular and Angular Material 21.2, so PLANNING.md's tech stack line is stale. `matButton` with an appearance value — `"filled"`, `"outlined"`, or bare for a text button — is the unified button directive Material introduced in v20 in place of separate selectors like `mat-flat-button` and `mat-stroked-button`; on v19 that attribute matches nothing and the buttons would render unstyled. The Material version I use also animates components such as the dialog with CSS, which is why `package.json` has no `@angular/animations` and `app.config.ts` has no `provideAnimationsAsync()`, and v21 is the version that made the zoneless change detection this app runs on the default.

**[05-task-manager-073] `TaskTable` imports both `MatPaginator` and `MatPaginatorModule`. Does that matter?** ⭐

Not at runtime: `MatPaginatorModule` already exports `MatPaginator`, a standalone component's `imports` are flattened into one template scope, and the compiler only references the directives the template actually matches, so the bundle is the same either way. It is noise a reviewer will flag, and it sits next to an inconsistency: `TaskFilters` imports the standalone `MatInput` while `TaskDialog` imports `MatInputModule`, and `ConfirmDialog` lists individual dialog directives where `TaskDialog` imports `MatDialogModule`. I would pick one convention for Material imports, apply it to every component and delete the duplicate.

**[05-task-manager-074] Your badge colours are hex values in `styles.css`, not Material tokens. Why, and what happens if the app gets a dark mode?** ⭐

Material 3's `--mat-sys-*` roles are primary, secondary, tertiary, error and the surfaces — there is no amber "pending" or green "done" role — so I defined semantic custom properties in `:root` (`--status-pending-bg`, `--priority-high-text`, …) and the badge rules in `task-table.css` read them by name. The cost is that they sit outside the theme: `material-theme.scss` hard-codes `color-scheme: light`, and switching it to `light dark` would flip every Material surface while the badges stayed light pastel, so each variable would need a dark value, for example through CSS `light-dark()`. The same block also declares `--shadow` and `--danger`, which no stylesheet reads — `--danger` is dead because the red delete button takes its colour from the scoped `mat.$red-palette` theme.

**[05-task-manager-075] The sort arrows on Assignee and Created At are positioned by rules in the global `styles.css`. Why there, and how fragile are they?** ⭐

I wanted those headers centred over their centred cells, and centring `.mat-sort-header-container` moves the arrow along with the label, so I also made `.mat-sort-header-arrow` `position: absolute` at `left: calc(50% + 30px)` and `calc(50% + 38px)`. Those elements are created by `MatSortHeader`'s own template, which the emulated encapsulation of `task-table.css` cannot reach, so the rules had to be global rather than use the deprecated `::ng-deep`. They are the most fragile CSS in the project: both class names are Material internals that can change in any major version, the pixel offsets are tuned to the rendered width of "Assignee" and "Created At", so a renamed or translated label misplaces the arrow, and being global they hit any future table with columns of the same names. It is the opposite of the token-based approach I used for the theme, and the cheaper alternative is leaving sortable headers left-aligned, as Name already is.

**[05-task-manager-076] Why does your table use `table-layout: fixed`, and how does the page cope with a phone-width screen?** ⭐

With the default automatic layout, column widths follow the content of the rows currently rendered, so paging or filtering to rows with longer names would make the columns jump; `table-layout: fixed` with `width: 100%` splits the width evenly across the six columns and keeps it stable. The trade-off is that widths ignore content — a long name wraps inside a sixth of the table, and a long unbroken string can overflow its cell. The page has no responsive handling at all: no media queries, a `.stats-row` flex that never wraps, filter fields with `min-width: 180px` and six fixed columns, so a phone gets horizontal overflow. I would wrap the table in an `overflow-x: auto` container and derive `displayedColumns` from the CDK's `BreakpointObserver`, so narrow screens drop Assignee and Created At.

**[05-task-manager-077] In `task-dialog.css`, how does Description span both columns, and would that rule survive adding a field?** ⭐

The form is a two-column grid, and `mat-form-field:nth-child(5) { grid-column: 1 / -1; }` makes the fifth field — Description — span both. The selector is positional, so adding a Due Date field before Description would make the new field span the row and push Description into a single column; a `full-width` class on the Description field would state the intent and survive reordering. The file's other `grid-column: 1 / -1` rule, on `mat-dialog-actions`, does nothing: `<mat-dialog-actions>` is a sibling of `<mat-dialog-content>`, not a child of the `<form>` grid, so it can be deleted.

**[05-task-manager-078] `{{ task.createdAt | date }}` shows "Sep 14, 2026". Where does that format come from, and what would a Spanish client need?** ⭐

`DatePipe` with no argument uses the `mediumDate` format of the application's `LOCALE_ID`, which defaults to `en-US`, and I left it there because the whole interface — labels, buttons, `<html lang="en">` — is in English. The pipe also parses the stored `'YYYY-MM-DD'` as a local date rather than as UTC midnight, the way `new Date('2026-09-14')` would, so the displayed day never shifts back in a timezone west of UTC. For a Spanish client I would call `registerLocaleData(localeEs)` and provide `{ provide: LOCALE_ID, useValue: 'es' }` to get "14 sept 2026", and translate the paginator separately with a custom `MatPaginatorIntl`, because its "Items per page" label does not follow `LOCALE_ID`.

**[05-task-manager-079] How do Roboto and the Material icons reach the browser in your app?** ⭐

From Google's CDN: `index.html` links the Roboto stylesheet for weights 300, 400 and 500 and the Material Icons font, while `typography: Roboto` in `mat.theme()` only writes the family name into the typography tokens and loads nothing. I chose the links because they need no packages and no build configuration, and accepted their costs: a third-party request on every visit that sends the visitor's IP to Google — a GDPR concern that has already reached EU courts — a render-blocking stylesheet in `<head>`, and icon names like "assignment" showing as plain text if the icon font is slow or blocked. One gotcha is my own: `task-page.css` sets `font-weight: 700` on the title and the stat values, a weight I never load, so the browser falls back to a lighter face or a synthesised bold — self-hosting through npm font packages listed in `angular.json` would fix that and the third-party request together, loading exactly the weights I use.

**[05-task-manager-080] Why did you build this with Angular Material instead of your own components and plain CSS, and what did that cost you?** ⭐⭐⭐

I chose Material because the project's goal was the UI library Spanish consultancies actually use in enterprise Angular apps, and because it gave me behaviour I would otherwise have had to write and get wrong: `MatTableDataSource` sorts and pages the rows, `mat-sort-header` makes each header a labelled button, and `MatDialog` renders in an overlay with a focus trap, Escape to close and focus restored to the trigger. Hand-written, each of those is a small accessibility project of its own, and the table and dialogs are most of this app. The cost is that I style inside Material's rules rather than my own: colours go through `mat.theme()` and its tokens, and the one place I needed a layout it does not offer — centred sort headers — forced global CSS against internal class names that can break on any upgrade. It also ties the project to Material's release pace, as the v20 move from `mat-flat-button` to `matButton="filled"` shows.

**[05-task-manager-081] Why is your task store a `signal<Task[]>` in a service rather than a `BehaviorSubject` or NgRx?** ⭐⭐⭐

I chose a signal because everything that consumes the list is synchronous derived state: `TaskPage` builds `filteredTasks` and the stat counts with `computed()` over `tasks()` and the three filter signals, and the template reads them by calling them — no `async` pipe, no subscription to manage and no `combineLatest` to join the filters. A `BehaviorSubject` would give the same single store, but each derived value would become an observable pipeline and the table's input would need `async` or `toSignal()` before the template could read it. NgRx would wrap one entity list and three operations in actions, a reducer and selectors, a structure that pays off when many features share state and need effects and devtools, not on one page. I still use RxJS where the source is really an event: `afterClosed()` stays an observable, because a dialog result is a one-shot notification rather than state.

**[05-task-manager-082] Why do the tasks persist in `localStorage` rather than a backend, `sessionStorage` or IndexedDB?** ⭐⭐

I wanted tasks to survive a refresh without a server to build, host and secure, because the project was about Material and CRUD patterns in the UI, not persistence. `sessionStorage` would drop the list when the tab closes, which defeats a task list, and IndexedDB is asynchronous, so the service could not start the store with `signal<Task[]>(this.loadTasks())` in a field initializer — it would start empty, fill in a moment later and need a loading state. A synchronous `getItem()` over a few kilobytes of JSON fits that shape exactly. The cost is that the data belongs to one browser on one device: the assignee list suggests a team, yet nobody else can see the tasks, and clearing site data deletes them all.

**[05-task-manager-083] Your filters live in signals on `TaskPage`. What does a user lose because they are not in the URL, and how would you move them there?** ⭐⭐

A refresh resets every filter to `'all'` even though the tasks survive in `localStorage`, a filtered view cannot be bookmarked or sent as a link, and the browser's Back button cannot undo a filter, because nothing the router knows about ever changes. I kept them as signals because this is a single-user tool on one route, where those losses are small and syncing the URL would add router code to every filter change. To move them I would make the query string the source of truth: register `withComponentInputBinding()` in `provideRouter()` so `?status=done&priority=high&q=report` arrives in `input()`s on the routed `TaskPage`, derive `filteredTasks` from those, and have each handler call `router.navigate([], { queryParams: { status }, queryParamsHandling: 'merge' })` instead of `set()` — with `replaceUrl: true` for the search box, so each keystroke does not add a history entry.

**[05-task-manager-084] When a user edits one task, does `mat-table` destroy and rebuild every row?** ⭐

No. `editTask()` maps the array and returns the same object for every untouched task and a new one only for the edited task, and the `filter()` in `filteredTasks` and the data source's sort and page slices all keep those references. `mat-table` diffs each new array against the rows it last rendered using its `trackBy`, which defaults to object identity, so it keeps the DOM of every unchanged row and replaces only the edited one; an add or a delete likewise touches only the rows that enter or leave the current page. That reuse comes from my update style rather than from anything I declared: a change that rebuilds every object — re-parsing `localStorage` on the `storage` event to sync tabs, for example — would re-create every row, and a `[trackBy]` function returning `task.id` would tie row reuse to the id instead.

**[05-task-manager-085] Your filter fields set `subscriptSizing="dynamic"` but the dialog's fields do not. Why the difference?** ⭐

By default a `mat-form-field` reserves one line under the control for its hint or `mat-error`, so an error appearing does not move anything around it. The dialog needs that: its four required fields show `mat-error` after a failed save, and in the two-column grid a field that grew only when invalid would push the rows below and misalign against its neighbour, so I kept the default there. The filter fields never show a hint or an error, so the reserved line would only be empty space under the filter bar, and `dynamic` removes it. The cost is the one `dynamic` always carries: if I ever gave a filter a hint or an error, the layout would shift the moment it appeared.

**[05-task-manager-125] `strictTemplates` is on. Would a typo like `{{ task.nmae }}` in your table template fail the build?** ⭐⭐

No — and the table's cells are the one place in the app where it would not. I kept the CLI's `strictTemplates` because it checks every binding against its component: in `task-page.html`, `[tasks]="filteredTasks()"` must be a `Task[]`, and `$event` in `(status)="onStatusChange($event)"` is typed `FilterStatus` by the child's `output()`. But MatTable's `*matCellDef` and `*matRowDef` declare no type for their template context, so `let task` is `any`: `{{ task.nmae }}` compiles and renders an empty cell, and `(click)="openConfirmDialog(task)"` hands that `any` to a `Task` parameter without complaint. Closing the gap takes a small directive on the same `[matCellDef]` selector whose `static ngTemplateContextGuard` declares `$implicit` as `Task`; for six columns I accepted it, which makes `task-table.html` the template that deserves the closest review.

**[05-task-manager-126] Your global styles are split into `material-theme.scss` and `styles.css`, listed in that order in `angular.json`. Why two files, and does the order matter?** ⭐

I split them by what each one needs: `mat.theme()` is a Sass mixin, so the theme and the scoped `.btn-danger` rule have to live in a Sass file, while my custom properties, the reset and the sort-header fixes are plain CSS. It is also a second reason the red theme could never sit next to the table: every component stylesheet in this project is `.css`, and a `.css` file cannot `@include` a mixin. The order changes nothing today — both files style `body`, but with different properties — and the `* { margin: 0; padding: 0; }` reset in `styles.css` has zero specificity, so Material's class-based padding wins wherever it loads. What the reset does remove is the browser's default margin on elements like `h1` and `p`, which is why `.subtitle` adds its own `margin-top` and why `.no-data-row p { margin: 0 }` in `task-table.css` is redundant.

**[05-task-manager-127] The browser tab of your app reads "05TaskManager". Where does that come from, and how would the router set it?** ⭐

It is the `<title>` the CLI wrote into `index.html` from the project name, and nothing ever replaces it, because the only route in `app.routes.ts` has no `title`. The router's default `TitleStrategy` sets `document.title` after every navigation from the matched route's `title` property, so `{ path: '', component: TaskPage, title: 'Task Manager' }` would name the tab without injecting the `Title` service anywhere. I would still correct `index.html`, since its text is what shows before the app boots and what a link preview that runs no JavaScript reads; and once a second route exists, each route's own `title` keeps the tab and the browser history telling the pages apart.

**[05-task-manager-128] Your project has a `.prettierrc` but no ESLint. What does the `angular` parser override in it do, and what does Prettier not catch?** ⭐⭐

Prettier only picks its `angular` parser by itself for files named `*.component.html`, and since the v20 naming convention my templates are called `task-page.html`, so the override forces it for every `*.html` — without it they would be parsed as plain HTML, with the `@if`/`@for` blocks and the bindings formatted as ordinary text. But Prettier only decides layout, such as the 100-character line and single quotes, never whether the code is correct, and the project has no `lint` script or `lint` target: the CLI does not generate one and I never ran `ng add angular-eslint`. A type-aware ESLint config would already flag real code — `announceSortChange()` calls `LiveAnnouncer.announce()`, which returns a `Promise`, without awaiting or handling it, which `@typescript-eslint/no-floating-promises` reports. I would add `angular-eslint` and run `ng lint` before the build, so correctness is checked and not only formatting.

**[05-task-manager-129] Some files import the model with `import type { Task }`, others with a plain `import { Task }`, and `TaskPage` writes `type FilterStatus` inline next to a plain `Task`. Does the difference matter?** ⭐

Not in the output: everything in `task.model.ts` is an interface or a type alias, and TypeScript erases an import that is only ever used as a type, so each of those imports disappears from the bundle whichever form I wrote. The mix is an inconsistency, not a decision — `isolatedModules`, which the tsconfig enables so every file can be compiled on its own, requires the `type` keyword only when re-exporting a type, so nothing forced one convention. `import type` is still the clearer form, because it tells the reader the import has no runtime side, and turning on `verbatimModuleSyntax` would make it mandatory by rejecting the plain imports at compile time. The one import that must never take the keyword is a class Angular uses as an injection token, since `import type` erases it: here every service is passed to `inject()` as a value, so no tool can mistake it for a type, whereas with constructor injection the class appears only in a parameter's type position, and a lint auto-fix such as `@typescript-eslint/consistent-type-imports` could rewrite that import to `import type` and break the injection.

**[05-task-manager-130] Task Manager is live on Netlify, yet the project has no `netlify.toml` and no `_redirects` file. What does Netlify publish, and what does keeping that configuration out of the repo cost?** ⭐⭐

It publishes the production build: `ng build` defaults to the `production` configuration in `angular.json`, and the application builder writes `index.html` into `dist/05-task-manager/browser`, one level below the project's output folder — so a publish directory pointing at `dist/05-task-manager` would serve Netlify's 404 page instead of the app. I set the base directory, the build command and that publish directory in Netlify's site settings rather than in a `netlify.toml`, which was the quickest path for a static app with no environment variables, but it means nothing in the repo describes the deploy: a folder move such as the repo's `angular/` → `projects/` reorganisation leaves the site building from a path that no longer exists, and no diff shows why. The missing `_redirects` costs little today, because `/` is the only URL the app answers, yet any other path gets Netlify's 404 before Angular even boots; a second route would need `/* /index.html 200` in `public/`, which the `assets` glob copies next to `index.html`. `outputHashing: "all"` gives the bundles content-hashed names like `main-TPX3EEMR.js`, so they could be cached for a year, but Netlify's default `max-age=0, must-revalidate` still revalidates them on every visit unless a `_headers` rule says otherwise.

**[05-task-manager-131] `material-theme.scss` passes `mat.$blue-palette` as both `primary` and `tertiary`, with `density: 0`. What does each setting control, and what would a client's brand colour need?** ⭐⭐

`ng add @angular/material` generated an azure primary with a blue tertiary; I changed the primary to blue, so both keys now point at the same tonal palette, and `mat.theme()` takes the secondary, neutral and error roles from the sub-palettes the primary palette carries. The tertiary key feeds the contrasting-accent roles, and among the components this app uses none reads them — in Material 21 that is mainly the datepicker — so today it changes nothing on screen, and the only second colour is the scoped red on Delete. `density: 0` is the default scale: `mat.theme()` accepts `0` down to `-5`, and a negative value shortens form fields, buttons and table rows, which a dense enterprise screen often wants and five rows per page did not need. A brand colour is the real gap, because the prebuilt palettes are a fixed set of hues: `ng generate @angular/material:theme-color` turns the client's hex into `$primary-palette` and `$tertiary-palette` in a generated `_theme-colors.scss`, and switching the `mat.theme()` call to them restyles the whole app without touching component CSS, since every rule reads `--mat-sys-*` tokens.

**[05-task-manager-132] Task names are free text and come back from `localStorage`, which anyone can edit in DevTools. What happens if a stored name is `<img src=x onerror=alert(1)>`?** ⭐⭐

Nothing runs: the table cell renders `{{ task.name }}`, and Angular compiles an interpolation into an update of a text node, so the browser shows the markup as literal characters and never parses it — the same holds for the delete confirmation, whose title is that name rendered through `{{ data.title }}`. I kept every piece of user data in interpolations, so no template binds it to `[innerHTML]`, a URL or a style; had I bound the name with `[innerHTML]`, Angular's sanitizer would strip the `onerror` handler and warn in the console, and only `bypassSecurityTrustHtml()` would let it through. The only stored strings that reach something other than text are status and priority in `[ngClass]`, and a class name cannot execute — a tampered `"done high"` would just add two classes. What interpolation does not protect is the storage itself: any script running on the same origin can read and rewrite the `tasks` key, which is harmless for a task list and the reason `localStorage` is the wrong place for anything sensitive, such as an auth token.

**[05-task-manager-133] The assignee options use `@for (member of members; track member)`. Why track by the name itself, and when would that be wrong?** ⭐

`track` tells Angular which item each rendered `<mat-option>` belongs to, so when the array changes it can keep or move the existing DOM instead of recreating it. `members` holds plain strings with no id and every name is unique, so I let the string be its own identity; `track $index` would tie each option to its position instead, so an insertion at the top would rewrite the text of every option below it rather than add one. In this dialog the choice barely shows, because `members` is a constant and the options render once per dialog. It becomes wrong the day two team members share a name: Angular warns with `NG0955` about duplicated track keys in development, and the real problem is the data, since a task stores its assignee as that same string — the fix is an id per member, tracked with `track member.id` and stored on the task.

## Testing

**[05-task-manager-086] What do the tests in Task Manager actually check, and why did you put the real assertions on the two dialogs?** ⭐⭐⭐

There are seven spec files, but five of them — `App`, `TaskPage`, `TaskTable`, `TaskFilters` and `TaskService` — only hold the CLI's `should create` check; the real assertions are in `confirm-dialog.spec.ts`, which checks that the dialog renders the title and message it was opened with and that `confirm()` closes with `true`, and in `task-dialog.spec.ts`, which checks that `onSubmit()` does not close on an invalid form and closes with the built task on a valid one. I chose the dialogs because their result is a contract other code acts on: `TaskTable` emits a delete only on a truthy confirm result, and `TaskPage` persists whatever `TaskDialog` hands back, so a wrong value there silently deletes or saves bad data. They were also the cheapest to isolate, because I made each dialog return its result through `dialogRef.close()` instead of calling `TaskService`, so a test only has to watch one fake method — no page and no overlay. The next candidates are the pure logic in `TaskPage`'s `filteredTasks` and `hasActiveFilters` computeds, which a test can drive by setting signals, and the guard in `TaskService.loadTasks()` against corrupted storage.

**[05-task-manager-087] Your `TaskTable` and `TaskPage` specs need no providers, but both dialog specs provide `MatDialogRef` and `MAT_DIALOG_DATA`. Why the difference?** ⭐⭐⭐

`TaskTable` and `TaskPage` only inject services declared `providedIn: 'root'` — `MatDialog`, `LiveAnnouncer` and `TaskService` — so TestBed's root injector resolves them with no configuration. `MatDialogRef` and `MAT_DIALOG_DATA` are not root services: `MatDialog.open()` creates a child injector for every dialog it opens and provides that dialog's own ref and data there, so when a test creates `ConfirmDialog` directly with `TestBed.createComponent()`, nothing has opened it and `inject(MatDialogRef)` throws `NullInjectorError`. That is why the generated dialog specs failed until I added a `providers` array standing in for what `open()` would have supplied: a fake ref, `{ close: vi.fn() }`, and the data — a `ConfirmDialogData` fixture for the confirm dialog and `null` for the task dialog.

**[05-task-manager-088] Your specs use `describe`, `expect` and `vi.fn()` without importing them. What runs these tests, and in what environment?** ⭐⭐

The `test` target in `angular.json` uses `@angular/build:unit-test`, the Angular CLI's Vitest builder, which v21 generates in place of Karma and Jasmine, so `ng test` runs Vitest 4. The builder turns on Vitest's globals and `tsconfig.spec.json` lists `vitest/globals` in `types`, which is why `describe`, `it`, `expect` and `vi` need no import — `vi.fn()` being Vitest's counterpart of `jasmine.createSpy()`. The DOM is `jsdom`, the devDependency in `package.json`, not a real browser: it builds the element tree and its `textContent`, which is all my rendering assertion reads, but it computes no layout or theme, so a test here can check that the confirm button carries the `btn-danger` class and never that it is actually red. I left the builder's `browsers` option unset — it would run the same specs in Chromium through a Vitest browser provider such as `@vitest/browser-playwright` — because no assertion in this suite reads layout, so a real browser would only add a browser install and a slower run.

**[05-task-manager-089] Your specs `await fixture.whenStable()` instead of calling `fixture.detectChanges()`. Why, and what does being zoneless take away in tests?** ⭐⭐

The app loads no `zone.js` and neither do the tests, so the fixture runs on the same zoneless scheduler as production: automatic change detection is on for the fixture, creating the component schedules its first render, and awaiting `whenStable()` waits for that render to finish — which is what lets the `textContent` check in `confirm-dialog.spec.ts` see the title. I kept that instead of forcing `detectChanges()`, because a forced pass renders whether or not anything notified Angular, so it can hide the bug a zoneless app actually has: a plain field changed in a callback that production would never re-render. What I lose is `fakeAsync` and `tick()`, which depend on `zone.js/testing`; to control time in a test I would use Vitest's `vi.useFakeTimers()` instead.

**[05-task-manager-090] Five of your specs only check `should create`. What does that one assertion actually prove — in `TaskPage`, for example?** ⭐⭐

It proves the component can be built and rendered once without throwing: every `inject()` resolves and the first template pass hits no runtime error. For `TaskPage` that is more than it looks, because the test renders the real tree — `TaskFilters`, and `TaskTable` with its `MatTableDataSource`, sort and paginator — against the real root `TaskService`, which reads `localStorage` when it is created; a new dependency that is not `providedIn: 'root'`, or a template reading a property of `undefined` on first render, would fail it. It proves nothing about behaviour — no emitted event, no filtered row, no rendered count is checked — and `app.spec.ts` never even reaches `TaskPage`, because TestBed registers no routes and the `<router-outlet />` stays empty. I treat them as the smoke tests the CLI generated, not as coverage of any decision.

**[05-task-manager-091] To test `ConfirmDialog` you create it directly with a fake `MatDialogRef` instead of opening it through `MatDialog`. Why that approach?** ⭐⭐

What I wanted to test is the dialog's own contract — render the data it receives, close with `true` on confirm — and `TestBed.createComponent()` plus two providers isolates exactly that, with a spy I can assert on straight away. Opening it for real with `MatDialog.open()` would test Material's overlay as well: the dialog renders into the overlay container outside the fixture's element, closing waits for the exit animation, and the result has to be read from `afterClosed()`. That wider style is the right one for the caller's side — checking that `TaskTable` emits `taskId` only after a confirm — and Material ships component harnesses for it, such as `MatDialogHarness` from `@angular/material/dialog/testing`, which find the dialog in the overlay without depending on Material's internal DOM.

**[05-task-manager-092] Your `MatDialogRef` fake is just `{ close: vi.fn() }`. Why is that enough, and what does the compiler check about it?** ⭐

My own code only ever calls `close()` on the ref, so that is the one member I faked — but it is not the only reader: `mat-dialog-title` and `mat-dialog-actions` in both templates inject the same `MatDialogRef` token and reach for its `_containerInstance`, and they survive the fake only because Material reads that field with optional chaining. The compiler checks none of this, because a provider's `useValue` accepts any object, so a dialog that later called `dialogRef.afterClosed()` or `backdropClick()` would fail at runtime with "is not a function", not at build time. The data fixture is the opposite — I declared it `const data: ConfirmDialogData`, so renaming a field of that interface breaks the spec at compile time. Typing the fake as `Pick<MatDialogRef<ConfirmDialog>, 'close'>` would state which slice of the ref my component depends on, while a test that needs everything Material's directives expect would open the dialog inside a real ref with `MatTestDialogOpener` from `@angular/material/dialog/testing`.

**[05-task-manager-093] Walk me through your two `TaskDialog` behaviour tests. What bug would each one catch that the other would miss?** ⭐⭐

"should not close while the form is invalid" calls `onSubmit()` on a fresh add-mode form, whose four required controls start empty, and expects `close` never to be called — it guards the `if (this.newTaskForm.valid)` check, so deleting that check would push an empty task through the `as TaskStatus` casts and this test would fail while the other still passed. "should close with the new task once the form is valid" fills every control with `setValue()` and expects `close` to receive a task carrying those values — it catches an `onSubmit()` that validates but never closes, or closes with the wrong fields. On its own, the negative test also passes for an `onSubmit()` that does nothing at all, which is why I paired it with the positive one: together they pin both branches of the `valid` check.

**[05-task-manager-094] Both dialog specs create `dialogRef = { close: vi.fn() }` once, at `describe` level. Can one test's calls leak into another?** ⭐⭐

Yes: `beforeEach` rebuilds the testing module and the component for every test, but the fake is created once, when the `describe` body runs, and Vitest keeps a mock's call history between tests unless `clearMocks` or `mockReset` is set — neither the Angular builder's defaults nor this project set them. `task-dialog.spec.ts` passes today only because Vitest runs a file's tests in the order they are written, so "should not close" runs before the test that calls `close`. Swap the two, or enable `sequence.shuffle`, and `not.toHaveBeenCalled()` fails on the call the valid-form test left behind. I would create the fake inside `beforeEach`, or call `vi.clearAllMocks()` there, so every test starts from zero calls.

**[05-task-manager-095] Why does the valid-form test assert with `expect.objectContaining()` instead of the exact task, and what does that leave unchecked?** ⭐⭐

In add mode two fields are not deterministic — `id` comes from `crypto.randomUUID()` and `createdAt` from `today()` — so an exact `toHaveBeenCalledWith({ ... })` would need values the test cannot know. I chose `objectContaining({ name, status, priority })` to sidestep that, but it also leaves out `assignee` and `description` and says nothing about whether an id and a date were stamped at all: a task closed with `id: undefined` would pass. The tighter version either constrains the random parts — `id: expect.any(String)`, `createdAt: expect.stringMatching(/^\d{4}-\d{2}-\d{2}$/)` — or pins them, with `vi.spyOn(crypto, 'randomUUID')` returning a fixed id and `vi.useFakeTimers()` plus `vi.setSystemTime()` fixing today's date, so the whole task can be compared exactly.

**[05-task-manager-096] The spec fills the form with `setValue()`, while the dialog itself pre-fills with `patchValue()`. Why the different method in the test?** ⭐

`patchValue()` fills whatever keys it is given and ignores the rest, which is the right fit in the dialog, where a `Task` is mapped onto the form. `setValue()` demands a value for every control: because the form is typed, its argument is the full raw value of the group, so if someone adds a `dueDate` control the spec stops compiling at that call — and at runtime `setValue()` throws for a missing control too. That is what I want in a test: it forces me to decide what a valid task now needs instead of quietly testing a form that is no longer valid. The same typing rejects a wrong value, so `status: 'pendng'` would not build against `FormControl<TaskStatus | ''>`.

**[05-task-manager-097] The `TaskDialog` spec provides `MAT_DIALOG_DATA` as `null`. Why `null`, and how would you test edit mode?** ⭐⭐

I provided `null` because that is what the real dialog receives in add mode — `openDialog()` passes no data and `MatDialogConfig`'s default is `null` — so the test runs the component exactly as `TaskPage` opens it for a new task. It also means every test in the file is add mode: the constructor's `patchValue()` and the reuse of `data.task.id` and `data.task.createdAt` in `onSubmit()` never run. Edit mode needs its own `describe` block whose `configureTestingModule` provides `{ task }` as the data, because the shared `beforeEach` already creates the component and `TestBed.overrideProvider()` is rejected once the testing module has been instantiated. Its tests would assert that the form starts with the task's values and that submitting closes with the original `id` and `createdAt` — the guarantee that matters most, since `editTask()` matches by id and an edit carrying a new one would be silently dropped.

**[05-task-manager-098] `TaskDialog` injects `TaskService`, but its spec does not provide one. Which instance does the test use, and does that matter?** ⭐⭐

The real one: I provided no double, and since `TaskService` is `providedIn: 'root'`, TestBed creates it and the dialog reads `members` from it exactly as in the app. Creating it runs `loadTasks()` against the test environment's `localStorage` and registers the effect that writes the list back, so this test of a form also touches storage — and the Angular builder defaults Vitest's `isolate` to `false`, to match the Karma experience, so spec files running in the same worker can share that storage. It is harmless today because the dialog only reads a constant and nothing in the file adds a task. If the service ever loaded its tasks from an API, this spec would start failing on a missing `HttpClient` for a reason unrelated to the form; providing `{ provide: TaskService, useValue: { members: ['Ana'] } }` would make it depend only on what the dialog actually uses.

**[05-task-manager-099] Your tests call `component.confirm()` and `component.onSubmit()` directly instead of clicking the buttons. What does that skip?** ⭐⭐

The template: the tests prove what the methods do, not that the buttons call them. `strictTemplates` would reject a `(click)` naming a method that does not exist, but not a binding that was deleted or moved to the Cancel button — and in `TaskDialog` the click is the only path to `onSubmit()`, since pressing Enter in the form never reaches it. A click-level test queries the rendered button, calls `.click()` and awaits `fixture.whenStable()`, or — better in a Material project — uses `MatButtonHarness.with({ text: 'Add Task' })` from `@angular/material/button/testing`, which finds the button by its visible text instead of Material's internal DOM. I called the methods directly because each test's purpose was the dialog's close contract, which a method call reaches with the least setup.

**[05-task-manager-100] `ConfirmDialog`'s test is called "should render the labels it was opened with". What does it really assert?** ⭐

Less than its name says: I only check that the host's whole `textContent` contains the title "Delete task" and the message — not the button labels the name promises, and not where each string appears. Adding the labels as written would be a weak check too: `confirmLabel` is "Delete", already a substring of the title, so `toContain('Delete')` would pass even if the confirm button rendered nothing. The fixture also sets `danger: true` without asserting that the confirm button gets `btn-danger`, the one styling rule its callers rely on. A tighter test gives every field a distinct value and queries the elements themselves — the `h2` for the title, each button for its label, and `querySelector('.btn-danger')` for the flag.

**[05-task-manager-101] How would you test that `TaskDialog`'s Cancel asks for confirmation only when the form is dirty?** ⭐

`onCancel()` depends on the answer of a second dialog, so I would provide a `MatDialog` double whose `open` is a `vi.fn()` returning `{ afterClosed: () => of(true) }` — `of()` emits synchronously, so the assertions can follow the call directly. Three tests cover the branches: a pristine form closes the task dialog without calling `open`; after `newTaskForm.markAsDirty()`, a `true` answer means `open` received `ConfirmDialog` and `close` was called; and with `of(false)`, `close` is never called. The current spec cannot reach this, because it lets the real root `MatDialog` in, which would render a real `ConfirmDialog` into an overlay nobody answers.

**[05-task-manager-102] Your specs put the standalone component in `imports` and call `compileComponents()`. Is that call needed?** ⭐

A standalone component belongs to no NgModule, so it goes in `imports`, and TestBed takes its compilation scope from the component's own `imports` array — which is why no spec lists a single Material module. `compileComponents()` exists to fetch and compile external `templateUrl` and `styleUrl` files at test time, which only matters when tests run outside the CLI's build. Under `@angular/build:unit-test` the templates are compiled by the build before Vitest starts, so the call has nothing left to do; it is harmless scaffold the CLI still generates, and I left it rather than diverge from the generated shape.

**[05-task-manager-103] Your `TaskService` spec gets the service with `TestBed.inject()` from an empty testing module. Why not simply `new TaskService()`?** ⭐⭐

Because the constructor calls `effect()`, and `effect()` has to run in an injection context: `new TaskService()` outside one throws `NG0203` before the test can assert anything. `TestBed.inject()` builds the service in TestBed's root injector exactly as `providedIn: 'root'` builds it in the app, so `configureTestingModule({})` needs no providers and the effect gets the injector and scheduler it depends on. I kept that shape because it is how every consumer obtains the service; the service has no constructor parameters to swap, so constructing it by hand would buy nothing. It is also why its `beforeEach` is synchronous where the component specs `await`: there is no template to compile and no fixture to stabilise.

**[05-task-manager-104] `task-table.spec.ts` renders `TaskTable` without passing it any tasks. Why does that pass, and what would `input.required()` do to it?** ⭐⭐

It passes because I gave every input of `TaskTable` and `TaskFilters` a default — `tasks = input<Task[]>([])`, `hasTasks = input<boolean>(false)` — so the first render reads an empty list and the table's effect assigns `[]` to the data source without the spec ever supplying a value. Switching to `input.required()` would break both smoke specs at runtime: a required input read before it has a value throws `NG0950`, and `TaskTable`'s effect reads `this.tasks()` on the very first pass. The spec would then set the inputs the way a parent does, with `fixture.componentRef.setInput('tasks', [...])` before awaiting `whenStable()`, since an `InputSignal` has no `set()` a test could call. Outputs work in the other direction: subscribing to the `OutputEmitterRef`, as in `component.taskToEdit.subscribe(spy)`, lets a test check what the table emits without writing a host component.

**[05-task-manager-105] `TaskService`'s spec only checks that it is created. How would you test its `localStorage` persistence, and what makes that awkward?** ⭐⭐

The read happens in a field initializer, `tasks = signal<Task[]>(this.loadTasks())`, so a load test has to seed `localStorage.setItem('tasks', ...)` before `TestBed.inject()` — seeding afterwards tests nothing, since TestBed creates a fresh service per test and reads storage at that moment. On the write side the effect does not run inside `update()`: it is scheduled, so after `service.addTask(task)` I would call `TestBed.tick()` to flush it before reading `localStorage.getItem('tasks')`. I would also clear storage in `beforeEach`, because `localStorage` outlives each test inside the file, and under the Angular builder's `isolate: false` it can also carry over from other spec files in the same worker — the `TaskDialog` and `TaskPage` specs create the same service against it. With that in place, the corrupted-storage guard is two short tests that seed `'not json'` and `'{}'` and expect `service.tasks()` to equal `[]`.

**[05-task-manager-134] `TaskPage`'s `filteredTasks` and `hasActiveFilters` have no test. How would you test the coordinator's filter logic, and what would you stub?** ⭐⭐

I would test it through the class rather than the rendered table: a `computed()` can be read synchronously outside any template, so after `component.onStatusChange('done')` or `component.onSearchName('rep')` the test reads `component.filteredTasks()` at once, with no `whenStable()`, and checks `hasActiveFilters()`, the stat counts, and that `onClearAll()` brings all three filters back. I would create the page with `{ provide: TaskService, useValue: { tasks: signal<Task[]>([...]) } }` instead of seeding `localStorage`, because the filter paths only read `tasks`, the fixture list is then visible in the spec itself, and the real service would read and write a storage that other specs can share under the builder's `isolate: false`. The first run would already find a bug: `onSearchName('   ')` followed by `expect(component.hasActiveFilters()).toBe(false)` fails today, because `hasActiveFilters` compares the untrimmed term that `filteredTasks` trims.

**[05-task-manager-135] `task-dialog.spec.ts` checks that an invalid form does not close, but not what the user sees. How would you test the `SubmitOnlyErrorStateMatcher`, and why is calling `onSubmit()` from the test not enough?** ⭐⭐

The behaviour worth pinning is the one that makes the matcher mine: leaving an empty field shows no `mat-error`, and a save attempt shows all four. So the test dispatches `blur` on the Name input, awaits `fixture.whenStable()` and expects no `mat-error` in `fixture.nativeElement` — the step Material's default touched-or-submitted matcher would fail — then clicks the Add Task button, awaits again and expects four. It has to be the click: `onSubmit()` only sets the plain `submitted` field on `errorMatcher` and reads the form, and neither notifies the zoneless scheduler, so `whenStable()` would find no render to wait for and the errors would stay hidden in the test although the app shows them. The button's `(click)` listener, like the input's `blur` listener, is what schedules that change-detection pass in production, so going through it tests the path the user actually takes.

**[05-task-manager-136] Your `ConfirmDialog` spec only tests the confirm path. Which bug on the Cancel side would slip through, and how would you test it?** ⭐⭐

The expensive one: if Cancel ever closed with a truthy value — say the bare `mat-dialog-close` became `[mat-dialog-close]="true"` — `TaskTable` would delete the task the user had just declined to delete, and all three current tests would still pass. Cancel has no method on the class, only the `MatDialogClose` directive, so no method call reaches it: the test clicks the rendered Cancel button, and because the directive injects the same `MatDialogRef` token and closes through it, the fake's `close` records the result. I would assert `expect(dialogRef.close.mock.calls[0][0]).toBeFalsy()` rather than `toHaveBeenCalledWith('')`, since what `TaskTable` and `TaskDialog` rely on is "not truthy", not the empty string — and only with a `vi.fn()` created per test, or `calls[0]` would be the `true` the confirm test left behind.

**[05-task-manager-137] Nothing in the repository runs your specs automatically. What stops a failing test from reaching the live site, and what would a coverage report tell you about this suite?** ⭐⭐

Nothing: the only trigger is `npm test`, which runs `ng test` on my machine, the repository has no CI workflow, and Netlify's build only runs the production build, which compiles the app without executing a single spec. The cheapest gate is a build command of `ng test --watch=false && ng build`, so a red spec fails the deploy; the Vitest run needs only Node and the `jsdom` devDependency already in `package.json`, no browser on the build image. Coverage is `ng test --coverage`, which also needs `@vitest/coverage-v8` installed, and on this suite its number would flatter it: rendering `TaskPage`, `TaskTable` and `TaskFilters` in the smoke specs executes most of their code while asserting nothing about it. Coverage counts the lines that ran, not the behaviour that was checked, which is why I describe these tests by what they assert rather than by a percentage.

**[05-task-manager-138] The CLI generated a `should render title` test in `app.spec.ts`, and it is no longer there. Why did you delete it rather than fix it?** ⭐

The scaffold test looked for an `<h1>` containing "Hello, 05-task-manager", which only the CLI's placeholder template ever rendered; once `app.html` was just `<router-outlet />`, `querySelector('h1')` found nothing, so the test could only fail, and the `title` signal it was written for had no reader left. I removed both in one refactor commit because there was no behaviour to rescue — rewriting it as "renders a router outlet" would pin a line of markup rather than a decision — and a red test the suite learns to live with trains everyone to ignore red, which hides the next real failure. What the root level actually carries is the route table, and the test worth writing there provides `provideRouter(routes)` and awaits `harness.navigateByUrl('/', TaskPage)` on a `RouterTestingHarness`, which throws unless the empty path activates `TaskPage` — something the remaining `should create`, with no routes registered, can never check.

**[05-task-manager-139] Every test double in your specs goes through TestBed `providers`. Why not `vi.mock('./task.service')`, the way a Jest suite would mock a module?** ⭐

I replace dependencies at the seam Angular already gives me: `TaskService`, `MatDialogRef` and `MAT_DIALOG_DATA` all reach the components through `inject()`, so a `{ provide: …, useValue: … }` entry swaps one per testing module and leaves the import graph untouched. Under `@angular/build:unit-test` that is more than a preference: the CLI bundles each spec with esbuild before Vitest runs it, so a relative import is already compiled into the bundle rather than a module Vitest could intercept, and the builder patches `vi.mock`, `vi.doMock` and their siblings to throw "not supported for relative imports … Please use Angular TestBed" for any path starting with `.` or `/`. Package imports stay external, so `vi.mock('@angular/material/dialog')` would still be accepted, but mocking a whole library to fake one ref replaces far more than the component depends on. The DI version is also the one that reads the same in a Jasmine/Karma suite, where `jasmine.createSpyObj` fills the `useValue` instead of `vi.fn()`.
