# Interview Questions — 04-meal-finder

**Last banked:** 2026-09-13

Questions specific to the implementation decisions made in this project.
Use these alongside the topic-based files in `interview-prep/{LEVEL}/en/` and `es/`.

## Architecture & Patterns

**[04-meal-finder-001] Every route in `app.routes.ts` uses `loadComponent()`, including the empty path that is the first screen anyone sees. What does the browser actually download on a cold visit to `/`, and why lazy-load the landing route at all?** ⭐⭐⭐

The initial bundle is the framework plus the `App` shell and the route table; `SearchPage` arrives as its own chunk on the first navigation, which for `/` is immediately — so there is one extra round trip before the landing screen paints. I chose uniformity over shaving that trip: every routed page is a chunk, so adding a page never changes the bundle shape and there is no eager/lazy exception for a reader to remember. What stays eager is genuinely shared by all four routes, because the shell is only the nav bar, the favourites badge and the `<router-outlet/>`.

**[04-meal-finder-002] The wildcard `**` route is declared last and is lazy like the rest. What happens if I move it to the top of the array?** ⭐⭐

Route matching is first-wins in declaration order, so a `**` above `detail/:id` would match every URL and the app would render `NotFoundPage` and nothing else — no error, no warning, just a dead application. I decided the wildcard should be lazy for the same reason as the others: the 404 chunk is only ever fetched by someone who already typed a wrong URL, so it never costs a correct visit anything.

**[04-meal-finder-003] The detail page reads an id out of the URL and calls `lookup.php`, even though the card the user clicked already holds the whole `Meal` object. Why pay for a request for data you already have?** ⭐⭐⭐

Handing the object across through a shared signal would render instantly and save the call, but then `/detail/52772` typed, refreshed or shared with somebody would render an empty page — the route would only work when reached by a click. I chose the URL as the page's only input: `toSignal(paramMap)` → `effect` → `getMealById`, which makes every detail view linkable, reloadable and correct under the back button. The cost is one request per view, which a read-only public API serves without complaint.

**[04-meal-finder-004] You read the id with `toSignal(this.activatedRoute.paramMap...)` instead of `this.activatedRoute.snapshot.paramMap.get('id')`. When does that difference actually bite in this app?** ⭐⭐⭐

The router reuses the component instance when only a parameter changes, so with a snapshot a navigation from `/detail/52772` to `/detail/52773` would leave the old recipe on screen — the constructor never runs a second time and the snapshot is never re-read. I chose the observable projected into a signal so the id is reactive and the loading `effect` re-runs whenever it changes. Honestly, no screen today links one recipe to another — a hand-edited URL reloads the whole app and builds a fresh component — so the snapshot would pass every current test; I chose the stream because the first "related meal" link would otherwise ship a bug nobody could see from the link's own code.

**[04-meal-finder-005] `onSearchMeals()` in the search page does not call `MealService` at all — it calls `router.navigate()`. Can you walk me through the loop that ends in an HTTP request?** ⭐⭐⭐

The handler writes the URL only: `router.navigate([], { relativeTo: this.activatedRoute, queryParams: { q: term } })`. `queryTerm = toSignal(queryParamMap…)` reads it back as a signal, and the constructor `effect` is what calls `searchMeals(term)` and fills `meals`. I chose one direction of flow so that typing a search, pressing the back button and opening a shared `/?q=beef` link are literally the same code path rather than three that have to agree; the price is the indirection — nothing calls the API where the click happens, and that is the thing I have to explain when someone reads the file.

**[04-meal-finder-006] That navigate call passes an empty commands array. What does navigating to `[]` mean, and why `relativeTo` at all?** ⭐⭐

Empty commands means "keep the current URL and change only what else I pass", so the effective change is the `queryParams`. `relativeTo` is what resolves *relative* commands such as `['../x']`, and with no commands there is nothing to resolve — on this page it changes nothing observable, since the search page is the root route and both forms produce `/?q=beef`. I kept it so the call still means "this page's route" if the page ever moves under a path like `/search`, and I decided against `queryParamsHandling: 'merge'` because `q` is the only parameter this route has — merging would faithfully preserve parameters I never put there.

**[04-meal-finder-007] Both pages fire their HTTP call from an `effect()` in the constructor, rather than `ngOnInit` with a subscription, or a route `resolve`. Why an effect?** ⭐⭐

In both pages the request is derived from a signal that comes from the URL — `queryTerm`, `mealId` — and an effect is exactly "re-run when the signals I read change"; with `ngOnInit` I would be subscribing to `paramMap` by hand and owning that subscription's lifetime myself. A `resolve` would also work and would take the loading state out of the component, but it delays the navigation, so the user sits on the old page with nothing happening instead of seeing a spinner on the new one. I chose the spinner, which is also why `isLoading` exists in both pages.

**[04-meal-finder-008] Your effects take `onCleanup` and unsubscribe in it. What concretely breaks if I delete those two lines?** ⭐⭐⭐

The cleanup runs before every re-run and once on destroy, so the request for the previous id or term is cancelled before a new one starts. Without it two overlapping searches can settle out of order and the slower, older response wins — the stale-result race — and navigating away mid-request would still push into signals of a destroyed component. I chose the effect's own cleanup rather than a `switchMap` pipeline because the trigger is a signal and not a stream, so the cancellation stays with the thing that re-runs.

**[04-meal-finder-009] Three root-provided services — `MealService`, `FavouriteService`, `NavigationHistoryService`. Why three instead of one app state service?** ⭐⭐

They have genuinely different natures: `MealService` is stateless HTTP, `FavouriteService` is persistent state with an invariant, and `NavigationHistoryService` is an observation of the router. `providedIn: 'root'` is what makes the favourites a singleton — the shell's badge, the search page and the detail page must all read the same signal, and a component-provided service would give each route its own copy. I decided against bundling them because the two presentational components inject none of the three, and a single state object would make that boundary harder to see rather than easier.

**[04-meal-finder-010] `FavouriteService` keeps `_favourites` private and exposes `favourites = this._favourites.asReadonly()`. What does that actually prevent?** ⭐⭐⭐

The writable handle never leaves the service, so `addFavourite` and `deleteFavourite` are the only writers and nothing can go around them. A page holding the writable signal could call `.set([])` and the persistence effect would faithfully write that to `localStorage` — the invariant "what is on screen is what is stored" only holds while every write goes through a method. I chose read a signal, call a method as the service's whole contract, which is also why the pages hold `favourites` and never a setter.

**[04-meal-finder-011] `favouriteIds` is a `computed()` that builds a `Set`. Why derive a data structure instead of exposing an `isFavourite(id)` method on the service?** ⭐⭐

A method called from a template runs on every change-detection pass, and `favourites().some(m => m.idMeal === id)` is a linear scan each time; a `computed()` recomputes only when the favourites signal changes. A `computed` takes no arguments, so what I can memoise is the lookup structure rather than the answer for one id — hence a `Set` of ids and `favouriteIds().has(id)` at the call sites. I chose deriving the structure once over trying to memoise a per-id call.

**[04-meal-finder-012] Persistence is a single `effect()` in the service constructor, not a `localStorage.setItem` at the end of `addFavourite` and `deleteFavourite`. Why is the effect the better place?** ⭐⭐

The effect reads `favourites()`, so every writer persists — the two methods today and any method I add later, which cannot forget a step it does not have. I chose to treat storage as a derivation of state rather than as part of each command; the honest cost is that persistence is invisible at the call site, which is why the effect sits in the constructor of the service that owns the signal instead of somewhere in the app shell.

**[04-meal-finder-013] The favourites signal is initialised inline with `JSON.parse(localStorage.getItem('favourites') ?? '[]')`. Why read synchronously in the field initialiser, and what happens if that entry is corrupt?** ⭐

I chose to read storage in the field initialiser because it runs while the service is being constructed, before any page can read the signal, so the first render already shows the stored favourites instead of an empty list that fills in a tick later. The `??` covers a missing key but nothing covers a malformed value: a hand-edited `favourites` entry makes `JSON.parse` throw, the service fails to construct, and because the shell injects it that failure happens during bootstrap. The fix is a `try/catch` returning `[]`, which `03-expense-tracker` does and this project does not.

**[04-meal-finder-014] Your Back button on the detail page goes through `NavigationHistoryService`. Why is `location.back()` on its own not good enough?** ⭐⭐

`Location.back()` replays browser history, so on a detail URL that was opened directly — a shared link, a refresh, a bookmark — it walks out of the application entirely. The service counts `NavigationEnd` events from bootstrap and exposes `canGoBack = navigations() > 1`; the page calls `location.back()` when that holds and falls back to `router.navigate(['/'])` when it does not. I chose counting the app's own navigations because that is the only thing the page can observe — the browser will not tell you what is behind you.

**[04-meal-finder-015] Why `takeUntilDestroyed()` on the router-events subscription of a service that lives as long as the application?** ⭐

It binds the subscription to the destruction of the injection context it was created in, which for a root service is the application's own injector — so on a normal page it never fires, and it is what unsubscribes when a test destroys the `TestBed` injector or a teardown destroys the app. An `ngOnDestroy` on the service would also run when that injector is destroyed; I chose `takeUntilDestroyed()` because the teardown sits in the same pipe as the subscription and needs no `Subscription` field to remember, and an untied `Router.events` subscription is the shape that leaks the moment the service is provided somewhere shorter-lived than root.

**[04-meal-finder-016] `App` injects `NavigationHistoryService` into a private field it never reads. Why is it there, and what would you do instead?** ⭐⭐

Injection is construction, and this service's constructor is what starts counting `NavigationEnd` — if the first injection happened in the detail page, the counting would begin after the navigations it exists to count. The field carries a comment saying exactly that, because a field nothing reads is the first thing a reviewer deletes. `provideAppInitializer` in `app.config.ts` would state the intent in the right place, and I decided the one-line injection plus its comment was proportionate here.

**[04-meal-finder-017] The favourites badge is `computed(() => this.favouriteService.favourites().length)` in the shell. Why is the count computed there rather than published by the service?** ⭐⭐

I decided the length is a view concern — one badge on one nav link — so the service publishes the state it derives from, plus the `Set` of ids that other consumers need, and the shell derives the number it displays. Putting the nav in `App` is the other half of the decision: `App` is the one component outside the outlet, so it survives every navigation, the badge never remounts, and the number is live on all four routes without any page having to remember to update it.

**[04-meal-finder-018] The brand link carries `[routerLinkActiveOptions]="{ exact: true }"` and the favourites link does not. Why the asymmetry?** ⭐

`routerLinkActive` matches by URL prefix, and `/` is a prefix of every URL in the app. The brand's `routerLinkActive` carries no class name, so it styles nothing — it is there only as the host for `ariaCurrentWhenActive` — and without `exact: true` a screen reader would announce the brand as the current page on every route, the detail and favourites pages included. `/favourites` needs no option because nothing is nested under it, so prefix and exact matching coincide; I chose to add the option only where the two actually differ, which in this app is the root link.

**[04-meal-finder-019] You use `ariaCurrentWhenActive="page"` next to `routerLinkActive`. What does the second one add?** ⭐

`routerLinkActive` only toggles a CSS class, which tells the eye and nothing else; `ariaCurrentWhenActive` sets `aria-current="page"` on the same link while it is active, so a screen reader announces which nav item is the current page. I chose the router's own input over binding `[attr.aria-current]` to a manual URL comparison, because the router already knows the answer and a hand-written comparison is one more thing that can disagree with the class.

**[04-meal-finder-020] `MealCard` and `CategoryFilter` inject nothing at all. What does that split buy you in *this* project, concretely?** ⭐⭐⭐

`MealCard` is rendered by the search page, where favourite-ness is `favouriteIds().has(id)`, and by the favourites page, where it is `[isFavourite]="true"` by definition — one component, two different truths, only because it takes the value as an input instead of asking a service. Both children emit intent rather than act: `favouriteToggled` means add-or-remove on the search page and always-remove on the favourites page, and `categorySelected` means whatever `FavouritesPage` decides. I chose inputs down, outputs up precisely so the card has no idea which of those two screens it is in, and that is why there is one card and not two.

**[04-meal-finder-021] You used `input.required()` and `output()` rather than `@Input()` and `@Output()`. What changes?** ⭐⭐

`input.required<Meal>()` is a signal, so `favouriteLabel` in the card can be a `computed()` that reads it directly, and "required" is enforced by the compiler instead of by a `!` and hope — using `<app-meal-card>` without a `[meal]` is a build error. `output()` is the same emitter without a decorator, and I chose the pair so each component's public surface is declared as fields rather than as decorator metadata. The cost lands in the tests: a required signal input must be supplied with `componentRef.setInput()` before the first change detection, which is what the generated specs do.

**[04-meal-finder-022] `selectedCategory` lives in `FavouritesPage` and is passed back *down* into the filter as `[selected]`. Why doesn't the filter keep its own selection?** ⭐⭐

The page needs the value to compute `filteredFavourites`, and it also needs to *write* it — removing the last favourite of a category resets the selection to "All" — so I gave the state exactly one owner and left the child to render it. The child spends it twice, `[class.active]` for the eye and `[attr.aria-pressed]` for the accessibility tree. If the filter owned its own selection, the page-side reset would have to be pushed back into it, which is the two-sources-of-truth problem this shape avoids.

**[04-meal-finder-023] `allCategories` is derived in the page with `[...new Set(...)]`. Why is that not in `FavouriteService` next to `favouriteIds`?** ⭐⭐

The category list is a projection of the favourites for one screen's filter, so I derive it where it is consumed; the service publishes what every consumer needs — the list itself and the `Set` of ids. As a `computed()` it recomputes only when the favourites change, and `[...new Set(...)]` deduplicates in a single pass, which for a personal favourites list is the entire algorithm. Had a second screen needed the same categories, that is the point at which I would move it into the service.

**[04-meal-finder-024] The search page exposes `isFavourite(id)` as a method used from the template, while the detail page uses a `computed()`. Same question, two mechanisms — why?** ⭐⭐

The detail page has exactly one id, so the answer is a single derived value and `computed()` memoises it along with `favouriteLabel`. The search page asks it once per card, and a `computed` takes no arguments, so I chose a plain method over the already-memoised `favouriteIds()` Set — the expensive part, building the lookup, is cached in the service and the per-card call is a `has()`. It is still an inconsistency a reader notices, and the honest answer is that it is one, justified by where the memoisation actually sits.

**[04-meal-finder-025] `MealService` returns `Observable<Meal[]>` and `Observable<Meal | null>`, never `Observable<MealResponse>`. What is that boundary for?** ⭐⭐

`{ meals: Meal[] | null }` is MealDB's transport envelope and it stops inside the service: `map(r => r.meals ?? [])` for search, `map(r => r.meals?.[0] ?? null)` for the lookup. I chose to translate once at that boundary so no page ever writes `response.meals?.[0]` and so changing provider is an edit in one file. It also lets the two absences be shaped differently on purpose — an empty array for "nothing matched a search", `null` for "there is no meal with this id" — which is what the detail page's not-found branch reads.

**[04-meal-finder-026] `handleFailure` is a private method that returns a function taking an `Observable`. Why build a custom operator instead of writing `catchError` twice?** ⭐⭐

It returns `(source: Observable<T>) => source.pipe(catchError(...))`, which is what an RxJS operator is, so it drops into `.pipe()` and both public methods end with the identical failure translation. The `action` string is the only thing that varies — `Could not search meals.` versus `Could not load the meal.` — while the `console.error` and the `throwError(() => new Error(...))` stay in one place. I chose one generic `<T>` factory so the service cannot drift into two different failure contracts as it grows.

**[04-meal-finder-027] Neither page ever sees an `HttpErrorResponse`. Where is that decided, and what is a page left to handle?** ⭐⭐

`catchError` in the service logs the transport error and rethrows a plain `Error` carrying a user-facing message, so a page's `error:` callback handles exactly one shape and its whole job is `hasError.set(true)`. I decided the service owns that translation because a status code is transport knowledge and there is nothing the page could do with it here — no retry, no token refresh, and not even a 404 branch, since MealDB answers an unknown id with `200 { "meals": null }` rather than an error at all. An `HttpInterceptorFn` would be the home for logging once several services call several APIs, but it cannot know which user action failed, and that action is the one thing the page's message carries.

**[04-meal-finder-028] The detail page carries `isLoading`, `loadFinished` *and* `hasError` for what looks like a three-state screen. Why the third flag?** ⭐⭐

Because there are four outcomes: loading, loaded, not found, and failed. `mealDetails()` being `null` cannot distinguish "nothing has been asked yet" from "asked, and there is no meal with that id", so `loadFinished` records that a callback actually ran; the template's `@else if` chain then reads recipe → still loading → request failed → meal not found. I chose to record the observation rather than infer it from the absence of data, which is the same reason the search page has `hasSearched`.

**[04-meal-finder-029] In `MealCard` the root of the clickable area is an `<a [routerLink]>` and the favourite `<button>` is its *sibling*, not inside it. Why that structure?** ⭐

An element that navigates should be a link, so keyboard focus, Enter and open-in-new-tab come from the tag instead of from a click handler I would have to reimplement; and interactive content cannot be nested inside an anchor, so the favourite control sits beside the link inside the card `<div>`. That structure is also what makes the focus ring work: `.meal-card:has(.meal-link:focus-visible)` raises the ring from the link up to the whole card, which would be meaningless if the card itself were the anchor.

**[04-meal-finder-030] `CategoryFilter` is the only component in the project with a `:host` rule. Why did extracting it need one?** ⭐

Extracting the filter introduced an `<app-category-filter>` element between the page container and the buttons, and a custom element is `display: inline` by default — so the row's flex layout suddenly had nowhere to live and the buttons stacked as inline content. I chose to fix it from inside with `:host { display: flex; … }`, which styles that wrapper so the layout travels with the component instead of the page having to know the component exists and reach around it.

**[04-meal-finder-031] Every component has its own `styleUrl`, yet the colour tokens are in the global `styles.css`. Why split styling that way?** ⭐

Component styles are view-encapsulated, which is what I want for layout and local class names — `meal-card.css` cannot leak onto the filter. A palette is the opposite kind of thing: one definition every component reads, so `:root` in `styles.css` holds the custom properties and no component or page stylesheet carries a literal hex. Custom properties inherit through the encapsulation boundary, which is what makes the split possible: `--primary` is one edit and the whole app follows.

**[04-meal-finder-032] `NotFoundPage` is an empty class with a template. Why is it a routed page at all instead of a redirect to `/`?** ⭐

It has no state and no dependencies, so the class body is genuinely empty; the file exists to give the `**` route something to load and the message somewhere to live, with a `routerLink="/"` back to search. I decided a real page beats `redirectTo: ''` because a redirect silently rewrites the URL and tells the user nothing — they end up on the search screen wondering whether their link was wrong or the app lost it.

**[04-meal-finder-033] `app.config.ts` holds exactly three providers. What does that inventory tell you about this app, and what is deliberately not there?** ⭐⭐

`provideBrowserGlobalErrorListeners()`, `provideRouter(routes)` and `provideHttpClient(withFetch())` — a routed app that reads one public API and has no authentication: no interceptor, no guard, no initializer. I decided the config should be an honest inventory of the app's cross-cutting concerns rather than a pre-registration of what a later project needs, because a stub interceptor or an empty `provideAppInitializer` suggests infrastructure that does not exist. The favourites persistence is not there either — it belongs to the service that owns the signal, not to the application's provider list.

**[04-meal-finder-034] Why `withFetch()` in a project with no server-side rendering?** ⭐

It swaps `HttpClient`'s backend from `XMLHttpRequest` to the platform's `fetch`. With no SSR the user-visible difference here is essentially nil: nothing in this app streams a response, and cancellation already works through unsubscribing. I chose it because it is the backend Angular is moving towards and the one that keeps working unchanged if the app is ever rendered on a server or at the edge — XHR stays the default only for backwards compatibility, not because it is the better choice for new code.

**[04-meal-finder-035] `main.ts` is `bootstrapApplication(App, appConfig).catch(err => console.error(err))`. What class of failure actually lands in that `catch`?** ⭐

Bootstrap failures — the promise rejects if constructing the application throws, for example the `JSON.parse` in `FavouriteService` on a corrupt `favourites` entry, since the shell injects that service and it is therefore constructed during bootstrap. At that moment nothing has been rendered, so I kept the handler to a log: there is no UI to degrade into and no state worth recovering. It is also why `provideBrowserGlobalErrorListeners()` is not a substitute for it: that catches errors once the application is running, and this catches the failure to have an application at all.

**[04-meal-finder-036] Every component here is standalone with its own `imports` array, and `MealDetailPage` declares `imports: []` while its template is full of `@if`, `@else if` and interpolation. Why is that array empty?** ⭐⭐

The built-in control flow is compiled by the template compiler itself, so `@if` and `@for` need no `CommonModule` the way `*ngIf` did, and that page reaches the router through injected `Location` and `Router` rather than a `routerLink` in the markup — so there is genuinely nothing left to import. I chose standalone components with per-component imports so each file declares exactly the directives its own template uses: `MealCard` imports `RouterLink` because its root is a link, `SearchPage` imports `MealCard`, `CategoryFilter` imports nothing. The payoff is that deleting a component cannot leave a dangling declaration in a module somebody else owns, and the cost is that a shared directive has to be listed in every template that uses it.

**[04-meal-finder-037] The layering rule here looks like "whatever is routed is smart, whatever is under `components/` is presentational" — but `App` injects two services and is neither routed nor presentational. Where does the shell fit?** ⭐⭐

`App` is the one component outside the outlet, so I treated it as a third kind: a shell that owns the cross-route furniture — the nav, the live badge, the `<router-outlet/>` — and is allowed to inject for exactly that reason. It reads `FavouriteService` because the badge has to be live on all four routes, and it injects `NavigationHistoryService` purely so the counting starts at bootstrap. I decided against pushing the nav into a `components/nav` child, because that child would need both services injected and would stop being presentational, which is the property that makes `components/` a useful folder at all.

**[04-meal-finder-038] Your `Meal` interface carries MealDB's own field names — `idMeal`, `strMeal`, `strMealThumb` — and templates interpolate `meal().strMeal` directly. Why didn't you map that to a domain shape at the service boundary?** ⭐⭐

I translated the envelope and stopped there: `map(r => r.meals ?? [])` unwraps `MealResponse`, but the field names travel through the services, the pages and every template exactly as the provider sends them. I decided a mapper was not worth its cost for a read-only app with one provider and seven fields that nothing ever writes back — it would be a second shape to keep in step for no change in behaviour. The price is real and I would name it in an interview: the provider's naming is now visible in every template, so swapping MealDB would be an edit in `MealService` *and* in every `str*` reference, which is the coupling the envelope translation was meant to prevent.

**[04-meal-finder-039] `searchMeals` builds `new HttpParams().set('s', name)` instead of interpolating the term into the URL. What does a user have to type for that to matter?** ⭐⭐⭐

A term containing query syntax: "salt & pepper" concatenated into `search.php?s=` becomes two parameters and searches for `salt`, a `#` truncates the URL at the fragment, and a `+` is read as an encoded space. I chose `HttpParams` for both calls so `HttpClient` percent-encodes the value and user input can never become part of the query's structure — including for the `i` parameter on `lookup.php`, even though an id coming from the route is a much narrower input. It is the same class of defect as building SQL by concatenation, one layer up, and the correct version costs one line.

**[04-meal-finder-040] The MealDB base URL is a `private readonly baseUrl` field inside `MealService`, and the project has no `environment.ts`. Where would that choice break?** ⭐

It breaks the moment the same code has to point somewhere else — a mock server for tests, a staging host, or a proxy added to work around CORS — because the host is baked into the class rather than supplied to it. I chose the field because MealDB is one public, read-only, key-less endpoint with no per-environment variant, so an environment file would be a build-time indirection holding a single value. What I would reach for if that changed is an `InjectionToken` provided in `app.config.ts`, which is also what would let a test swap the host without touching the service's source.

**[04-meal-finder-041] The favourite control exists twice — the button, the `[class.active]`, the ★/☆ glyphs and a `favouriteLabel` computed are in `MealCard` and again in `MealDetailPage`. Why is there no shared favourite-toggle component?** ⭐⭐

It is duplication I accepted knowingly, and the reason is that the two are not the same control: the card's sits absolutely positioned over an image inside a link, while the detail page's sits in a heading row beside an `<h1>`, so a shared component would be one element with two layouts passed into it. I decided the genuinely shared part was the *label logic* rather than the control, and even that is three lines, so extracting it would trade a real duplication for an indirection of about the same size. If a third screen needed the toggle I would extract a `FavouriteButton` taking `meal` and `isFavourite` as inputs and emitting the same `favouriteToggled`, which is the shape both copies already have.

**[04-meal-finder-042] The search box's text exists twice: a `searchTerm` signal bound with `[value]`, and the `#meal` template reference the click handler actually reads. Why two?** ⭐⭐

The signal is what the template reacts to — `[disabled]="!searchTerm().trim()"` on the button, and re-displaying the term when `?q=` is read back out of the URL on load — while `(click)="onSearchMeals(meal.value)"` reads the element because that is the value at the instant of the click. I chose the signal as the source of truth for what is shown and what is forbidden, and kept the ref as a convenience at the call site, which only holds together because `(input)` writes the signal on every keystroke. I would write it single-source now — pass `searchTerm()` to the handler and drop the `#meal` ref — because two ways to read one input is a bug waiting for the day one of them stops being updated.

**[04-meal-finder-043] `page-title` and `visually-hidden` are used inside component templates but defined only in the global `styles.css`. Why does that work at all, given view encapsulation?** ⭐

Encapsulation scopes the rules a component *declares*, not the class names in its markup: Angular rewrites a component stylesheet's selectors to carry that component's own attribute, so global rules keep matching the element normally. I chose to leave the reset, the typographic `.page-title` and the `.visually-hidden` clipping box global because they are identical on every page, and copying them into four page stylesheets would be four things to keep in step. The tradeoff is a component template that silently depends on a stylesheet it does not import, which is why I kept that set tiny and obviously app-wide instead of letting local layout classes drift into the global file.

**[04-meal-finder-044] In the class you narrow — `const id = this.mealId(); if (!id) return;` — but the detail template is full of `mealDetails()!`. Why the double standard?** ⭐⭐

In the class the `null` is in the type rather than on the screen — `paramMap.get('id')` returns `string | null` and `initialValue: null` adds another — so the compiler demands a check even though `detail/:id` cannot match without an id, and narrowing into a local satisfies it without an `as string` that would also silence a real `null` if the route ever changed. In the template the surrounding `@if (mealDetails() && loadFinished())` has already proved the value, but each `mealDetails()` is a fresh signal read that the compiler cannot narrow across, so the `!` is me asserting what the guard established one line above. I chose it at the time for brevity; `@let meal = mealDetails()!` at the top of the block, or `@if (mealDetails(); as meal)`, removes every other `!` from that template and is what I would write now.

**[04-meal-finder-045] The favourite buttons bind `[attr.aria-label]` and the filter buttons `[attr.aria-pressed]`, not `[ariaLabel]` or `[ariaPressed]`. Why the `attr.` prefix, and why is the label a `computed()`?** ⭐

A plain binding in Angular sets a DOM *property*, and ARIA is defined as attributes whose property reflections are recent and uneven, so `[ariaPressed]` can bind nothing at all and fail silently while `[attr.aria-pressed]` writes the attribute the accessibility tree actually reads. I made the label a `computed()` because an icon-only ★ has no text content, so that attribute is the control's entire accessible name and it has to carry both the meal and the direction: `Remove Teriyaki Chicken from favourites`, not a static "favourite". On the filter the same prefix carries state rather than name, because `[class.active]` is only colour and a screen-reader user would otherwise never learn which category is selected.

**[04-meal-finder-127] Every lazy route is `loadComponent: () => import('./pages/…').then((m) => m.SearchPage)`. Angular accepts a default export there with no `.then` at all. Why keep named exports and the extra hop?** ⭐

The `.then` is the price of every page being a named export, and I chose named exports because the same kind of class is also imported eagerly elsewhere — `MealCard` by two pages, `App` by `main.ts` — so one export style holds across the whole app instead of routed pages being the only default exports. It also keeps the route table explicit: each entry names the class it loads, so renaming `SearchPage` breaks `m.SearchPage` at compile time instead of the route quietly loading whatever the file exports by default. `export default` would shrink each entry to `loadComponent: () => import('./pages/search-page/search-page')`, which is a fair rule for a codebase that default-exports every routed page; I decided it was not worth making pages the one exception here.

**[04-meal-finder-128] Components here are `meal-card.ts` exporting `MealCard` and `search-page.ts` exporting `SearchPage` — no `.component` file suffix, no `Component` class suffix — yet the services are `meal.service.ts` exporting `MealService`, and PLANNING.md's own tree still says `meal-card.component`. What is the naming rule?** ⭐⭐

The components follow the current Angular style guide, which is also what the CLI generates from version 20: file and class are named for what the thing is, so `MealCard` rather than `MealCardComponent`, and a routed screen carries its role in the `Page` of its name and in the `pages/` folder. I kept the suffix on the services and the model deliberately, writing it into the generate path, because there the bare name collides — `Meal` is already the interface, so a `meal.ts` service beside `meal.model.ts` would be ambiguous, while `MealCard` cannot be confused with anything. The PLANNING.md tree was written before the code and never updated — it also says `detail-page` for what shipped as `meal-detail-page` — and I would say in an interview that the tree drifted rather than pretend it describes the files.

**[04-meal-finder-129] The injected services are `private`, but every signal a template reads is public, nothing is `protected` or `readonly`, and `MealDetailPage` exposes `mealId` and `isLoading` publicly although its template reads neither. What is the visibility rule?** ⭐

The rule I actually applied is the one the template compiler enforces: a template cannot read a `private` member, so dependencies are `private` and anything bound in the markup is left public — `queryTerm` in the search page is private precisely because only the effect reads it. That stops short of what the current style guide asks for: `protected` for members that exist only for the template, so no outside code holding a component reference can call `meals.set(...)`, and `readonly` on inputs, outputs and signal fields, so a field like `meals` can never be reassigned to a different signal the template is no longer reading. The detail page shows what the looser rule costs — `mealId` and `isLoading` are public API with no reader, which a narrower default would at least have made me justify.

**[04-meal-finder-130] `MealCard`'s `favouriteToggled` emits the whole `Meal`, and `FavouritesPage` only ever reads `idMeal` out of it. Why that payload?** ⭐⭐

I sized the output for its richest consumer: on the search page a toggle can mean *add*, and `addFavourite` stores the complete object, so an id-only event would force the page to look the meal back up in `meals()` before it could add it. The honest counterpoint is that the payload is redundant in both parents — each renders the card inside an `@for`, so `(favouriteToggled)="toggleFavourite(meal)"` already has the loop variable in scope and the card could emit `output<void>()`. I kept the payload because it makes the event self-describing: a handler never depends on template scope to know which card fired, and the card's contract reads as "this meal was toggled" rather than "something happened in me".

**[04-meal-finder-131] `MealCard` emits through an `onToggle()` method, `CategoryFilter` calls `categorySelected.emit(category)` straight from its template, the search page writes `searchTerm.set(meal.value)` inline, and `FavouritesPage` wraps the same kind of one-line write in `onSelectedCategory()`. Where is the line between template and class?** ⭐

There is no single rule applied across these four files, and I would say so rather than invent one after the fact. The line I would defend is that a template may do one direct write or emit whose meaning is obvious from the markup — `categorySelected.emit(category)` inside a `@for` needs no name — and anything that makes a decision belongs in a named method, which is why the pages' `toggleFavourite` is a method and should stay one. By that rule `onToggle()` and `onSelectedCategory()` are wrappers that name nothing the binding did not already say, so I would inline them, and the payoff of applying it uniformly is that a method on the class always means logic.

**[04-meal-finder-132] `MealCard` is the presentational component, yet it hardcodes `[routerLink]="['/detail', meal().idMeal]"`. Doesn't a dumb card that knows the app's URL scheme break the split?** ⭐⭐

It bends it, and I chose that knowingly: the card injects no service and holds no state, but it does know that a meal lives at `/detail/:id`, a fact owned by `app.routes.ts`. Renaming that path to `meal/:id` would still compile, because a link array is only strings to the compiler, and every card would start landing on `NotFoundPage`. The purer shapes are an input the parent fills, or one exported helper such as `mealDetailLink(id)` beside the routes that both the table and the card read; I decided a path written in two files did not yet justify either, and a third file linking to a recipe is where I would extract it.

**[04-meal-finder-133] The card is `position: relative; overflow: hidden`, the star is `position: absolute` in its top-right corner, the title's `.card-head` wrapper carries `padding-right: 2.5rem`, and the link's focus outline has `outline-offset: -2px`. How do those four rules depend on each other?** ⭐

`position: relative` makes the card the containing block, so the absolutely positioned star anchors to the card's corner rather than to the page, and the header's right padding reserves the strip the star floats over so a long meal name wraps before it runs under the button. `overflow: hidden` is what makes the image follow the card's `border-radius`, and it has a cost I had to pay back: it clips anything painted outside the card box, including an outline drawn outside the full-width link. I chose the negative offset so the focus ring is drawn inside the link and stays visible, which is why removing `overflow: hidden` to "fix" the ring would instead break the rounded corners.

**[04-meal-finder-134] Every `transition` sits on the base rule — `.meal-card`, `.nav-link`, `.favourite-btn`, `.category-btn` — never on `:hover`, and nothing checks `prefers-reduced-motion`. Why there, and what about the user who asked for less motion?** ⭐

A transition declared only on `:hover` applies only while the hover state holds, so the effect animates in and snaps back the moment the pointer leaves; on the base rule it governs both directions, which is why PLANNING.md records it as a pattern rather than a preference. What I did not do is honour the operating-system setting: the card's `translateY(-3px)` lift and the spinner's infinite `spin` run regardless, and a `@media (prefers-reduced-motion: reduce)` block removing the transform and slowing the spinner is the whole fix. The colour transitions are harmless under that setting; movement is what it exists for, so that is what I would scope it to.

**[04-meal-finder-135] The search input sets `outline: none` and signals focus only by changing its 1px border to `--primary`, while the category buttons and the card link draw a 2px `:focus-visible` outline. Is the input's focus state good enough?** ⭐⭐

No, and it is the one place the project breaks its own focus convention: a 1px border shifting colour is a change a keyboard user has to hunt for, and a removed outline is the first thing an accessibility review flags. I removed it for looks on a field that already had a border, and no rule in `styles.css` restores it, so this component stylesheet is the only thing deciding. The fix is to follow the rest of the app — keep the border change and add the same `outline: 2px solid var(--primary)` on `:focus-visible` — or simply not write `outline: none` on a text field at all.

**[04-meal-finder-136] The recipe instructions render as `{{ mealDetails()!.strInstructions }}` inside a `<p>` capped at `max-height: 300px; overflow-y: auto`. What does a user actually get?** ⭐

A wall of text in a box that scrolls separately from the page: MealDB separates the steps with line breaks, and plain interpolation into a paragraph collapses that whitespace, so every step runs into the next. I capped the height to keep the recipe panel compact beside the photo, but a scroll region inside a scrolling page is awkward on touch and is not reliably reachable by keyboard in every browser without a `tabindex`. The cheaper and better version is `white-space: pre-line`, which keeps MealDB's own breaks, and no height cap — the instructions are the content of that page, not a sidebar to be contained.

**[04-meal-finder-137] The spinner is an empty `<div>`, the failure message a plain `<p>` that an `@if` creates, and the nav badge's number changes silently. What does a screen-reader user hear after pressing Enter on a search?** ⭐⭐

Nothing: a sighted user watches the grid turn into a spinner and then into cards or "Something went wrong. Try again.", but none of those nodes has a role or a live region, so no change is announced — and the badge count that moves after a star click is just as silent. I built the loading and error states for the eye and stopped there. The gotcha in the fix is that a live region has to exist before its content changes — an element an `@if` inserts together with its text is often not announced — so the right shape is one permanent `role="status"` element outside the branches, holding visually-hidden text I update ("Loading", "12 meals found", "Search failed").

**[04-meal-finder-138] The shell renders `<nav>` and then `<router-outlet />` with no `<main>`, and all four pages open with their own `.container { max-width: 1100px; margin: 0 auto; }`. Why is the page frame repeated in every page?** ⭐⭐

I let each page carry its own frame, and that produced two separate costs. The layout one is duplication: the 1100px width is written four times plus once more on `.app-nav`, and the not-found page already diverges on padding. The structural one matters more: with no `<main>` landmark and no skip link, a screen-reader or keyboard user cannot jump past the nav to the content. I would move the frame into the shell as `<main class="container"><router-outlet /></main>`, since the shell already owns what every route shares, and let a page that genuinely needs different spacing say so in its own stylesheet.

**[04-meal-finder-139] Every page has one `<h1>`, but the recipe page jumps to `<h3>Instructions</h3>` with no `<h2>`, and a result card's title is a `<p class="meal-title">`. Does the heading outline matter here?** ⭐

It matters to people who navigate by headings, which is how many screen-reader users skim: on the search screen the only heading is "Find a meal", so a grid of results offers nothing to jump between, and on the recipe page the skipped level makes "Instructions" read as a sub-section of a section that does not exist. I picked `<h3>` for its default size and `<p>` for the card to avoid heading styles, which is choosing an element for how it looks. The fix is `<h2>` in both places with the size set in CSS, and `.meal-title` already carries its own typography in both stylesheets.

**[04-meal-finder-140] The detail page's Back control is a `<button type="button">` with its background, border, padding and font reset to look like a link, while the two favourite stars and the Search button carry no `type` at all. Why a button, and does the missing `type` matter?** ⭐⭐

Back performs an action — `goBack()` decides at click time between `location.back()` and navigating home — rather than pointing at an address, so it is a button: an `<a>` with no `href` is skipped by Tab, has no link role and never fires on Enter, and a real `href` would have to name a destination the method only chooses later. The resets are there because a user-agent button is visually loud and this one is meant as a quiet affordance above the recipe. The missing `type` is harmless today because the default, `submit`, only means something inside a `<form>` and there is none; I would still write `type="button"` on every button that is not a submit, because the day a form wraps any of them, an unmarked button starts submitting it.

**[04-meal-finder-141] `strYoutube` and `strMealThumb` go straight from a third-party API into `[href]` and `[src]`, and `strInstructions` into `{{ }}`. What stops MealDB — or whoever compromises it — from injecting script into your page?** ⭐⭐

Angular does, in two different ways. Interpolation writes a text node, so markup inside `strInstructions` is shown as characters and never parsed, and property bindings to URL attributes such as `href` and `src` pass through the built-in sanitizer, which rewrites a `javascript:` value to `unsafe:javascript:…` and logs a warning instead of producing a clickable script. I chose to rely on that and never reach for `[innerHTML]` or `bypassSecurityTrustUrl`, because at that moment the API's text becomes my markup. What the sanitizer does not check is the destination: any `https://` URL passes, so a compromised `strYoutube` still becomes a working link to a site that is not YouTube, and validating the host is the part I would have to write myself.

**[04-meal-finder-142] Both pages' `toggleFavourite` is `this.isFavourite(...) ? this.favouriteService.deleteFavourite(...) : this.favouriteService.addFavourite(...);` — a ternary used as a statement. Would you let that through a code review?** ⭐

Not in a team codebase. A conditional expression exists to produce a value, and here both results are discarded, so the line reads as a calculation while it is really two branches with side effects — ESLint's `no-unused-expressions` flags exactly this shape. I wrote it for brevity because each branch is one call, but an `if … else` is barely longer once formatted and says plainly that the side effect is the point. It also survives change better: the first time one branch needs a second statement, the ternary has to be rewritten anyway.

**[04-meal-finder-143] The search box is an `<input type="text">` with `(keyup.enter)` and a sibling `<button (click)>` — there is no `<form>`. Why not let the browser's own submit handle Enter?** ⭐⭐

I wired both events by hand, which works, but a `<form (submit)>` turns Enter in the field and a click on the button into one event, so the handler is bound once and there is no second path to keep in step. The gotcha is that with no `FormsModule` imported there is no `ngSubmit` to cancel the native submission, so a bare `(submit)` must call `$event.preventDefault()` or the browser reloads the page and throws the app away. The same change is where the semantics come from: `role="search"` on the form makes it a landmark and `type="search"` gives mobile keyboards a Search key, neither of which a text input with `(keyup.enter)` can express.

**[04-meal-finder-144] `MealDetailPage` injects six things — `ActivatedRoute`, `MealService`, `FavouriteService`, `Location`, `Router` and `NavigationHistoryService` — and three of them exist only for `goBack()`. Is that page doing too much?** ⭐⭐

The loading and favourite logic belong to it, but the Back policy does not: "go back if the app has history, otherwise go home" is navigation knowledge, and the page assembles it by hand from `canGoBack()`, `Location` and `Router`. I kept it in the page because it had a single consumer, and the cost is that a second screen with a Back button would copy three injections and the branch. The shape I would move to is a `back(fallback = '/')` method on `NavigationHistoryService` that holds `Location` and `Router` itself — the service already owns the count, so it is the natural owner of the decision that count exists for, and the page drops to one injection and one call.

**[04-meal-finder-145] Every dependency is a field — `private activatedRoute = inject(ActivatedRoute)` — never a constructor parameter, and the next field down is `queryTerm = toSignal(this.activatedRoute.queryParamMap…)`. Why `inject()`, and what does that ordering depend on?** ⭐⭐

Field initialisers run while the component is being constructed, which is an injection context, so `inject()` works there — and so does `toSignal()`, which needs one because it ties its subscription to the component's destruction; called from a click handler it would throw `NG0203`. I chose field injection because it lets derived fields such as `queryTerm` sit directly beside the dependency they read, leaving the constructor holding only the effect. The rule it imposes is declaration order: initialisers run top to bottom, so `queryTerm` above `activatedRoute` — or `favourites = this.favouriteService.favourites` above `favouriteService` in `FavouritesPage` — would read a field that does not exist yet, which TypeScript reports as used before its initialisation, while `computed()` fields are immune because they read nothing until first used.

**[04-meal-finder-146] The app is organised by kind — `components/`, `pages/`, `services/`, `models/` — with no `core/`, `shared/` or feature folders. Where does that layout stop working?** ⭐⭐

At four pages, two presentational components and three services, organising by kind keeps every file one folder away from every other, and the folder name states the rule: `components/` injects nothing, `pages/` are routed. It stops working when a feature spans all four folders — adding meal plans would scatter a page, a card, a service and a model across four places, and removing the feature means hunting through all of them. That is the point where I would switch to feature folders, `favourites/` holding its page, `CategoryFilter` and `FavouriteService`, with `shared/` for UI reused across features such as `MealCard` and `core/` for app-wide singletons such as `NavigationHistoryService` — the layout a consultancy codebase of any real size expects.

**[04-meal-finder-147] The landing route is `{ path: '', loadComponent: … }` with no `pathMatch: 'full'`, and `''` is a prefix of every URL. Why doesn't it swallow `/favourites` the way a `**` at the top of the array would?** ⭐

The default `pathMatch: 'prefix'` lets `''` match by consuming zero segments, but a route with no `children` only succeeds when nothing of the URL is left over, so on `/favourites` the leftover `favourites` segment makes the router abandon that match and try the next entry. `'full'` is what the *redirect* form needs — Angular's route validation rejects `{ path: '', redirectTo: … }` without an explicit `pathMatch`, because a prefix match there would redirect every URL — and I had no redirect to write, since the search page itself lives at `''`. I decided to leave the default rather than add `'full'` out of habit, and the day the empty path turns into a redirect is the day that option becomes mandatory.

**[04-meal-finder-148] Both `toSignal` calls pass an `initialValue` — `null` for the meal id, `''` for the query term — yet the router's `paramMap` emits on subscribe. When is that initial value ever read?** ⭐

Never, through this code: `ActivatedRoute` keeps its params in `BehaviorSubject`s and `toSignal` subscribes inside the field initialiser, so the current value replaces the initial one before the constructor's `effect` or the template reads the signal. I chose `initialValue` because it type-checks without thought, but it documents a state that never renders, and it is part of why the detail page carries `if (!id) return;` twice for a `null` the route does not deliver. `{ requireSync: true }` states the real contract instead: no invented starting value, and a thrown error at construction if the source ever stops emitting synchronously, so the assumption fails loudly rather than as a page that quietly shows nothing. The id would stay `string | null` either way, because that is what `paramMap.get` returns.

**[04-meal-finder-149] The loading spinner — its markup, `.spinner-container`, `.load-spinner` and a `@keyframes spin` — is written out in both `search-page` and `meal-detail-page`, and `.empty-message` in three page stylesheets. Why no shared loading component?** ⭐

I accepted the copy because the two spinners sit in different layouts — inside the result grid on the search page, where the container has to span every column, and inside a plain block on the detail page — so a shared `<app-loading-spinner>` would need each parent to size its host differently. The copies have already drifted, which is the argument against my choice: the detail page's `.load-spinner` still carries `grid-column: 1/-1` and `justify-self: center`, and its `.empty-message` a `grid-column` of its own, all dead declarations in a container that is not a grid. With two consumers I would now extract the spinner as a component whose `:host` centres itself and let each page place the host, and move `.empty-message` into `styles.css` beside `.page-title`, since it is the same text style everywhere it appears.

## Business Rules

**[04-meal-finder-046] An empty search is forbidden twice — `[disabled]="!searchTerm().trim()"` on the button and `if (!term) return;` inside `onSearchMeals()`. Why both, and which one is the actual rule?** ⭐⭐⭐

The guard in the handler is the rule; the disabled binding is only the part the user can see. `(keyup.enter)="onSearchMeals(meal.value)"` is wired to the input and not to the button, so a disabled button stops nothing when the term arrives by Enter, and a `disabled` attribute is a hint any other call site can bypass. I chose to put the single non-empty check where the navigation happens and let the binding mirror it, so the two can never disagree about what is submittable.

**[04-meal-finder-047] The term is trimmed twice: in `onSearchMeals()` before the navigate, and again in the effect as `this.queryTerm().trim()`. Isn't the second one dead code?** ⭐⭐

No, because the URL is an input the user controls directly: `/?q=%20%20`, typed or bookmarked or shared, never passes through `onSearchMeals()`, and without the second trim the effect would send `s=%20%20` to `search.php`. I chose the handler's trim to keep the URL canonical — `beef ` and `beef` produce the same `?q=beef`, which is also what makes a re-submit idempotent — and the effect's trim as the real enforcement point, because the effect is the only place a request is ever started.

**[04-meal-finder-048] Project 03 used reactive forms; this project's one input has no `FormControl`, no `Validators`, no `FormGroup`. Why was leaving them out the right call for this form?** ⭐⭐

The whole validation rule here is "the trimmed term is not empty", and the value's home is the URL rather than a form model — `?q=` is read back with `toSignal(queryParamMap)` and the effect is what runs on it. I decided a `ReactiveFormsModule` import, a control and a `valueChanges` subscription would add a second source of truth for one string beside the one the router already owns, and `Validators.required` would only give me an `ng-invalid` class I would then have to translate into `[disabled]` myself. I would reach for reactive forms the moment there are several fields, cross-field rules, or per-control error messages to render.

**[04-meal-finder-049] `(input)` writes `searchTerm` on every keystroke, but no request is made until Enter or the button. Why isn't this a search-as-you-type box?** ⭐⭐

Because a submit here is a `router.navigate()` with `queryParams: { q: term }`, so every keystroke would become a history entry and the back button would walk back through `?q=b`, `?q=be`, `?q=bee`. I chose explicit submit, which keeps one history entry per real search and one request per user intention; search-as-you-type would need `debounceTime` plus `replaceUrl: true` just to stop poisoning history, and MealDB's `search.php` has no prefix endpoint that would make the intermediate calls useful.

**[04-meal-finder-050] Press Search twice on the same term. How many requests reach MealDB, and what stops the second one?** ⭐⭐

One. The handler navigates to an identical URL and the router's default `onSameUrlNavigation: 'ignore'` drops it, so `queryParamMap` never emits again and the effect does not re-run; even if it did emit, `queryTerm` is a signal and its default `Object.is` equality would not notify on the same string. I chose the URL as the trigger partly for that reason — de-duplicating a repeated search is something the router does for free, where a plain `(click)="search()"` would have needed me to remember the last term and compare it by hand.

**[04-meal-finder-051] Backspace the search box to empty and the results stay on screen. Is that the bug it looks like, and when does the effect's empty-term branch actually run?** ⭐⭐

It is deliberate: clearing the box only writes `searchTerm`, and `onSearchMeals()` refuses to navigate on an empty term, so `?q=beef` and the results it produced are still the state of the page — nothing was searched, so nothing was unsearched. The branch that does `meals.set([])` and `hasSearched.set(false)` runs when the *URL* loses `q`: the first visit to `/`, the brand link in the nav bar, or the back button landing on a pre-search entry. I chose to let only the URL change the results, which is the same decision that refills the box from `?q=` on a shared link.

**[04-meal-finder-052] `hasSearched.set(true)` appears in the `error:` callback as well as in `next:`. Why does a failed search count as having searched?** ⭐⭐

Because `hasSearched` answers "has this page asked MealDB anything?", not "did it get results", and a failure must still clear the initial invitation: rendering "Search for a meal to get started" after a request blew up would tell the user nothing happened when something did. On that path the `hasError()` branch is what actually shows, so the flag pays off on the next search that succeeds with an empty list, and resetting it to `false` in the empty-term branch is what genuinely restores the initial state. I decided each flag should record an observation the template reads, rather than inferring state from `meals().length`.

**[04-meal-finder-053] On a second search the spinner replaces the previous results — `@if (isLoading())` wraps the whole grid — yet `meals` is never cleared. Why blank the screen instead of leaving the previous results visible?** ⭐⭐

I chose to blank it because the old list answers a different question: leaving "beef" results under a spinner that is fetching "pasta" invites a click on a card the user did not search for. `meals` is left alone only because nothing can read it while `isLoading()` holds and the next `next:` overwrites it, so clearing it would be a write no one observes. The cost is layout that jumps on every search; the alternative I would weigh is dimming the grid in place with `aria-busy`, which keeps the scroll position at the price of showing stale data.

**[04-meal-finder-054] Open `/detail/abc`. Nothing validates that id, and the `**` wildcard cannot catch it because `detail/:id` matches first. What does the user see, and where is the rule?** ⭐⭐⭐

Not "Meal not found.", which is what I expected: for a non-numeric id MealDB answers `200 {"meals": "Invalid ID"}` — a string where `MealResponse` promises `Meal[] | null` — so `response.meals?.[0] ?? null` indexes the string and hands the page `"I"`. The success branch then renders a recipe card with no image and a blank heading, and its star stores `"I"` in favourites as though it were a meal, once per click. The not-found branch only shows for a well-formed id that does not exist, such as `/detail/99999999`, which does come back as `{"meals": null}`; I still treat MealDB as the only authority on which ids exist, but its answer to a malformed one is not the shape I typed, so the rule belongs at the service boundary — `Array.isArray(response.meals) ? response.meals[0] ?? null : null` sends both cases to "Meal not found.". What I would keep is not redirecting to `NotFoundPage`: a wrong recipe id is a missing resource on a real page, not a URL the app has no route for.

**[04-meal-finder-055] The detail template's spinner branch is `@else if (!loadFinished())` — it never reads `isLoading()`. What state does that leave the screen in before any request has started?** ⭐⭐

Loading, which is the honest state for a page that is about to ask: `loadFinished` is false until a callback has run, so the first render shows the spinner instead of falling through to "Meal not found." before MealDB has been asked anything. It also means the `if (!id) return;` path would spin for ever — unreachable through this route table, since `detail/:id` cannot match an empty segment, so I left that guard as defence rather than as a state the screen has to render. The consequence is that `isLoading` on this page is written and never read, and I would delete it and keep the single `loadFinished` flag.

**[04-meal-finder-056] The favourite button on the detail page exists only inside the `@if (mealDetails() && loadFinished())` branch, and `toggleFavourite()` still re-checks `if (!id) return;`. What is each of those forbidding?** ⭐

The branch forbids favouriting a meal the app does not have: on the error and not-found screens there is no star, because storing a favourite means storing the whole `Meal` object and there would be nothing to store. The re-check inside the method guards the id the *store* is keyed by rather than the object being rendered, which matters because the router reuses this component instance across `/detail/:id` changes and the method reads `mealId()` fresh on every click. What I would change is the split that re-check belongs to: the star's state and the delete are keyed on the URL id while the add stores the loaded object, and those two ids are not guaranteed to be the same string.

**[04-meal-finder-057] `addFavourite` is `[...meals, meal]` with no duplicate check. What stops the same meal being stored twice?** ⭐⭐⭐

Nothing in the service — the rule lives in each caller: the search and detail pages ask `isFavourite()` first and route to `deleteFavourite` instead, and the favourites page only ever removes. I decided that was enough because the toggle is the only way in from the UI, but it is the wrong home for an invariant: one caller that adds unconditionally would put two identical entries in the array, and the favourites `@for ... track favourite.idMeal` would then trip Angular's duplicated-key error. The fix is to let the store own it — `if (this.favouriteIds().has(meal.idMeal)) return;` at the top of `addFavourite`, or holding the collection as a `Map<string, Meal>` so the shape cannot express a duplicate.

**[04-meal-finder-058] A favourite stores the whole `Meal` object in localStorage, not its id. What is stale a month later, and why not store ids and re-fetch?** ⭐⭐⭐

Everything `/favourites` and the card render — title, thumbnail, category — is the snapshot taken at the moment of the click, so a recipe MealDB later renames or re-photographs keeps its old values until the user removes and re-adds it. I chose the snapshot because it makes the favourites page render with zero requests, work offline, and never need a spinner or an error branch; ids would mean N lookups per visit, since `lookup.php` takes one `i` at a time and MealDB has no bulk endpoint. The tradeoff I accept is drift on data that is effectively static, and against a backend of my own I would store ids and serve the user's favourites in one call.

**[04-meal-finder-059] `FavouritesPage.toggleFavourite` calls `deleteFavourite` and, on the very next line, reads `filteredFavourites().length` to decide whether to reset `selectedCategory`. How can that read already see the deleted state, and why make the repair there rather than in an `effect()`?** ⭐⭐

Signal writes are synchronous: `_favourites.update(...)` has replaced the array before `deleteFavourite` returns, and that write only marks the `filteredFavourites` computed dirty, so reading it on the next line recomputes on the spot against the new list — no change-detection pass has to run in between, and the template never renders the intermediate state. I chose to repair the selection in the handler that emptied it, because removing a card is the only way this page can empty a filtered list, so the reset is a consequence of one user action rather than an invariant the page has to watch. An `effect(() => { if (filteredFavourites().length === 0) selectedCategory.set(''); })` is the form I would switch to the day favourites can change from outside the page — a `storage` listener pushing another tab's writes in, for instance — because then no handler would be there to make the repair.

**[04-meal-finder-060] `allCategories` recomputes after that delete, so the Dessert button vanishes on its own. Why touch `selectedCategory` at all?** ⭐⭐

Because the button disappearing does not clear the signal: `selectedCategory` would still hold `'Dessert'`, `filteredFavourites` would keep filtering against a category nothing has any more, and the remaining cards would stay hidden with no visible control left to undo it. The "All" button reads its own state as `selected() === ''`, so a dead value also leaves the filter row with nothing highlighted. I decided the derived list and the selection have to be repaired together, since only one of the two is derived.

**[04-meal-finder-061] `CategoryFilter` wraps only the "All" button in `@if (categories().length > 0)`. Why does the `@for` below it need no guard?** ⭐

Because `@for` over an empty array renders nothing by itself, while "All" is a literal in the template and would otherwise appear as a lone filter button on an empty favourites page — a control that filters nothing, sitting next to "No favourites found.". I chose to guard the one element that cannot guard itself, so the component's whole output is empty exactly when there is nothing to filter and the page never has to ask whether the filter has anything to show.

**[04-meal-finder-062] On the favourites page the card is given `[isFavourite]="true"` as a literal and the handler only calls `deleteFavourite`. What does that screen forbid, and what happens to the star the instant you click it?** ⭐⭐

Every card there is a favourite by construction, so the input is not a question worth asking the service, and removal is the only meaningful action — the screen cannot un-favourite and re-favourite, because the card unmounts the moment the signal loses that meal. The method is still called `toggleFavourite`, a name inherited from the search page and misleading here; `onRemoveFavourite` is what it actually does. The consequence I would raise in a review is that there is no undo: a mis-click is recoverable only by searching for the meal again, and a real version would hold the card in place with an "Undo" affordance for a few seconds.

**[04-meal-finder-063] The search term lives in the URL; the favourites category filter lives in a component signal that is lost on reload. How do you defend that asymmetry?** ⭐⭐⭐

A search is a result set worth sharing, linking and reaching with the back button, so `?q=` belongs in the address; the category filter is a momentary view of a list that is private to this browser anyway, and `?category=Dessert` would have to be validated against the user's own favourites on every load. I chose the URL only where the value has a reader outside this tab, which is the same reason the detail page takes its id from the route rather than from a shared signal. The honest counter is consistency — a reviewer can fairly say two adjacent screens now keep state two ways — and if the filter ever gained a shareable meaning I would move it into the query string rather than invent a third mechanism.

**[04-meal-finder-064] The nav badge is wrapped in `@if (favouritesNumber() > 0)` instead of rendering `0`. Why?** ⭐

A badge is a notification that something is there, so a "0" is noise that also takes layout on every page before the user has saved anything — the "Favourites" link already says where it goes. I chose to render the element only when it carries information, which also keeps the badge's existence and its value coming from the same `computed()` with no extra flag to keep in step.

**[04-meal-finder-065] The YouTube link is behind `@if (mealDetails()?.strYoutube)` although the surrounding branch has already proved the meal. What is that `@if` for, and what is the `?.` doing there?** ⭐⭐

MealDB sends `strYoutube: ""` for meals with no video and an empty string is falsy, so the `@if` is a truthiness test on the field rather than an existence test on the meal — without it the page would render an `<a href="">`, which navigates to the current URL when clicked. The `?.` is redundant inside a branch that already established `mealDetails()`, and it is there because the compiler cannot narrow across two separate signal reads; `@let meal = mealDetails()!` at the top of the block is how I would remove it along with the other `!`s. I decided the model should keep MealDB's own `string` type rather than `string | null`, so falsiness is the one test that field needs everywhere it is used.

**[04-meal-finder-066] That link is `target="_blank"` with no `rel`. What would a reviewer say, and does it still matter?** ⭐

The historical answer is `rel="noopener"`, because a `_blank` page could reach back through `window.opener` and navigate the tab it came from; current browsers imply `noopener` for `target="_blank"`, so that hole is closed by default rather than by this markup. What is not implied is `noreferrer`, so the YouTube target still receives this app's URL as the referrer. I would write `rel="noopener noreferrer"` anyway — it is the habit an interviewer is checking for, and it costs one attribute.

**[04-meal-finder-067] `filteredFavourites` compares `favourite.strCategory === this.selectedCategory()` with no trimming or case folding. Why is exact equality safe here?** ⭐

Because both sides come from the same objects: `allCategories` is `[...new Set(this.favourites().map(m => m.strCategory))]`, the filter emits one of exactly those strings back, and the comparison runs against the field they were read from. I chose to derive the options from the data instead of declaring a category list, so there is no second spelling of "Dessert" anywhere in the app for the comparison to miss. Normalisation would become necessary the moment the value could be typed — a `?category=` parameter, for instance, which is exactly what this filter deliberately does not have.

**[04-meal-finder-068] The favourites `@empty` block has one message, "No favourites found.", with no separate wording for "none in this category". Is that a gap?** ⭐

It is provable coverage rather than a gap: the only way to empty a filtered list is by removing its last card, and that handler resets `selectedCategory` to `''` in the same tick, so a rendered empty grid always means the user has no favourites at all. I decided one message was honest because the second state cannot be reached — and the day `selectedCategory` becomes persisted or URL-driven, that stops being true and the message has to split.

**[04-meal-finder-069] Nothing disables the Search button while a request is in flight, so a user can submit a second search before the first answers. Why is that not a race here?** ⭐

Because the request belongs to the effect rather than to the click: a new term changes `queryTerm`, the effect re-runs, and its `onCleanup` unsubscribes the previous `searchMeals` subscription before the new one starts, so a slow first response cannot overwrite a fast second one. A re-submit of the same term is ignored outright by the router, so the only way to submit twice is with a different term. I chose not to add an in-flight `[disabled]` because it would forbid something that is already correct, and it would leave the button dead for ever if a response never arrived.

**[04-meal-finder-070] Open the app in two tabs and favourite a different meal in each. What is in localStorage afterwards?** ⭐⭐

Whichever tab wrote last, with the other tab's addition gone: each tab reads `favourites` exactly once, in the service's field initialiser, and the persistence effect then writes its own whole array on every change. I decided against listening for the `storage` event because this is a single-user app with no sign-in and the failure needs two tabs open at the same time to appear at all. The fix has one shape either way — a `window.addEventListener('storage', …)` that pushes the parsed value back into `_favourites` — and it is what I would add the day favourites are worth more than a re-search.

**[04-meal-finder-071] The search effect's empty-term branch sets `meals` and `hasSearched` and returns — it touches neither `hasError` nor `isLoading`. Click the brand link once after a failed search, and once while a search is still in flight. What does `/` show each time?** ⭐⭐

Neither time the "Search for a meal to get started" invitation. After a failure, `hasError.set(false)` only runs on the path that is about to make a request, and the template tests `hasError()` ahead of the results branch, so "Something went wrong. Try again." outranks the invitation on a screen that has asked MealDB nothing. Mid-request it is worse: the change to `queryTerm` re-runs the effect, `onCleanup` unsubscribes the in-flight `searchMeals` — and an unsubscribe calls neither `next` nor `error` — so `isLoading` stays `true` and the spinner turns until the next search, as it also does when the browser's Back lands on `/` mid-request. I did not decide either — it is one bug, a branch that resets only part of the page's remote state; the immediate fix is `isLoading.set(false)` and `hasError.set(false)` in that branch, and the shape that would have prevented it is a single status signal (`'idle' | 'loading' | 'error' | 'loaded'`) whose idle assignment cannot forget a field.

**[04-meal-finder-072] A search fails and the user presses `Search Meal` again on the same term. Nothing happens — no spinner, no request. What swallows the retry, and how would you give it back?** ⭐⭐

The handler navigates to the URL that is already active, the router's default `onSameUrlNavigation: 'ignore'` drops that navigation, so `queryParamMap` never emits and the effect — the only thing in this page that starts a request — does not re-run. That is exactly the mechanism I chose for de-duplicating a repeated successful search, and the error path is where the choice costs: recovery for that same term is a reload or a different term, because the brand link only strands the user on the stale error state. I would add an explicit `Try again` control that calls `searchMeals` for the current term rather than loosen the router's dedupe, which would trade this bug for a duplicate request on every re-entry to the page.

**[04-meal-finder-073] "All" is encoded as `selectedCategory === ''` — not `null`, not a separate `showAll` flag. What does that buy, and what would break if MealDB ever sent a meal with an empty `strCategory`?** ⭐

The empty string keeps `filteredFavourites` to one ternary and lets `CategoryFilter` state its own highlight as `selected() === ''` through the same `input.required<string>()` it uses for a real category, so the child never has to model absence — that is why I chose it over `string | null` plus a second input. The cost is that "no filter" and "a category named the empty string" are the same value: such a meal would render an unlabelled filter button that looks permanently selected, and pressing it would show every favourite rather than that one. I decided that was safe because `allCategories` is derived from MealDB's own field and every recipe there carries a category, but a `null` sentinel is what I would use the day the list came from data I do not control.

**[04-meal-finder-074] In Safari's private mode, or once the origin's quota is full, `localStorage.setItem` throws. Star a meal there — what does the user see, and where does the failure go?** ⭐

The star turns on and the nav badge increments, because `addFavourite` has already written `_favourites` and the persistence `effect()` only runs after it; the throw happens inside the effect, so it reaches Angular's `ErrorHandler` and the console while nothing on screen contradicts what the user just saw. I chose a single effect as the home for persistence, and this is the one cost of that placement: the write is not part of the command, so there is nothing at the call site that could refuse the add or roll it back. The proportionate fix is a `try/catch` in the effect that shows "favourites can't be saved in this browser" once — the same guard the `JSON.parse` on the way in is also missing.

**[04-meal-finder-075] Type three spaces and press Enter. Nothing happens and the screen says nothing, while the button at least shows itself greyed out. Is silence the right feedback for a refused submit?** ⭐⭐

I decided it was, because the only invalid input here is a blank term and the box in front of the user already shows what is wrong; a message saying "enter something to search" would state what is visible and would then have to be cleared on the next keystroke. The asymmetry is the real defect: `[disabled]="!searchTerm().trim()"` makes the button's refusal visible, `(keyup.enter)` refuses invisibly, and a keyboard-only user meets only the invisible half. So what I would add is not an error but the always-present half of the rule — a hint beside the field, linked with `aria-describedby`, which tells a screen-reader user what the disabled button only tells the eye.

**[04-meal-finder-076] Search `beef`, open a card, then press the browser's Back button. Are the results still there, and what did that cost?** ⭐⭐

They are there, but they are new: the lazy route destroys `SearchPage` on the way out, so the instance that comes back has `meals` empty and `hasSearched` false, and the screen refills only because `?q=beef` is still in the URL and the effect fires on it — one fresh `search.php` call per return. I chose the URL as this page's memory precisely so restoring the screen needs no cache and no component reuse, and the price is a round trip the browser will spare me only if MealDB's own cache headers allow it, which I do not control. Keeping the last result set in `MealService` keyed by term is what I would do if that traffic mattered; at this size I decided one request was cheaper than a cache to invalidate.

**[04-meal-finder-150] Open `/detail/052772` — the Teriyaki Chicken Casserole's id with a leading zero — and press the star. What happens, and what happens on the second press?** ⭐

MealDB reads the id as a number and returns the casserole with `idMeal: "52772"`, but `isFavourite` is `favouriteIds().has(this.mealId())`, keyed on the URL's `"052772"`, so the star shows ☆ even when that meal is already saved. The press routes to `addFavourite(meal)`, which stores the loaded object under `"52772"`; the lookup still misses, the star stays ☆, and every further press appends another copy — the nav badge climbs and the delete branch can never be reached from that URL. The rule I broke is that the URL is what the page asked for while the response is what it got, so I would key the star's state and the delete on `mealDetails()?.idMeal`, and give `addFavourite` its own `has()` guard so no caller can reintroduce the duplicate.

**[04-meal-finder-151] The recipe branch is `@if (mealDetails() && loadFinished())`, and the `error:` callback runs `mealDetails.set(null)` although a fresh page already starts at `null`. What is that pair protecting against?** ⭐

A recipe on screen that is not the answer for the id in the URL. The router reuses this component when only `:id` changes, so on a move from `/detail/52772` to `/detail/52773` `mealDetails` still holds the first meal while the second loads: `loadFinished.set(false)` is what drops the old recipe to the spinner, and if the second request fails `loadFinished` turns true again, so without the `set(null)` the first recipe would reappear under the second URL — beside a star keyed on one id that would add the other meal. Nothing links one recipe to another today, so both lines are defence for the reuse `004` describes; I kept them because the failure they prevent shows wrong data rather than no data.

**[04-meal-finder-152] The detail page's failure message is "Could not load this meal. Go back and try again." and there is no retry control. Follow that advice — does it work, whichever way the user arrived?** ⭐⭐

From inside the app, yes: Back returns to the search page, and clicking the card again is a navigation from `''` to `detail/:id`, which builds a new `MealDetailPage` whose effect requests the meal afresh — unlike the search page, where retrying the same term is a same-URL navigation the router ignores (`072`). From a shared link or a bookmark it does not: `canGoBack()` is false, so the page's Back sends the user to a blank `/`, and getting back to the recipe now takes the browser's own Back button or a reload, neither of which the message mentions. I wrote copy that assumes the in-app path; the fix is a `Try again` button on this branch that re-runs the lookup for `mealId()` — the request moved into a method that both the effect and the button call — so recovery does not depend on how the user got there.

**[04-meal-finder-153] Every favourite is stored as the whole `Meal`, yet the detail page never reads that copy. Open a saved meal from the favourites page while offline — or one MealDB has since removed. What does the user get?** ⭐⭐

Offline, "Could not load this meal." for a recipe whose instructions, category and video link are sitting in `localStorage`, because `addFavourite` stores the object exactly as MealDB sent it; for a removed recipe, "Meal not found." — and since the star only exists in the success branch (`056`), that favourite cannot be removed from its own page, only from `/favourites`, where its card keeps pointing at a recipe that no longer exists. I chose one source for this page, the lookup by URL id, so it has a single code path and never passes off a snapshot as current data. The proportionate change keeps that and adds a fallback: on `error:` or a `null` result, read `favourites()` for the same id and render the saved copy with a "saved version" note, and render the remove star on the not-found branch whenever the id is still in `favouriteIds()`.

**[04-meal-finder-154] In what order do the favourite cards and the category buttons appear, and what happens to the buttons when you remove a favourite?** ⭐

Both follow save order: `addFavourite` appends, so the newest favourite is the last card, and `[...new Set(favourites().map(m => m.strCategory))]` lists each category where its first remaining favourite sits. With Beef, Dessert, Beef saved, removing the first Beef leaves Dessert, Beef, so the two buttons swap places under the user's pointer although no category appeared or disappeared. I never chose an order — I inherited insertion order — and a row of controls people click repeatedly should not move on its own; `.sort((a, b) => a.localeCompare(b))` on the derived list fixes it, with "All" staying first because it sits outside the `@for`.

**[04-meal-finder-155] Search `chicken`, then just `a`. How many cards does each return, and is that the whole answer?** ⭐

Exactly 25 both times: `search.php` on the free key stops at 25 matches, so a single letter that appears in far more than 25 meal names still returns 25, and even `%` comes back with 25, which says the server runs a loose substring match. The page renders `meals()` as if it were complete — no count, no "showing the first 25" — and the only outcomes the template knows are cards or "No meals found". I built it without knowing about the cap, so the decision I made by default is that a result list is whatever came back; now I would show the count and, when it is exactly 25, a line asking the user to refine the term, since the API returns no total to page through.

**[04-meal-finder-156] PLANNING.md and the README both promise "the full recipe" on the detail page. Where are the ingredients?** ⭐⭐

Not on the page, and not in the model either: MealDB sends them as forty flat columns — `strIngredient1`…`strIngredient20` and `strMeasure1`…`strMeasure20`, with unused slots as `""` or `null` — while my `Meal` interface declares seven fields, so the template only has the photo, category, area, instructions and video link to render. I did not decide to leave them out; I typed the model from what the first screens needed and never came back to it, so the page calls itself a recipe while showing the method without the list of what goes into it. The fix belongs at the service boundary rather than in the template: `getMealById` maps the numbered pairs into `ingredients: { name: string; measure: string }[]`, dropping the blank and `null` slots, and the page renders one `@for` over that. The columns are already inside every stored favourite, because `addFavourite` saves the parsed object exactly as MealDB sent it and an interface strips nothing at runtime — only the type pretends they are not there.

## Technical Decisions

**[04-meal-finder-077] This app keeps every piece of state in `signal()`s spread across three services and four pages — no NgRx, no `BehaviorSubject` store, not even one central state service. At what size does that stop being the right answer?** ⭐⭐⭐

The state here is three unrelated things — the favourites array with its `localStorage` invariant, a navigation count, and per-page remote state that the URL already keys — and none of them has two writers, so a store would add actions, reducers and selectors to solve a coordination problem this app does not have. I chose signals because the one genuinely shared piece, `FavouriteService._favourites`, needs exactly the two properties a store would also give it — a single writer surface through `asReadonly()` and derived reads through `favouriteIds` — and gets them in twelve lines with no library. It stops being the right answer when two features write the same state for different reasons, or when I need effects and time-travel for optimistic updates and rollback; with a read-only public API and one user, neither is true here.

**[04-meal-finder-078] `SearchPage` holds `meals`, `hasSearched`, `isLoading` and `hasError` as four independent signals, and the detail page holds four of its own. Angular 21 ships `resource()` and `httpResource()`, which carry exactly that as one value. Why is the state hand-rolled?** ⭐⭐⭐

I hand-rolled it because `effect()` plus a subscription was the pattern this project set out to learn, and the four independent flags are the honest cost of that shape: a combination the screen should never show — a failure flag left true on a page that has asked MealDB nothing — is representable in four booleans, and it does in fact occur. A `resource()` keyed on `queryTerm` would give me `value`, `status` and `error` as one value with cancellation on re-key built in, so the impossible combinations would stop being expressible, and that is what I would reach for now; when I wrote this, those APIs were still marked experimental, which is why the project's core loading path is not built on them. What I would not change is where the state lives — keyed off the URL, owned by the page — because that is the property that makes both screens linkable.

**[04-meal-finder-079] Your search `effect()` writes five signals — `searchTerm`, `meals`, `hasSearched`, `isLoading`, `hasError` — and Angular no longer asks you for `allowSignalWrites`. What stops it from re-running itself for ever?** ⭐⭐

Dependency tracking is by read, never by write: the only signal the effect reads is `queryTerm()`, so those five `set()` calls create no dependency and the effect re-runs only when the URL's `q` changes. I decided to keep every write in that effect one-directional for exactly that reason — the moment it reads one of the signals it writes, say an `if (this.meals().length)` guard, it becomes its own trigger and loops, and the escape hatch would be `untracked()` around that read. It is also what makes `this.searchTerm.set(term)` safe inside the loading effect even though the input box's own `(input)` handler writes the same signal: the effect writes it and never reads it back.

**[04-meal-finder-080] `FavouriteService` reads `localStorage.getItem('favourites')` in a field initialiser and writes it back from an `effect()`. Why `localStorage` rather than `sessionStorage` or IndexedDB, given that the nav badge has to be right on the first paint?** ⭐

`sessionStorage` dies with the tab, and a favourite that disappears when the browser closes is not a favourite — the whole feature is a promise that outlives one session, so that rules it out on behaviour rather than on taste. I chose `localStorage` over IndexedDB because its API is synchronous, which is precisely what lets the service read it in the field initialiser and have the nav badge correct on the very first paint; an IndexedDB read is a promise, so the first render would show nothing and then correct itself. The costs I accept are the origin's ~5MB quota and a blocking main-thread write on every change, neither of which a personal list of recipe cards can reach.

**[04-meal-finder-081] The storage key is the bare string `'favourites'`, with no app prefix and no schema version. What does that cost the day the `Meal` interface gains a field?** ⭐⭐

Nothing on write and everything on read: the service parses whatever sits under that key straight into `signal<Meal[]>` with no validation, so objects stored before the new field come back missing it while TypeScript insists they have it — a `strYoutube` that is `undefined` behind a `string` type, which then reaches a template. I decided one hardcoded key was proportionate for an app with a single stored shape, and the fix a real app carries is a pair: a namespaced, versioned key such as `meal-finder:favourites:v1`, so a shape change becomes a new key instead of a silent migration, plus the `try/catch` the parse is also missing. The prefix earns its keep for a second reason — every app served from the same origin shares that store, and every project in this roadmap is served from `localhost:4200`, so an unprefixed `favourites` is one name collision away from reading somebody else's data.

**[04-meal-finder-082] `index.html` carries `<base href="/">` and `provideRouter(routes)` takes no `withHashLocation()`, so `/detail/52772` is a real path. What happens when a static host receives a request for it?** ⭐⭐⭐

With the default `PathLocationStrategy` the router rewrites URLs through the History API, so a deep link only reaches Angular if the server answers an unknown path with `index.html` — on a static host without that rewrite, a refresh or a shared `/detail/52772` returns the host's own 404 and the application never boots. I chose real paths because the detail page's entire justification is that its URL is the page's only input, and `withHashLocation()` would make `#/detail/52772` work on any host with zero configuration at the price of a URL that looks like 2012 and a fragment the server never sees. The decision therefore has a deployment half that lives outside the code, and this repository does not carry it: there is no SPA fallback file in the project, which is what I would add before calling a deploy of it finished.

**[04-meal-finder-083] Both pages read the URL by hand with `toSignal(activatedRoute.paramMap…)`. `provideRouter` has a `withComponentInputBinding()` feature that would hand those values to an `input()` instead. Why is it not enabled?** ⭐⭐

With that feature on, `MealDetailPage` would declare `id = input<string>()` and the router would keep it in step with the `:id` segment, which removes the `toSignal` + `map` + `initialValue` ceremony from both pages. I did not enable it because reading `ActivatedRoute` explicitly is this project's stated learning objective — I wanted the projection from observable to signal visible in the class rather than performed for me by a provider I would then have to explain. The tradeoff I would name in an interview is that the hand-rolled version is three lines per page the router does for free — and that neither version fails loudly when the param is renamed: the router sets every input it has no value for to `undefined`, so even `id = input.required<string>()` would hold `undefined` behind a `string` type, while `paramMap.get('id')` at least returns an honest `string | null` that forces the `if (!id) return` guard.

**[04-meal-finder-084] Every search calls `router.navigate` with no `replaceUrl`, so each term becomes a new history entry. Search three terms, then press Back three times — is that what you wanted?** ⭐⭐

It is: each search is a place the user has been, so Back stepping `pasta` → `chicken` → `beef` and only then leaving the app is what a URL-as-state design should do, and it costs nothing to implement because the term already lives in `?q=`. The price is that each of those steps re-fires the effect and re-requests MealDB, since the page keeps no cache; `replaceUrl: true` would collapse a whole session of searching into one entry and make a single Back leave the site, which I decided was the worse behaviour. Where I would reverse that call is a search-as-you-type box, because then every keystroke would push an entry and replacing becomes the only sane option.

**[04-meal-finder-085] `provideRouter(routes)` is bare — no `withInMemoryScrolling()`. Scroll to the bottom of a long result grid and open a card: where does the detail page start?** ⭐

Wherever the previous page was, because the router does not touch scroll position unless asked — a navigation from halfway down a `beef` grid lands on a detail page already scrolled past its own title. I left it out because nothing in the project's steps called for it, and the forward half is one feature flag: `withInMemoryScrolling({ scrollPositionRestoration: 'enabled' })` scrolls every new page to the top. The backward half is the gotcha — the same option restores the old offset when the user returns to the grid, but it restores it right after the navigation ends, and this search page re-requests its results at that moment, so the page is only a spinner tall and the restore is clamped near the top; making Back land on the card again means caching the results or calling `ViewportScroller.scrollToPosition` myself once they have rendered.

**[04-meal-finder-086] `package.json` has no `zone.js` and `angular.json` declares no polyfills, so this app runs zoneless. What actually schedules a change-detection pass, and what class of code would silently stop updating the screen?** ⭐⭐⭐

Nothing monkey-patches `setTimeout`, `addEventListener` or `XMLHttpRequest` any more, so the framework is notified by a fixed, declared set of things: a template event binding firing, a signal read in a template changing, `AsyncPipe` or `toSignal` emitting, and an explicit `markForCheck`. That is the real reason every asynchronous result in this app lands in a signal — `meals.set(...)` inside the subscribe callback, `toSignal` for the route params — and why code that mutated a plain class field from a `setTimeout` or a bare `.subscribe()` would update the object and never repaint. I decided the signal discipline was worth keeping strictly for that reason rather than for speed: under `zone.js` the same code appears to work by accident, so the zoneless build is what proves the reactivity is actually declared rather than stumbled into.

**[04-meal-finder-087] Not one component in this project declares `changeDetection: ChangeDetectionStrategy.OnPush`. In a codebase this signal-heavy, how do you defend that?** ⭐⭐

Zoneless removed part of what `OnPush` guards against — nothing outside Angular's own listeners and signals schedules a pass any more — but it did not make the two strategies equal: a tick still refreshes every `Default` component below a dirty ancestor, so each keystroke in the search box, whose `(input)` listener marks the page and the shell dirty, re-evaluates the bindings of every `MealCard` in the grid, where `OnPush` would skip each card whose inputs kept the same value. I decided against the annotation because at MealDB's result sizes that is a few dozen cheap bindings no profiler would show, and it would not touch the binding that looks expensive: `isFavourite(meal.idMeal)` sits in `SearchPage`'s own template, and that page is dirty on every keystroke under either strategy because the listener is its own. Where I would write it without thinking is a component with non-signal `@Input()`s or with object mutation, because there `OnPush` is the contract that forbids the mutation rather than a performance hint.

**[04-meal-finder-088] `@for (meal of meals(); track meal.idMeal)` in the grids, `track category` in the filter. What does the tracking expression actually change, and what breaks if I put `$index` in both?** ⭐⭐

`track` is how Angular matches items of the new list to the DOM nodes of the old one: with `idMeal`, removing a favourite destroys exactly that card and moves the rest, while with `$index` the nodes stay where they are and every card after the hole is re-bound to a different meal — correct in the end, but every image below the removal reloads its `src`, and anything living in a node stays with the position rather than the meal: remove a favourite with the keyboard and focus is left on a star that now belongs to the next meal, so a second Enter removes that one too. I chose the meal id because it is a stable identifier the server gives me, and `track category` in the filter because there the string *is* the identity — the list comes from `[...new Set(...)]`, so the values are unique by construction and there is nothing else to track by. `$index` is only right for a list that is append-only or whose items have no identity at all.

**[04-meal-finder-089] `handleFailure` does two things to one failure: `console.error` with the real error, then `throwError(() => new Error('Could not …'))`. Why log *and* rethrow rather than one or the other?** ⭐⭐

They serve two different readers: the `console.error` keeps the status code, the URL and the stack, which is the only thing that tells *me* why it failed, while the rethrown `Error` carries the sentence a page can put on screen, so nothing downstream has to work out which half it is holding. I chose to log at that boundary and nowhere else because the page's `error:` callback handles the failure, which means it never reaches Angular's `ErrorHandler` — had the service not logged it, the transport detail would be gone for good. The limitation I would name is that `console.error` is this app's entire observability and it ships to production untouched: a real deployment swaps that line for an injected logger, or moves it into an `HttpInterceptor` that does it once for every request, which is also where a retry or a correlation id would belong.

**[04-meal-finder-090] Both meal images carry `alt=""` — an empty alt, not a missing one. Is a photograph of the dish really decorative?** ⭐⭐

An empty alt tells a screen reader to skip the image, and I chose it because in both places the name is already adjacent text the user gets anyway: in the card the `<img>` sits inside the same `<a>` as `{{ meal().strMeal }}`, so an alt repeating the title would announce the same dish twice on one link, and on the detail page the `<h1>` immediately above does that job. The decision is deliberate rather than a forgotten attribute — an `<img>` with no `alt` at all leaves assistive technology reading out a CDN filename, which is the worst of the three options. What I would concede is that the photo is not purely decorative on the detail page, where it is the recipe's only visual content: an alt describing the plated dish would add something the heading does not, so the empty alt there is a judgement about noise, not a claim that the image says nothing.

**[04-meal-finder-091] A whole result grid of remote MealDB photos renders as bare `<img [src]>` — no `width`, no `height`, no `loading="lazy"`, no `NgOptimizedImage`. What does a user on a slow connection see?** ⭐

Every image starts downloading at once and each one occupies zero height until its bytes arrive, so the cards grow as responses land and whatever is under the cursor jumps — the layout shift Core Web Vitals measures as CLS. I chose the plain tag because the intrinsic sizes come from a third-party CDN I do not control and `NgOptimizedImage` refuses to render without `width` and `height` (or `fill`), which I would have had to guess for every thumbnail; the cheap two thirds of the fix needs no directive at all, which is `width`/`height` attributes to reserve the box and `loading="lazy"` on everything below the fold. That is a defect I would fix rather than defend, and the only reason it stays invisible here is that MealDB's thumbnails are small and the grid is short.

**[04-meal-finder-092] PLANNING.md pins the stack as "signals-based, no Angular Material", and every surface here is hand-written CSS over custom properties in `:root`. Why not the component library the next project uses?** ⭐⭐

The screens this app needs are a search box, a card grid, a filter row and a detail panel — none of them a data table, a dialog or a date picker, which is where Material earns its bundle and its theming layer — so I decided the library would cost me size and a new API and buy nothing this UI actually needs. I chose custom properties in `styles.css` instead, so colour is declared once and every component stylesheet reads a token rather than a literal, which is the same discipline Material's theming enforces at a fraction of the weight. Project 05 is deliberately the opposite experiment — the same class of problem built on `MatTable` and `MatDialog` — so that I can say what each approach costs instead of only defending the one I happened to use.

**[04-meal-finder-093] Every model import is `import type { Meal }`, while the services and the router come in as ordinary imports. What does the `type` keyword buy, given `isolatedModules: true` in `tsconfig.json`?** ⭐

It states that the import is erased at compile time, so nothing importing `meal.model.ts` emits a runtime `import` for a file that contains only interfaces, and no module edge exists where there is no value to fetch. I chose the explicit form because `isolatedModules` makes the compiler transpile each file on its own — it cannot look inside `meal.model.ts` to discover that `Meal` is only a type — so the keyword is what turns "probably elided" into a guarantee, and at the import site it documents that the symbol can never be used as a value. The ordinary imports are the other half of the same statement: `MealService` and `HttpClient` are there because the injector needs them at runtime.

**[04-meal-finder-094] Every route is `loadComponent()` and `provideRouter(routes)` takes no `withPreloading()`. So when is the favourites chunk actually fetched, and what would `PreloadAllModules` change for a user who searches once and then clicks Favourites?** ⭐⭐

With no strategy the default is `NoPreloading`, so a page's chunk is requested only when its navigation starts — and because the router activates nothing until that chunk has arrived, the user clicks Favourites and stays on the search page with no sign that anything happened, on a slow connection long enough to click again, even though the app sat idle for a minute beforehand. I decided against a strategy because there are four small page chunks and `PreloadAllModules` would pull every one of them down on the first idle moment: it keeps the smaller first paint, but spends the bandwidth the split was saving on users who never leave the search page. What I would reach for if the pages grew is a custom `PreloadingStrategy` that preloads `favourites` alone, since the nav bar advertises that route on every screen and it is therefore the one a user is most likely to click next.

**[04-meal-finder-095] `index.html` sets `<title>04MealFinder</title>` and no route declares a `title`, so the search screen, a recipe and the 404 all share the scaffold's value. For an app whose whole design is that `/detail/52772` is shareable, what does that cost?** ⭐⭐

The tab, the bookmark and every entry in the browser's history list read `04MealFinder`, so the one screen actually worth sharing is the one that identifies itself worst — and a chat client's link preview would keep showing it even after a fix, because a preview bot reads the raw `index.html` and never runs the router. Angular offers two fixes and only one of them fits the detail page: a static `title` per route, which the built-in `TitleStrategy` applies on every navigation, or `Title.setTitle()` from the page once the response has landed, which is the only one that can say `Teriyaki Chicken Casserole` because the name is not known until then. I left the scaffold's value because no step called for it, and it is the cheapest real improvement left in the routing config.

**[04-meal-finder-096] `this.http.get<MealResponse>(...)` carries a generic, and every field of `Meal` is a required `string`. What does that generic actually guarantee at runtime, and what happens the day MealDB omits a field?** ⭐⭐

Nothing at runtime: the generic is a compile-time label on parsed JSON, so `HttpClient` hands over whatever the API sent and the compiler believes me — `strictTemplates` then type-checks both templates against a shape nobody verified. If `strYoutube` or `strArea` came back absent, `mealDetails()!.strArea` would interpolate `undefined` into the detail panel and TypeScript would still insist the field is a `string`, because the only optionality I modelled is `meals: Meal[] | null`, which is the one case the API documents. I chose the cast knowingly rather than a validation step per endpoint — a `zod` schema or a hand-written type guard — because MealDB is a fixed public API with seven fields I use; the honest statement is that `Meal` describes what I expect to receive, not what anything checks, and the same hole exists at the `JSON.parse` that restores favourites.

**[04-meal-finder-097] This app is client-rendered only — `bootstrapApplication` in `main.ts`, no `provideClientHydration`, no server target in `angular.json`, no prerendering. For an app that exists to be linked to, how do you defend that?** ⭐⭐

A crawler or a link-preview bot that fetches `/detail/52772` receives `<app-root></app-root>` and nothing else, because the title, the photo and the instructions only appear after the framework boots, the route chunk loads and MealDB answers — and with JavaScript disabled there is no page at all. I chose CSR because the project's objective was `ActivatedRoute` and `effect()`, and server rendering would have moved the fetch into a server I was not building while crashing the render outright: `FavouriteService` reads `localStorage` in a field initialiser, the shell injects it, and `localStorage` does not exist on a server. If reach ever mattered more than practice, the proportionate step is not full SSR but prerendering the two static routes and adding hydration, leaving the id-keyed detail page client-fetched — after moving that read behind a browser-only check, since every route renders the shell and would hit it at build time.

**[04-meal-finder-098] The 2 → 3 → 4 column grid is declared twice, with the same two breakpoints, in `search-page.css` and again in `favourites-page.css`. Why duplicate it instead of sharing one class, and why hand-written breakpoints rather than `repeat(auto-fill, minmax(...))`?** ⭐

The two grids are identical by taste rather than by contract — one is a result set, the other a saved list — and with component-scoped styles the only places to share a layout rule are a global `.card-grid` class in `styles.css`, next to the colour tokens that are deliberately the only global thing, or a wrapper component created purely for a `display: grid`. I decided the duplication was cheaper than either at two call sites and that I would revisit it at three. The breakpoints are hand-written because I wanted to choose the column counts rather than derive them from a card width, but `repeat(auto-fill, minmax(220px, 1fr))` is the better rule for this layout: it needs no media query and responds to the container instead of the viewport, which is what a card grid actually wants.

**[04-meal-finder-099] Every user-facing string — `Search Meal`, `No meals found`, `Something went wrong. Try again.` — is hardcoded English in a template, and two more are built in TypeScript, in `MealService` and in `favouriteLabel`. What would adding Spanish cost from here?** ⭐

Each template string has to be found by hand and marked with an `i18n` attribute, and the ones that are not in a template cannot be marked that way at all: the `Error('Could not …')` messages `MealService` composes and the `favouriteLabel` computed that builds `Remove ${name} from favourites` would need `$localize` or a move into the template. I chose plain strings because the app has one audience and `@angular/localize` adds a build configuration and a bundle per locale, which is a lot of machinery for a portfolio project with four screens. The part I would change even while staying monolingual is where the text lives — the interpolated aria-label is proof that user-facing copy had already leaked out of the templates into the class, which is the expensive half of any later translation.

**[04-meal-finder-157] `FavouriteService`'s persistence `effect()` lives in a root service. When does it actually write — how many `setItem` calls does loading the app cause, and how many does removing two favourites in one handler cause?** ⭐⭐

An effect is scheduled, not synchronous: a signal write only marks it dirty, and a root effect runs on the next application tick, before the component tree is checked. So loading the app writes once — the first run is unconditional and stores back the array the field initialiser has just parsed, creating `[]` on a first visit — and two `update()` calls in the same handler collapse into one run that serialises the final array. I chose the effect partly for that: persistence follows the settled state rather than every intermediate one. The consequence is that storage lags the signal by one tick, so a test that calls `addFavourite` and reads `localStorage` on the next line sees the old value unless it flushes effects first with `TestBed.tick()`.

**[04-meal-finder-158] Open a shared `/?q=beef` link cold. The page is constructed with `isLoading` false and `meals` empty — does the user see "Search for a meal to get started" flash before the spinner?** ⭐⭐

No. `queryTerm` already holds `beef` when the component is constructed, and an `effect()` created in a component runs during change detection as part of that component, before its template is refreshed — so `isLoading.set(true)` has already happened when the view renders for the first time, and the first paint is the spinner with `beef` in the box. I relied on that timing rather than seeding `isLoading` from the URL in a field initialiser, which would have been a second place deciding what the page is doing. Had I started the request from a hook that runs after the view is checked, such as `ngAfterViewInit`, the first check would render the invitation and a second pass would have to correct it.

**[04-meal-finder-159] The search effect copies the URL into the box with `this.searchTerm.set(term)`, while `(input)` writes the same signal. Angular's guidance is not to use effects to propagate state from one signal into another. What would you write instead?** ⭐⭐

`searchTerm = linkedSignal(() => this.queryTerm().trim())` — a signal derived from `queryTerm` that resets whenever the URL's `q` changes and yet stays writable, so `(input)="searchTerm.set(meal.value)"` keeps working unchanged. That removes the one line of the effect that is not about fetching, and it makes the relationship declarative: the field's own declaration says where its value comes from, instead of a write buried in a constructor. The behaviour is identical — typing still diverges from the URL until the next submit, and a new `q` still overwrites what was typed — and I used the effect because this project set out to learn `effect()`, not because it was the better tool for that line.

**[04-meal-finder-160] Every page is a lazy chunk with a hashed filename (`outputHashing: "all"`). You redeploy while a user still has the old tab open, and they click Favourites. What happens, and who hears about it?** ⭐⭐

The old bundle asks for the old `favourites-page` chunk name, which the new deploy no longer serves, so the dynamic `import()` fails, the router emits `NavigationError`, and the click appears to do nothing — the user stays on the search page with no message. Nothing in the app handles that: `provideRouter` has no `withNavigationErrorHandler()`, and both `router.navigate()` calls discard the promise they return, so a failed programmatic navigation becomes an unhandled rejection that `provideBrowserGlobalErrorListeners()` only logs. I accepted it because lazy loading was worth having and the window is short, but the standard fix is small: a navigation error handler that recognises a failed dynamic import and calls `window.location.assign(error.url)`, so the browser fetches the new `index.html` and the user lands where they clicked.

**[04-meal-finder-161] `canGoBack` is `navigations() > 1`. Open `/detail/52772` from a bookmark, click Favourites, press the browser's Back, then press the page's own Back button. Where does the user end up?** ⭐⭐

Outside the app. The browser's Back is a `popstate` navigation that still ends in `NavigationEnd`, so the count is 3 while the user is back on the entry they opened directly: `canGoBack()` is true, `location.back()` runs, and the entry behind a bookmark belongs to whatever was open before. The count measures how many navigations happened, not how deep the current entry sits in this app's history, and the two diverge the first time the user goes backwards. I chose the counter because it is a few lines; the version that answers the real question keys on the entry itself — the router stamps each history entry it creates with a `navigationId` in `history.state` and hands it back as `restoredState` on `popstate`, so the directly opened entry can be recognised as the first one however the user returns to it.

**[04-meal-finder-162] The base URL is `https://www.themealdb.com/api/json/v1/1`, and that trailing `1` is MealDB's API key, committed in source. Is that a hardcoded secret, and would an `environment.ts` have fixed it?** ⭐⭐

It is a key but not a secret: `1` is the public test key MealDB documents for development and educational use, so publishing it discloses nothing. The half worth defending is the second one — an `environment.ts` would not have hidden a real key either, because it is compiled into the JavaScript the browser downloads, and the key would also sit in every request in the Network tab. I decided the test key in a service field was honest for a portfolio project; a paid production key would have to leave the browser altogether, behind a small server or a Netlify function that adds it to the upstream call, because anything shipped to a single-page app is public by construction.

**[04-meal-finder-163] `MealService` pipes `map` and `catchError` but no `timeout`. A request that never answers — a stalled connection, a captive portal — what does the search page show?** ⭐

The spinner, indefinitely: `catchError` only runs when the observable errors, and a request that simply hangs never does, so neither subscribe callback runs and `isLoading` stays true until the browser itself gives up, which `fetch` does not do on any short schedule. I left it out because MealDB answers quickly and I never saw it hang, but it is the one failure the page's error branch cannot reach. The fix belongs where the rest of the failure policy already lives: `timeout(10_000)` ahead of `handleFailure` in both pipelines, so the resulting `TimeoutError` goes through the same translation and lands on the existing error branch with no change to either page.

**[04-meal-finder-164] `angular.json`'s production configuration carries budgets — 500kB warning and 1MB error for the initial bundle, 4kB and 8kB for any component stylesheet. What do they actually enforce in this project?** ⭐

They are the CLI's defaults and I kept them, but they are the only size check that can fail a build here: `ng build` defaults to the production configuration, so crossing an error threshold fails the Netlify deploy itself. The initial budget measures what loads before any route resolves, which is where lazy-loading every page pays off — a page that imported a heavy library would grow its own chunk, not that number. The component-style budget exists because each component's CSS is compiled into its JavaScript rather than into a shared stylesheet; the gotcha is that nothing here measures the lazy chunks at all, which an `anyScript` or `bundle` budget would.

**[04-meal-finder-165] `allCategories` returns a new array and `favouriteIds` a new `Set` every time the favourites change — even when removing one of two Beef favourites leaves the categories exactly as they were. What does that reference change cost, and would you add an `equal` function?** ⭐

A `computed` notifies whenever its result is not `Object.is`-equal to the previous one, so a fresh array always counts as a change: `CategoryFilter` receives a new `categories` input and is re-checked, and on the search page every card's `isFavourite(...)` call re-runs against the new `Set`. Nothing visible happens, because `track category` and `track meal.idMeal` match the new items to the existing DOM, so the cost is a handful of comparisons on a personal list. I decided against `computed(() => …, { equal: (a, b) => a.length === b.length && a.every((c, i) => c === b[i]) })`, because a custom comparator is logic that can be wrong and would buy nothing measurable here; it earns its place when a derived value feeds something expensive, such as a chart redraw or a request.

**[04-meal-finder-166] `tsconfig.json` keeps the CLI's `strictTemplates: true`. In `(favouriteToggled)="toggleFavourite($event)"` and `(click)="onSearchMeals(meal.value)"`, what is the compiler checking that it would not check without that flag?** ⭐

Without it, `$event` from a component output and a template reference such as `#meal` are both typed `any`, so `toggleFavourite($event)` would compile against an output that emitted a `string`, and a typo such as `meal.valu` would ship as a runtime `undefined` instead of failing the build. With it, `$event` takes the type of `output<Meal>()` or `output<string>()`, `#meal` is an `HTMLInputElement`, and every `[meal]` and `[isFavourite]` binding is checked for assignability to its `input.required<…>()`, so handing the card a `Set` where it expects a boolean fails `ng build`. I kept the CLI default because the components in this project talk only through inputs and outputs, which makes the templates the place those contracts are wired together — and without the flag they are the place the compiler checks least.

**[04-meal-finder-167] The README lists "`subscribe` inside an `effect()` over the `async` pipe" as a tradeoff. Write the other side for the search page — the results as one stream — and what do the four state signals turn into?** ⭐⭐

The source is already a stream, so no effect is needed: `queryParamMap.pipe(map(p => p.get('q')?.trim() ?? ''), switchMap(term => …))`, read with `toSignal` or the `async` pipe, where `switchMap` does the cancellation my `onCleanup` does by hand. The price is that `isLoading`, `hasError` and `hasSearched` can no longer be `set()` from callbacks — they have to travel through the stream as values, so each term maps to `searchMeals(term).pipe(map(meals => ({ status: 'done', meals })), catchError(() => of({ status: 'error' })), startWith({ status: 'loading' }))` and the template switches on one `status`. The gotcha is where that `catchError` sits: on the inner request, because on the outer stream one failed search completes the whole pipeline and the page never searches again. I chose the effect because `effect()` was this project's objective and four named signals read plainly to someone new to RxJS; what the stream would have bought is that one emitted object cannot say "loading" and "failed" at once, which four independent booleans can.

**[04-meal-finder-168] The README trades "server-side filtering and a dataset I could extend" for a key-less API, and "Search by ingredient" is the first future improvement. What would MealDB's API make that feature cost in this codebase?** ⭐⭐

MealDB's `search.php` matches meal names only, and its ingredient endpoint, `filter.php?i=`, returns a reduced record — `idMeal`, `strMeal` and `strMealThumb`, nothing else. The cards would render fine from that, but `http.get<MealResponse>` would still type the result as a full `Meal`, so starring one of those cards would store a favourite with no `strCategory`, and the favourites page's category filter would render a blank button for it without a single compiler complaint. I chose MealDB because it needs no key and no account, which keeps the repository a one-command clone-and-run; the honest cost is that the provider's endpoint shapes decide my features, so ingredient search means either a `lookup.php` call per result before it can be starred, or a separate `MealSummary` type that the card accepts and `addFavourite` refuses.

## Testing

**[04-meal-finder-100] PLANNING.md's Testing section says authored tests begin at project 07 and that this project deliberately writes none — yet there are eight `.spec.ts` files and `ng test` has to pass. How do you defend both halves of that at once?** ⭐⭐⭐

The two halves answer different questions: what I was learning here was `ActivatedRoute`, `effect()` and signal inputs, so I decided to spend the project's budget there and start authored tests at 07, where the stack itself changes, rather than half-learn TestBed in parallel. What I would not accept is a suite that does not run, because `ng test` is part of a clone-and-run: a reviewer who clones this repo and gets a red or non-compiling suite learns that the repo is not maintained, which is a worse signal than a thin one. So the eight files are the CLI's own scaffolds kept compiling and green, each providing exactly what its unit injects — that is the whole claim, and I chose to state it in PLANNING.md rather than let someone infer coverage from a file count.

**[04-meal-finder-101] Five of those eight specs assert nothing but `expect(component).toBeTruthy()`. That is the textbook example of a test that always passes. Why keep them instead of deleting them?** ⭐⭐⭐

Because `toBeTruthy()` is not what the test exercises — everything before it is. `TestBed.createComponent` has to compile the template, resolve every directive in the component's own `imports` and satisfy every injection: drop `provideHttpClient` from `search-page.spec.ts` and it throws `NullInjectorError` for `HttpClient`, a template typo fails the compile, and a required input left unset throws when the first change detection reads it. So I keep them as a wiring smoke test, which catches the whole class of "I refactored a provider and forgot a page" — a mistake this app can make in five places. What I will not claim is that they test behaviour: they assert no rule, no branch and no output, and I say so rather than let eight spec files read as coverage.

**[04-meal-finder-102] In 2026 most large consultancies treat "no tests" as a hard filter. You documented not testing as a decision. What should I conclude from that as your interviewer?** ⭐⭐⭐

That I know the difference between a gap and a hidden gap. **[04-meal-finder-103] Three specs carry a hand-written assertion — the favourite label in `meal-card.spec.ts`, the pressed category in `category-filter.spec.ts`, and the nav-shell brand text in `app.spec.ts`. Out of everything this app does, why those three and nothing else?** ⭐⭐⭐

**[04-meal-finder-104] The meal-card test asserts `component.favouriteLabel()` — a class member — not the `aria-label` the browser actually reads. What does that assertion fail to prove?** ⭐⭐

**[04-meal-finder-106] That test collects every pressed button into an array and asserts `toEqual(['All'])`, then `toEqual(['Dessert'])`. Why array equality rather than just checking the right button is pressed?** ⭐⭐

**[04-meal-finder-107] Two component specs — `meal-card.spec.ts` and `category-filter.spec.ts` — call `fixture.componentRef.setInput(...)` before the first `await fixture.whenStable()`; the other four components take no inputs, so nothing in their specs calls it at all. **[04-meal-finder-108] There is no `detectChanges()` anywhere in these specs — every component spec that renders awaits `fixture.whenStable()` instead. Why, and what would go wrong if I put the `detectChanges()` calls back?** ⭐⭐

**[04-meal-finder-109] Two of the three authored tests — `meal-card.spec.ts` and `category-filter.spec.ts` — mutate an input on the same fixture mid-test and assert twice. Why one test asserting a transition instead of two tests asserting two states?** ⭐⭐

Because the bug worth protecting against is a value computed once and never recomputed — a field assigned in the constructor, or a `computed()` quietly replaced by a plain property — and two independent tests, each starting from a fresh fixture, would both pass against exactly that bug. Asserting `false`, then setting `true` on a live fixture, is what proves the derivation is reactive and not merely correct on first render. **[04-meal-finder-110] `meal-card.spec.ts` tests a presentational component that injects nothing, yet it registers `provideRouter([])`. What is that standing in for, and why is an empty route array enough?** ⭐⭐

**[04-meal-finder-111] Three specs register `provideHttpClient()` and `provideHttpClientTesting()` together, and not one of them sets an expectation or calls `verify()`. Why both providers for a test that never asserts a request?** ⭐⭐
