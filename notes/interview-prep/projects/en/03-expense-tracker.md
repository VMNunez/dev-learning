# Interview Questions — 03-expense-tracker

**Last banked:** 2026-09-09

Questions specific to the implementation decisions made in this project.
Use these alongside the topic-based files in `interview-prep/{LEVEL}/en/` and `es/`.

## Architecture & Patterns

**[03-expense-tracker-001] There is no `AppModule` anywhere in this project — `main.ts` just calls `bootstrapApplication(App, appConfig)`. Where does a template get `RouterLink` or `DecimalPipe` from, then?** ⭐⭐

Every component declares its own `imports` array, so the dependencies of a template are readable at the top of the file that owns that template: `DashboardPage` imports `RouterLink`, `SummaryCard`, `FilterBar` and `TransactionList`, and `SummaryCard` imports `DecimalPipe` for itself. I chose standalone components because the alternative is a module three folders away that declares nine unrelated things and tells you nothing about which of them this template actually uses. The consequence is that application-wide wiring had to move somewhere else, and that somewhere is `app.config.ts`, which is why `provideRouter(routes)` lives there and not in a `RouterModule.forRoot()` call.

**[03-expense-tracker-002] Your `app.config.ts` has exactly two providers: `provideBrowserGlobalErrorListeners()` and `provideRouter(routes)`. What does that list tell an interviewer about the architecture of this app?** ⭐⭐

It says there is no HTTP layer and no server: persistence is `localStorage`, handled inside `TransactionService`, so there is no `provideHttpClient()`, no interceptor and no auth guard to register. I decided to keep the config file as an honest inventory of the app's cross-cutting concerns rather than pre-registering providers "for later" — an unused `provideHttpClient()` would suggest a backend that does not exist. When project 06 needed interceptors and guards, they appeared in that project's config because the architecture genuinely had them.

**[03-expense-tracker-003] You kept the CLI's `provideBrowserGlobalErrorListeners()`. What does it actually do, and what is left for it to catch in an app that already try/catches its own storage read?** ⭐

It registers listeners for the browser's global `error` and `unhandledrejection` events and routes them into Angular's `ErrorHandler`, instead of letting them die in the console outside the framework's knowledge. The `try/catch` in the service covers exactly one predictable failure — a corrupt `localStorage` payload — and nothing else: a throw inside a `computed`, inside the persistence `effect`, or in template expression code has no other reporting route. I left it in because removing scaffolding I have not understood is how a project loses its only diagnostic for the class of failure I am least likely to predict.

**[03-expense-tracker-004] `App` contains a `<router-outlet />` and a `title` signal that no template reads. Why is that signal there?** ⭐

It is CLI scaffolding I did not delete, and the honest answer is that it should go — `app.html` is one line and never interpolates `title()`, so it is dead code that suggests a shell component doing more than it does. What I did keep on purpose is the emptiness of `App` itself: it is the mount point the router writes into, and keeping every visual decision inside the routed page means neither page inherits chrome it did not ask for. If I extracted a shared header later, `App` is where it would go, and that is the only reason the component exists at all.

**[03-expense-tracker-005] Both routes reference their component eagerly with `component:` — no `loadComponent`, no lazy chunk. Defend that.** ⭐⭐

I decided lazy loading pays for itself when a feature is large or rarely visited, and this app has two screens that a user hits within seconds of each other; splitting them would add a chunk boundary and a network round trip to save a few kilobytes of a bundle the user has already downloaded. Lazy loading also matters most when it defers a *dependency graph* — a Material module, a chart library — and neither page here imports anything the other does not. I applied `loadComponent` in project 06 where the routes were role-gated feature areas, which is the shape that actually benefits.

**[03-expense-tracker-006] Your `routes` array has `''` and `'add'` and nothing else. What does the app do when someone navigates to `/typo`?** ⭐⭐

Nothing renders inside the outlet and the router throws `NG04002: Cannot match any routes`, so the user sees an empty shell with no explanation. That is a real gap: the fix is a trailing `{ path: '**', redirectTo: '' }` or a dedicated not-found component, and the wildcard has to be last because the router matches in array order. I did not hit it during development because every navigation in the app is a `routerLink` or a `Router.navigate` I wrote myself, which is exactly why an unmatched URL is the kind of defect only a typed address bar or a stale bookmark finds.

**[03-expense-tracker-007] Your empty-path route has no `pathMatch: 'full'`. Doesn't a prefix match on `''` swallow `/add`, since `''` is declared first?** ⭐

No, and the reason is worth being precise about: an empty-path route with a component and no children still requires the URL to be fully consumed, so for `/add` the router fails that route and moves on to the next one. `pathMatch: 'full'` becomes load-bearing when the empty path carries a `redirectTo`, because a prefix-matching redirect matches *every* URL and sends the app into a redirect loop. I left it off here because there is no redirect, and adding it would be cargo-cult config that hides which case actually needs it.

**[03-expense-tracker-008] Adding a transaction is a whole route and a whole page. Why not a modal or an inline form on the dashboard, the way most expense apps do it?** ⭐⭐⭐

I chose a second route because the learning objective of this project was multi-page routing, and because a URL for "add" is a real product property: it is linkable, it survives a refresh, and the browser's back button means what the user expects. The cost is honest — a full navigation for a four-field form is heavier than an inline row, and on a mobile-first layout a modal would have been defensible. What made the route the right call for *this* app is that the two screens have genuinely different jobs: one summarises state, the other captures it, and each owns its own layout instead of competing for the same viewport.

**[03-expense-tracker-009] You navigate three different ways in two pages: `routerLink="/add"`, `routerLink="/"`, and `this.router.navigate(['/'])`. When do you reach for which?** ⭐⭐⭐

`routerLink` is for navigation the user initiates by clicking something that *is* a link — the "+ Add transaction" button and the "← Dashboard" back link — and I chose it because it renders a real `href`, so middle-click, open-in-new-tab and hover preview all work. `Router.navigate` is for navigation that is a *consequence* of something else: after `onTransactionSubmit` saves, there is nothing for the user to click, the code decides. The rule I apply is that if the decision to navigate is made in TypeScript, it belongs in TypeScript; if it is made by the user's finger, it belongs in the template.

**[03-expense-tracker-010] `TransactionForm` is the component that knows the submit succeeded, yet the `router.navigate(['/'])` is in `AddTransactionPage`. Why did the navigation not stay with the form?** ⭐⭐

Because a form that navigates is a form that can only be used on one screen. `TransactionForm` emits `transactionSubmit` with a `NewTransaction` and stops there, which means it could be dropped into a modal, an edit page or a second app without changing a line; the page is what decides that the consequence of a submit is "persist and go back to the dashboard". I decided routing is a coordinator's concern, and `AddTransactionPage` is the coordinator — it is the only component on that screen that knows both `TransactionService` and `Router`.

**[03-expense-tracker-011] The active filter lives in a signal inside `DashboardPage`, not in a query parameter. So `?filter=expense` is not a shareable URL and the filter resets after you add a transaction. Was that a decision?** ⭐⭐

It was, and it is the tradeoff I would revisit first. I chose component state because the filter is a transient view preference, not application data: it is not persisted, it does not belong in the service beside the transactions, and it dies with the page as it should. What that costs is exactly what you named — going to `/add` and back reconstructs `DashboardPage` and `currentFilter` is `'all'` again, and no filtered view can be linked or bookmarked. Putting it in the URL via `ActivatedRoute` query params would fix both, and the price is that every filter click becomes a navigation, which is the version of this decision I would defend if the app grew a date range and a category filter beside it.

**[03-expense-tracker-012] Walk me through your folder structure. Why do `summary-card`, `filter-bar` and `transaction-list` live inside `pages/dashboard-page/components/` instead of a top-level `shared/components/`?** ⭐⭐⭐

Because none of them is shared, and a `shared/` folder is a claim about reuse that I would have been making falsely. Each of those three exists to serve the dashboard, so they sit under the page that owns them, and `transaction-form` sits under `add-transaction-page` for the same reason — the folder tree tells you who consumes a component before you open a single file. What *is* genuinely cross-page went up a level: `models/transaction.model.ts` and `services/transaction.service.ts` sit at `app/` because both pages depend on them. I decided a component earns promotion to a shared folder the day a second page imports it, not the day I imagine one might.

**[03-expense-tracker-013] `Transaction`, `NewTransaction` and `Filter` all live in one `models/transaction.model.ts` at app level. Why not keep `Filter` next to the filter bar that uses it?** ⭐⭐

Because `Filter` is not the filter bar's type — it is the contract between `FilterBar`, `DashboardPage`'s `currentFilter` signal and the `switch` in `filteredTransactions`, so three files in two folders depend on it. If it lived in `filter-bar.ts`, the dashboard page would import a type from inside a child's folder, which inverts the dependency direction I want: a page may know about its children, a shared type should not live inside one of them. I decided all three types stay together because they describe one domain concept from three angles — the stored shape, the shape before an id exists, and the ways you can look at a list of them.

**[03-expense-tracker-014] But `Tone` is declared inside `summary-card.ts` and never leaves it, while `Filter` is in the model file. Isn't that the same type of decision made two different ways?** ⭐⭐

It is the same *shape* of decision with a different answer, and the difference is domain versus presentation. `Filter` is part of the app's vocabulary — the data can genuinely be all, income or expense — whereas `Tone` is `SummaryCard`'s private way of naming three colours, and `'neutral'` is a value the domain has no concept of. I chose to keep it local so nothing outside that component can start reasoning in colours. The place it leaks slightly is `[tone]="balance() >= 0 ? 'income' : 'expense'"` in the dashboard template: that expression knows the vocabulary without importing it, which works only because the strings happen to coincide.

**[03-expense-tracker-015] Walk me through the smart/dumb split on the dashboard. Which component is smart and what makes the other three dumb?** ⭐⭐⭐

`DashboardPage` is the only smart component on that screen: it injects `TransactionService`, owns `currentFilter`, derives `totalIncome`, `totalExpense`, `balance` and `filteredTransactions`, and is the one place that calls back into the service to delete. `SummaryCard`, `FilterBar` and `TransactionList` are presentational — each has `input()`s for what it renders and, where relevant, an `output()` for the intent it emits, and none of the three imports the service, the router or the model's storage concerns. I chose that split so the whole state story of the screen is readable top to bottom in one file, while each child can be reasoned about, and tested, entirely from its inputs and outputs.

**[03-expense-tracker-016] `TransactionList` renders the delete button, so it knows exactly which transaction the user wants gone. Why does it emit an id up to the page instead of injecting `TransactionService` and deleting it itself?** ⭐⭐⭐

Because the moment it injects the service it stops being reusable and starts being untestable without one — every test needs a service double, and the component can no longer be dropped into a screen that shows transactions it is not allowed to delete. I decided the child emits *intent* (`deleteTransaction` with an id) and the parent decides what that intent means; today `onDeleteTransaction` forwards it straight to the service, but tomorrow it could ask for confirmation or apply a permission check without the list knowing. It also keeps a single writer to the state: only `DashboardPage` and `AddTransactionPage` ever call the service, so if the list is wrong there are two files to read, not five.

**[03-expense-tracker-017] `FilterBar` takes `current` as an input and emits `filterChange` as an output, so a click has to go up to the parent and come back down before the button highlights. Why not let it own its own filter state?** ⭐⭐

Because two components would then hold the same fact and could disagree. The filter is what `filteredTransactions` computes from, so `DashboardPage` must own it; if `FilterBar` also kept a copy, the highlighted button would be the bar's opinion and the list would be the page's, and a parent-side reset would leave the bar lit on a filter no longer applied. I chose the fully controlled shape — render from `current()`, emit the intent, own nothing — which is why `[class.active]="current() === 'all'"` reads the input rather than a local field. The round trip is synchronous inside one signal update, so the "cost" is a render the framework was going to do anyway.

**[03-expense-tracker-018] In the dashboard template you wrote `(filterChange)="currentFilter.set($event)"` inline but `(deleteTransaction)="onDeleteTransaction($event)"` as a method. Why the inconsistency?** ⭐⭐

The rule I was applying is that a template may perform an assignment, but not a decision: `currentFilter.set($event)` *is* the entire handler, whereas deleting reaches into `TransactionService` and that call belongs in the class where it can be read and tested. I would defend either style if it were applied uniformly, and the version I would choose today is a named `onFilterChange` for both, because the symmetry makes the two child contracts look alike in the template. What I would not do is the reverse — put `this.transactionService.deleteTransaction($event)` in the HTML — since that puts a dependency in a file that cannot declare it.

**[03-expense-tracker-019] You call `TransactionForm` a dumb component, yet it builds a whole `FormGroup` with four controls and validators. How is that presentational?** ⭐⭐⭐

Because the state it owns is *its own UI state*, not the application's: the `FormGroup` is the current contents of four inputs, and it disappears when the form is destroyed. The line I use is whether the component knows anything outside itself — `TransactionForm` does not inject a service, does not know the router, does not know that a saved transaction ends up in `localStorage`, and its only contact with the world is `transactionSubmit` emitting a `NewTransaction`. I decided that made it presentational in the sense that matters for this pattern: `AddTransactionPage` can change what happens on submit without touching the form, and the form can change its fields without touching the page — as long as the emitted shape stays a `NewTransaction`.

**[03-expense-tracker-020] `AddTransactionPage` has no state, no template logic and one three-line method. Does it earn its place, or is it a wrapper around `TransactionForm`?** ⭐⭐

It earns it as the seam where the route, the data and the form meet, and it is the only component on that screen allowed to know all three. Delete it and `TransactionForm` has to inject `TransactionService` and `Router` — at which point the form is no longer droppable into an edit screen or a modal, and the "save then navigate" policy is buried inside a component whose job is collecting four fields. I chose to pay one small class for that: `onTransactionSubmit` is the whole policy of the screen, visible in one place, and the fact that it is three lines is a sign the split is working, not that the component is empty.

**[03-expense-tracker-021] `SummaryCard` declares `label` and `amount` with `input.required()` but `tone` and `prefix` with a default. How did you decide which inputs are required?** ⭐⭐

An input is required when the component cannot render anything meaningful without it, and optional when there is a correct default: a card with no label and no amount is not a card, but `tone: 'neutral'` and `prefix: ''` are perfectly valid renderings. `input.required()` also moves the check to compile time — forgetting `[amount]` is a template error, not a card showing `undefined€` at runtime — which is the whole reason I preferred it to `input<number>(0)`, where a missing binding silently renders a plausible zero. The same reasoning made `current` and `transactions` required on the other two children: there is no sensible default for "which filter is active" or "which rows to show".

**[03-expense-tracker-022] All the outputs here are `output<T>()`, not `@Output() x = new EventEmitter<T>()`. What actually changes?** ⭐⭐

`output()` returns an `OutputEmitterRef`, which is not an RxJS `Subject` at all — the old `EventEmitter` extended `Subject`, so it could be `.subscribe()`d, piped and misused as a stream, and its subscriptions had to be cleaned up manually when subscribed in code. I chose the function form because it narrows the API to the one thing an output is for, `emit()`, and because subscriptions through it are tied to the component's injection context and torn down with it. The templates are identical — `(filterChange)` and `(deleteTransaction)` bind the same way — so this is a decision about what the class can be abused for, not about the consumer.

**[03-expense-tracker-023] `TransactionList` is holding whole `Transaction` objects, but `deleteTransaction` is an `output<string>()` that emits only the id. Why the id and not the object?** ⭐⭐

Because the parent already owns the authoritative list and needs nothing from the child but identity — `deleteTransaction(id)` filters on `transaction.id !== deleteId`, so anything else in the emitted object would be ignored. Emitting the whole object also invites a subtler bug: it makes the child's copy look like a source of truth, and if the list is ever filtered or mapped on the way down, the object travelling back up may not be the one the service holds. I decided the narrowest payload that identifies the row is the right contract, which is the same reason `filterChange` emits a `Filter` and not the whole bar state.

**[03-expense-tracker-024] `DashboardPage` does `transactions = this.transactionService.transactionList`, and that is a `WritableSignal` exposed publicly. What stops the template calling `transactions.set([])`?** ⭐⭐

Nothing does, and that is a real weakness of this design rather than something I would argue away. The service declares `transactionList = signal<Transaction[]>(...)` as a public writable signal and the page re-exposes it under another name, so any consumer — including the template — can replace the whole list without going through `addTransaction` or `deleteTransaction`, and the two methods stop being the only writers. The fix is one line in the service: keep the writable signal `private` and expose `readonly transactions = this.#transactions.asReadonly()`, which leaves every reader working and makes a stray `.set()` a compile error. What is right about the current shape is the direction — the page reads state from the service and never copies it into a local signal, so there is one list and no synchronisation problem.

**[03-expense-tracker-025] `totalIncome`, `totalExpense` and `balance` are `computed()` in `DashboardPage`. Why derive them in the page instead of exposing them from `TransactionService`?** ⭐⭐⭐

I chose the page because a total is a view of the data, not the data itself, and the service's job here is to own the list and its persistence. That holds as long as one screen needs the numbers — the moment a second page wanted the balance, I would move all three into the service as computed signals and let the page read them, because duplicating the reduce is how two screens start disagreeing about the same number. The line I apply is that state and derivations *everyone* needs belong with the state, and derivations one screen needs belong to that screen; being wrong about this one costs a move of three `computed()` blocks, which is why I let the current requirement decide it.

**[03-expense-tracker-026] `balance` is `computed(() => this.totalIncome() - this.totalExpense())` rather than one pass over the list. Isn't reading two computed signals just more indirection?** ⭐

It is less work, not more: `totalIncome` and `totalExpense` each recompute once when the list changes, and `balance` reads two memoised values instead of walking the array a third time. More importantly it makes the three numbers on the screen consistent by construction — the balance cannot disagree with the two cards above it, because it is defined in terms of them rather than computed in parallel from the same source. I decided to express the arithmetic the way the domain states it, "income minus expenses", and let the signal graph handle the caching.

**[03-expense-tracker-027] `filteredTransactions` is a `computed()`. What would have gone wrong with a plain `getFilteredTransactions()` method called from the template?** ⭐⭐

A method has no memoisation and no dependency tracking, so it runs on every change detection pass — every click anywhere on the page — and re-filters the whole array whether or not anything it reads has changed. `computed()` records that it depends on `transactionList` and `currentFilter`, recomputes only when one of them actually changes, and caches the result for the several reads a template may perform. I chose it for correctness of *behaviour under growth* rather than for today's five transactions: the method version gets slower in a way that is invisible until the list is long.

**[03-expense-tracker-028] The `switch` inside `filteredTransactions` returns in all three cases and has no `default`. Doesn't TypeScript complain that the function may return `undefined`?** ⭐

No, because `currentFilter` is a `signal<Filter>` and `Filter` is the closed union `'all' | 'income' | 'expense'`, so the compiler's control-flow analysis sees the three cases exhaust it and types the callback as returning `Transaction[]`. That is the payoff of typing the filter as a union instead of a `string`: adding a fourth filter later turns this into a compile error at the exact place that has to change, which a `default: return this.transactions()` would have silenced by quietly showing everything. I decided to let the type system be the reminder rather than write a fallback that can only ever hide a bug.

**[03-expense-tracker-029] Every component here uses signals, but not one declares `ChangeDetectionStrategy.OnPush`. Why not?** ⭐⭐

Because the thing `OnPush` classically saves you from does not happen in this app: there is no `zone.js` in `package.json` and no `polyfills` entry in `angular.json`, so Angular 21 bootstraps zoneless and there is no blanket tree check after every timer, XHR and DOM event to opt out of — a view is checked when something marks it dirty, and reading a signal in a template is what registers that. What `OnPush` would still buy here is narrower and real: when a dirty view is refreshed, its `Default`-strategy children are refreshed along with it whether or not anything they read changed, and `OnPush` would limit that to the views actually notified. I did not set it because the CLI does not generate it and at two pages and a handful of rows the difference is unmeasurable — but every input on these components is a signal input, which is exactly the shape where turning it on is free, so I would still call it the first improvement to the component layer.

**[03-expense-tracker-030] Your `@for` uses `track transaction.id`. What breaks if you track by `$index` instead?** ⭐⭐

Angular uses the track expression to decide which DOM node corresponds to which item, so with `$index` deleting a row from the middle of the list makes every node below it change identity: the framework reuses and re-binds nodes rather than removing the one that went away. With few plain rows the visible result is only wasted work, but any per-row state — focus, a CSS transition, an inline edit field, an animation — ends up attached to the wrong transaction. I chose `transaction.id` because `crypto.randomUUID()` gives every transaction a stable identity that survives deletion and filtering, and filtering is exactly what this list does.

**[03-expense-tracker-031] You used the `@empty` block instead of an `@if (transactions().length === 0)` beside the loop. Any difference beyond taste?** ⭐

`@empty` is part of the same `@for` block, so the framework already knows whether the collection produced any views and does not evaluate a second condition over the same signal — the emptiness test and the loop cannot get out of step. The `@if` version reads `transactions()` twice and states the condition in a form that has to be kept in agreement with the loop's collection by hand. I chose the block because it says exactly what it means, "this is what this list looks like when there is nothing in it", in the place a reader is already looking.

**[03-expense-tracker-032] The templates use `@for` and `@if`, and no component imports `CommonModule`. How does that work?** ⭐⭐

The control-flow blocks are compiler syntax rather than directives, so there is nothing to import — unlike `*ngIf` and `*ngFor`, which are declarations that had to be brought in through `CommonModule` or, standalone, through `NgIf`/`NgFor`. That is why the only thing `SummaryCard` and `TransactionList` import from `@angular/common` is `DecimalPipe`, which is still a real class. I chose the block syntax because it also makes `track` mandatory on `@for`, turning the most common list-rendering mistake in Angular into something the compiler asks about instead of something you find later.

**[03-expense-tracker-033] `DecimalPipe` is imported separately by `SummaryCard` and by `TransactionList`. Why not import it once in `DashboardPage` and let the children use it?** ⭐⭐

Because standalone components do not inherit anything from a parent's `imports` — the array declares what *this* component's template compiles against, and a child's template is compiled against its own. That is the property I want: `TransactionList` can be moved anywhere without discovering at runtime that it relied on a pipe some ancestor happened to import. Importing it in `DashboardPage` would in fact do nothing, since the dashboard template does not use `| number` itself; the currency formatting happens entirely inside the two children.

**[03-expense-tracker-034] You inject with `private transactionService = inject(TransactionService)` instead of a constructor parameter. What did that buy you?** ⭐⭐

It puts the dependency at the top of the class as a normal field, so `DashboardPage` needs no constructor at all and `AddTransactionPage`'s two dependencies read as two lines rather than a parameter list. The practical wins are that it composes with inheritance and with reusable functions without threading arguments through a constructor signature, and that it is the same call the guards and interceptors in later projects use outside a class entirely. The constraint I have to respect is that `inject()` only works inside an injection context — a field initializer or a constructor — which is why the persistence `effect()` in the service is created in *its* constructor and not in a method.

**[03-expense-tracker-035] Your classes are `DashboardPage`, `SummaryCard`, `TransactionList` — no `Component` suffix anywhere, and the files are `dashboard-page.ts`, not `dashboard-page.component.ts`. Is that a convention you invented?** ⭐

No, it is the Angular CLI's own convention from version 20 onwards: the generator stopped appending `.component`/`.service` to filenames and stopped suffixing the class name, so `ng g c pages/dashboard-page` produces exactly this. I chose to follow the tooling rather than hand-rename everything back, since fighting the generator means every future `ng generate` produces a file that does not match the project. The one place I do still write the role is the selector — `app-dashboard-page`, `app-summary-card` — because that is what disambiguates my elements from HTML's in a template.

**[03-expense-tracker-036] The `+`/`-` sign is decided in two places: a `prefix` input on `SummaryCard` and a `transaction.type === 'income' ? '+' : '-'` ternary in `TransactionList`'s template. Is that duplication?** ⭐⭐

It is, and it is the kind worth naming: two components independently decide how a signed amount is rendered, so a change to that rule — parentheses for negatives, a locale currency symbol instead of a hard-coded `€` — has to be made twice and can be made inconsistently. The reason it happened is that the two components receive different things: the card gets a bare `amount` with no notion of income or expense, so the caller supplies the sign, while the list rows carry a `type` and can derive it. The fix I would make is a single presentational unit — a small `signed-amount` component or a pipe taking amount and type — used by both, which would also collapse the duplicated `[class.income]`/`[class.expense]` bindings that sit right beside it.

**[03-expense-tracker-037] `[tone]="balance() >= 0 ? 'income' : 'expense'"` puts a rule in the dashboard template. Why is that not a computed signal?** ⭐⭐

It should be one — `balanceTone = computed(() => this.balance() >= 0 ? 'income' : 'expense')` — and the reason is not type safety: `strictTemplates` is on in `tsconfig.json`, so that expression is already checked against `SummaryCard`'s `input<Tone>` and a typo like `'expence'` fails the build. The reasons that survive are that a rule expressed in HTML cannot be unit-tested without rendering the component, and that `Tone` is not exported, so a reader of the dashboard template cannot discover which three strings are legal without opening `summary-card.ts`. I decided against extracting it at the time because it is one comparison, and that is exactly the argument that lets template logic accumulate. The rule I would state now is that a template may read and format, but the decision "a negative balance is presented as an expense" is a rule about the domain and belongs in the class.

**[03-expense-tracker-038] Both pages open with their own `.container` div and their own heading, and there is no shared layout component. When would you extract one?** ⭐

When the chrome has to be *identical* rather than merely similar — a real header with navigation, a footer, a page title bar. Today each page's header is different in kind: the dashboard has a title plus a call to action, the add page has a title plus a back link, so a shared layout would immediately need content projection and inputs to express the difference, which is more machinery than the duplication costs. I decided the duplication is two `<div class="container">` and some CSS, and that extracting a layout before the third page exists would be designing for a shape I cannot yet see.

**[03-expense-tracker-039] Nothing stops a user from typing half a transaction and clicking "← Dashboard" — the form is silently lost. Was that considered?** ⭐

Yes, and I accepted it: the form is four fields, all of them fast to re-enter, and the guard that would prevent it — `CanDeactivate` with a confirmation on a dirty form — is a routing concept this project deliberately did not reach for. It is the exact feature I built in project 06, where the forms are long enough that losing one is a real cost, and doing it here would have meant a guard, an interface on the component and a way for the page to ask the child form whether it is dirty. That last part is the interesting cost: `AddTransactionPage` cannot see the `FormGroup` today, so the guard would force the form to expose its dirty state, which is the first crack in the input/output-only contract I chose for it.

**[03-expense-tracker-040] `FilterBar` declares `imports: []` — an empty array. Why keep it?** ⭐

There is no reason to and I would delete it; it is the CLI's scaffolding, and the template genuinely uses no directives, components or pipes — three `<button>` elements with a class binding and a click handler, none of which needs an import. Leaving it is mildly misleading, since an empty `imports` looks like a decision rather than an absence. It is also a small piece of evidence for the component being genuinely presentational: the one dependency it does have, the `Filter` type, is erased at compile time and never appears in the component's runtime metadata.

**[03-expense-tracker-041] Persistence is a single `effect()` in `TransactionService`'s constructor that writes the whole array to `localStorage`. Why not call `localStorage.setItem` inside `addTransaction` and `deleteTransaction`?** ⭐⭐⭐

I chose the effect because it makes persistence a *consequence* of the state rather than a step every mutation has to remember: `addTransaction` and `deleteTransaction` only call `this.transactionList.update(...)`, and any mutation I add later — an edit, a bulk import — is persisted without touching storage code or being able to forget to. The cost is honest: the effect re-serialises the entire list on every change, including once at start-up, so a one-row delete rewrites everything and a long list would make that visible. What it buys is that `localStorage` appears in exactly two places in the whole app — `loadTransactions()` reading it and this effect writing it — so persistence is a property of the service and no component knows it exists.

**[03-expense-tracker-042] `rxjs` is in `package.json`, but there is not a single `Observable`, `subscribe` or `async` pipe anywhere in `src/`. Where did the reactivity go?** ⭐⭐⭐

Into signals, deliberately: `transactionList` is a `signal`, every number on the dashboard is a `computed`, the filtered list is a `computed`, and the only side effect is the persistence `effect` — so there is nothing to subscribe to and nothing to tear down, which is the entire class of leak this app cannot have. I chose signals because all of this state is synchronous and in memory, and RxJS earns its place when you have values arriving over *time*: HTTP responses, a debounced search box, a socket. `rxjs` is in the dependency list because `@angular/core` and `@angular/router` still use it internally, not because I wrote any — the day this app grew a real backend or a typeahead, that is the line I would reach back across.

**[03-expense-tracker-043] There is no `zone.js` in `package.json`, no `polyfills` entry in `angular.json`, and no `provideZonelessChangeDetection()` in `app.config.ts` either. So what tells Angular to re-render after a click?** ⭐⭐⭐

Nothing has to: Angular 21's `bootstrapApplication` installs zoneless change detection as the default, so the absence of both the polyfill and the provider *is* the configuration. What schedules a render is a notification — reading a signal inside a template subscribes that view to it, so `this.transactionList.update(...)` in the service marks every view that read the list, and a template event binding like `(click)="filterChange.emit('all')"` marks its own view directly. I decided to stay on the default because every piece of state in this app already lives in a signal; what it would break is state Angular is never told about — a field mutated inside a `setTimeout`, or an array mutated in place — which is one more reason `addTransaction` builds a new array with `[...transactions, transaction]` instead of pushing.

**[03-expense-tracker-044] `TransactionService` is `@Injectable({ providedIn: 'root' })`. What would change if you had put it in `DashboardPage`'s `providers` array instead?** ⭐⭐

The list would stop surviving navigation. A component-provided service is created with the component and destroyed with it, so going to `/add` and back would build a second `TransactionService`, re-read `localStorage` and register a second persistence `effect` — and worse, `AddTransactionPage` would get an instance of its own, so the transaction it saved would not be in the signal the dashboard is rendering. I chose `providedIn: 'root'` because the transaction list is application state that both routes must see as one object, and because a root-provided service is tree-shakable — one nothing injects never reaches the bundle. The deliberate contrast is `currentFilter`, which I left inside `DashboardPage` precisely *because* it should die with the screen.

**[03-expense-tracker-045] `SummaryCard`, `FilterBar` and `TransactionList` style `:host` instead of wrapping their templates in a div, and both pages define their own `.container` class. Why do those two `.container` rules not collide?** ⭐⭐

Because Angular's default emulated encapsulation rewrites each component's CSS with a generated attribute, so `.container` in `dashboard-page.css` can only ever match elements in that component's own template — I chose to lean on that instead of inventing a BEM-style naming scheme to keep two pages apart. I styled `:host` on the three children because their host element is already a participant in the parent's layout: `app-summary-card` needs `flex: 1` to size inside the dashboard's `.summary` row, and adding a wrapper div to hang that class on would insert a meaningless element between the flex container and its item. The one thing I let cross the boundary on purpose is the custom properties in `styles.css` — `--income`, `--expense`, `--bg-card` — because inherited CSS variables are what a global stylesheet can hand a component without reaching inside it.

**[03-expense-tracker-046] `TransactionList` receives `filteredTransactions()`, but the three summary cards read `totalIncome()`, `totalExpense()` and `balance()`, which are computed from the unfiltered list. Filtering to "Expenses" changes the rows and not the numbers. Is that a bug?** ⭐⭐

No, it is the shape I chose, and the signal graph forks on purpose: `filteredTransactions` reads `currentFilter`, the three totals do not, so switching the filter recomputes one derivation and leaves the other three untouched. The totals are a statement about the user's finances and the filter is a view over the rows; deriving the balance from `filteredTransactions()` instead would make the balance card show the balance of whatever slice happens to be on screen, which is a number nobody asked for and which would read as broken under the "Income" filter. If both behaviours were wanted I would say so in the UI rather than in the wiring — a fourth card explicitly labelled for the filtered slice, not a silent change of meaning behind the same three labels.

**[03-expense-tracker-047] The browser tab reads `03ExpenseTracker` on both screens, because that is the `<title>` in `index.html` and nothing ever changes it. What is the Angular answer to that?** ⭐

A `title` on each route — `{ path: 'add', component: AddTransactionPage, title: 'Add a transaction' }` — which the router's built-in `TitleStrategy` applies after every successful navigation; no extra provider is needed for the default behaviour. I did not add it, and I would call it a genuine gap in a routed app rather than polish: the tab is the one piece of chrome still visible when the user has ten of them open, and it is close to the cheapest thing the router gives you. The `title` signal sitting unused in `App` is unrelated CLI scaffolding and could not do this job anyway — the document title is not something a component template can write.

**[03-expense-tracker-048] `filter-bar.html` repeats the same button three times with `'all'`, `'income'` and `'expense'` hard-coded. Why not `@for` over the `Filter` union?** ⭐

Because a TypeScript union does not exist at runtime — I would have had to write a companion array like `filters: Filter[] = ['all', 'income', 'expense']` and keep it in step with the type by hand, so the loop trades three visible buttons for one array that can silently disagree with the type the rest of the app switches on. With three fixed options I decided the explicit markup reads better than the indirection, especially since each button's label is prose and not just its value capitalised. The point where I would change my mind is a fourth or fifth filter, or filters arriving from data — and then I would make the array the source and derive the type from it with `typeof filters[number]`, so the two cannot drift.

## Business Rules

**[03-expense-tracker-049] Your form has four controls, four `Validators.required` and exactly one other validator, `min(0.01)` on the amount. Walk me through what this form actually forbids — and what it lets through.** ⭐⭐⭐

It forbids four things and only four: an empty description, a missing or non-positive amount, a type left on the placeholder option, and a cleared date. Everything else gets through — a description of three spaces, a date in 2099, an amount with six decimals, and the same transaction entered twice. I decided that for a personal ledger with no backend and no shared data, the cost of a wrong entry is that the user deletes it and retypes it, so the validation only has to stop the entries the app cannot render meaningfully: a nameless row, a zero-euro row and an untyped row that would land in neither the income nor the expense total.

**[03-expense-tracker-050] `description` carries `Validators.required`. What does that validator do with a value of three spaces?** ⭐⭐

It accepts it. `Validators.required` only tests for `null`, `undefined` and an empty string or empty array — it never trims — so `"   "` is a present value and the form is valid, and the dashboard then renders a transaction row whose description paragraph is blank. I know the fix is a validator of my own that trims before testing, or `Validators.pattern(/\S/)`, and I left it out because it is not the failure a single user typing their own expenses actually hits; on a form whose data another person reads, I would add it, since "required" that accepts whitespace is exactly the kind of gap an interviewer probes for.

**[03-expense-tracker-051] Nothing caps the length of the description. What does a 400-character description do to your dashboard?** ⭐⭐

It stretches the `.transaction-info` column and pushes the amount and the delete button of that row out of alignment with the rest of the list, because the row is a flex container with no `max-width` or `text-overflow: ellipsis` on the description. I chose not to add `Validators.maxLength` because a length limit is a storage constraint I do not have — there is no column width in `localStorage` — so the honest fix is a CSS truncation rule rather than a validator that tells the user their own description is too long for a layout decision I made.

**[03-expense-tracker-052] Why `Validators.min(0.01)` on the amount, and not `Validators.min(0)`?** ⭐⭐⭐

Because `min(0)` would accept `0`, and a zero-euro transaction is a row that changes no total and means nothing in a ledger. `Validators.required` does not catch it either — required treats `0` as a present value, so without `min(0.01)` a zero would be perfectly valid — and I chose `0.01` rather than any positive number because the currency's smallest unit is the cent, so it is the smallest amount this app can meaningfully record. It also does the work of a "no negatives" rule for free, which matters because the sign in this model comes from the `type` field, never from the number.

**[03-expense-tracker-053] Three of your controls are `nonNullable: true`. `amount` is `new FormControl<number | null>(null, …)`. Why is one control allowed to be null?** ⭐⭐

Because an `<input type="number">` that the user clears reports an empty value, and a number control has no sensible non-null empty state — `nonNullable` with an initial `0` would mean the form opens pre-filled with a valid-looking zero and `reset()` would put a zero back rather than an empty box. I chose `null` as the empty value so that `Validators.required` has something to fail on and the field renders blank, and I accepted the cost, which is that `amount` is the one field whose type forces a null check before I can emit a `NewTransaction`.

**[03-expense-tracker-054] There is no `Validators.max` on the amount. What stops someone entering 999999999999?** ⭐⭐

Nothing does, and that is deliberate rather than an oversight: any ceiling I picked would be an arbitrary claim about how much money this user handles, and the app has no currency, no account and no balance limit to justify one. What the number does hit is a real limit further down — beyond `Number.MAX_SAFE_INTEGER` the `reduce` in `totalIncome` starts losing precision, and floating-point addition of cents is already inexact, which is the argument for storing amounts as integer cents if this ever became something people relied on.

**[03-expense-tracker-055] The `type` control is typed `'income' | 'expense' | ''` and starts at `''`. Why a sentinel empty string instead of `null`?** ⭐⭐

Because the control is bound to a `<select>` whose first `<option value="">-- Select a type --</option>` is a real DOM option with an empty string value, so the empty string is the value the browser actually reports when nothing is chosen — using `null` would have meant a control whose value can never match its own placeholder option. `Validators.required` treats `''` as absent, so the placeholder is what fails validation, and I added `''` to the union rather than widening the control to `string` so the compiler still knows there are exactly three states to narrow.

**[03-expense-tracker-056] The `date` control is pre-filled with today's date and still carries `Validators.required`. When can that validator ever fire?** ⭐⭐

When the user clears the field — a native date input has a clear affordance, and the control then reports an empty string, which is why the validator is not decoration. I decided to validate every field the model requires rather than only the ones I expect to be empty, because the default is a convenience I control and the emptiness is a state the user controls, and a required field whose validator depends on my own initial value is one refactor away from silently accepting an empty date.

**[03-expense-tracker-057] Your `today()` builds the string by hand from `getFullYear()`, `getMonth() + 1` and `getDate()`. Why not `new Date().toISOString().slice(0, 10)`, which is one line?** ⭐⭐⭐

Because `toISOString()` converts to UTC first, so for a user in Spain adding an expense at 1 a.m. in summer it returns yesterday's date, and for a user east of UTC late in the evening it returns tomorrow's. The three getters I used read the local clock, which is the day the user believes they are in, and that is the only day a personal expense tracker can mean. The `padStart(2, '0')` is there because `<input type="date">` requires exactly `YYYY-MM-DD` and would silently reject `2026-9-9`.

**[03-expense-tracker-058] Nothing forbids a date in 2099 or in 1900. Should the form have a max?** ⭐⭐

For a tracker of what you have already spent, a future date is meaningless and I would accept `[max]="today()"` as a fair criticism — I left it out because back-dating is the case that actually matters and a max would have to be paired with a min I have no basis for. What I would not do is enforce it only in the template with the native `max` attribute, since that is a browser hint the user can bypass by typing; it would have to be a `Validators` entry so the same rule fails the control, which is the general point that the DOM's own validation is never the rule of record.

**[03-expense-tracker-059] `date` is a `string` in the `Transaction` model, not a `Date`, and `transaction-list.html` prints it with `{{ transaction.date }}`. What are the consequences of both of those?** ⭐⭐

The string choice is the one I would defend: `localStorage` holds JSON, `JSON.parse` gives a string back rather than a `Date` anyway, and `YYYY-MM-DD` sorts lexicographically in the same order it sorts chronologically, so keeping it a string removes a rehydration step and a class of "it is a string at runtime but typed as a `Date`" bugs. Printing it raw is the part I would change: a Spanish user reads `09/09/2026`, not `2026-09-09`, and the fix is `{{ transaction.date | date: 'dd/MM/yyyy' }}`, which is the same `@angular/common` import I already make for `DecimalPipe` in that component.

**[03-expense-tracker-060] The first line of `onSubmit()` is `this.transactionForm.markAllAsTouched()`, before the validity check. Why is it there, and what would the user see without it?** ⭐⭐⭐

Every error message in the template is gated on `touched`, so a user who opens the form and clicks the button without entering any field has touched nothing: without that line the submit would return silently and the screen would look identical, which reads as a broken button. I chose to mark the whole group touched on submit so the four messages appear at once and the user sees exactly which fields are blocking them, and I put it before the guard rather than inside the failure branch because it is the same call either way and the ordering keeps the method's shape flat.

**[03-expense-tracker-061] Each error block reads `description?.touched && description?.hasError('required')`. Why gate on `touched` at all instead of showing the error whenever the control is invalid?** ⭐⭐

Because the form opens invalid — three of four controls start empty — so an ungated check would greet the user with four red messages about fields they have not reached yet, which trains them to ignore the messages. I chose `touched` rather than `dirty` because `touched` means the user has visited and left the field, which is the moment the answer is due, while `dirty` only becomes true if they actually typed, so a field they tabbed straight through would never show its error. `markAllAsTouched()` on submit is what closes the remaining gap.

**[03-expense-tracker-062] The amount field has two error blocks — `required` and `min`. Can both messages render at the same time?** ⭐

No, and it is the validators that guarantee it rather than the template: `Validators.min` returns `null` for a `null` or empty value, so it deliberately does not fire on an absent field, which means `required` and `min` are mutually exclusive by construction. That is why I wrote them as two sibling `@if` blocks rather than an `@if / @else` chain — the exclusivity is a property of Angular's built-in validators, not something my markup has to enforce, and the pattern would still be correct if I later added a third validator that could co-occur.

**[03-expense-tracker-063] Your submit button is never disabled — no `[disabled]="transactionForm.invalid"`. Most tutorials do exactly that. Why didn't you?** ⭐⭐⭐

Because a disabled button is a dead end: it tells the user they cannot submit without telling them why, it is not reachable by keyboard focus in most browsers, and screen readers announce nothing useful. I decided the button stays enabled and the submit handler is the gate — it calls `markAllAsTouched()`, the messages appear under the offending fields, and the user is told the reason instead of being blocked by it. The cost is that `onSubmit` must guard rather than trust, which it does with the `if (!this.transactionForm.valid) return;` on the next line.

**[03-expense-tracker-064] You wrote `if (!this.transactionForm.valid) return;`. Is that the same as `if (this.transactionForm.invalid) return;`?** ⭐⭐

Not in general. A `FormGroup` has four statuses, and `valid` is only true for `VALID`, while `invalid` is only true for `INVALID` — so a group that is `PENDING` because an async validator is still running, or `DISABLED`, is neither valid nor invalid, and `!valid` refuses it while `invalid` waves it through. In this form there are no async validators and no disabled controls, so the two are equivalent today; I chose `!valid` because it is the one that stays correct the day I add an async validator, which is the direction the difference actually bites.

**[03-expense-tracker-065] After the validity check you have a second guard: `if (amount === null || type === '') return;`. Can that line ever be reached with a bad value?** ⭐⭐

In practice no — `Validators.required` on both controls means the group cannot be valid while `amount` is `null` or `type` is `''`, so the earlier guard has already returned. It is there for the compiler, not the user: `getRawValue()` returns the control types I declared, which include `null` and `''`, and `NewTransaction` accepts neither, so without that narrowing the emit would need an `as` assertion. I chose the runtime check over the assertion deliberately, because the assertion would silence the compiler by lying to it while this guard makes the same claim in a way that stays true if I ever remove a validator.

**[03-expense-tracker-066] Inside `onSubmit` you destructure `this.transactionForm.getRawValue()`, not `.value`. What is the difference and does it matter in this form?** ⭐⭐

`value` omits disabled controls, so a typed form's `value` is a `Partial<>` of its shape and every field arrives as possibly `undefined`; `getRawValue()` includes disabled controls and returns the full shape. Nothing in this form is ever disabled, so the two return the same data at runtime — what changes is the type I have to handle, and `getRawValue()` is what lets me destructure four fields and narrow only the two that can legitimately be empty. I decided to use it by default in typed forms for that reason, rather than switching to it later when the first `disabled` control appears and the `Partial` starts leaking.

**[03-expense-tracker-067] After a successful emit you call `this.transactionForm.reset({ date: this.today() })` — but the parent navigates away and destroys this component immediately. Is that reset doing anything?** ⭐⭐

On today's flow, no: `AddTransactionPage.onTransactionSubmit` navigates to `/`, the router destroys `TransactionForm`, and the reset state is thrown away with it. I kept it because the reset is the form's own contract — the component says "when I emit, I am clean again" — and it does not depend on what the parent chooses to do with the event; the day the page decides to stay put and let the user add several transactions in a row, the form is already correct. The argument on the other side is that untested behaviour is not really guaranteed, and I would accept a component test that submits twice as the thing that keeps it honest.

**[03-expense-tracker-068] Every amount in storage is a positive number and the sign comes from the `type` field. Why not store expenses as negative and make the balance a single `reduce`?** ⭐⭐⭐

Because the sign is not the only thing the type carries: the filter bar filters on it, the row colours on it, and the two summary cards need income and expense as separate totals — with signed amounts I would be recovering the category by testing `amount < 0`, which is a rule hidden in a comparison instead of stated in the model. I chose an explicit `type: 'income' | 'expense'` union so the classification is a value the compiler checks and the sign is derived at the edges, and the price is exactly what you are pointing at: `balance` has to be `totalIncome() - totalExpense()` rather than one pass, and the `+`/`-` has to be decided at render time.

**[03-expense-tracker-069] PLANNING.md's feature list says a transaction has "name, amount, and category", but your `Transaction` interface has `description`, `amount`, `type` and `date` — there is no category anywhere. What happened?** ⭐⭐

The plan was written before the model was, and what shipped renamed "name" to `description`, added `date`, and turned "category" into the two-value `type` union — a free-text or enumerated category like Food or Transport was never built. I would rather say that plainly than invent a category that does not exist: the app groups transactions on one axis only, income against expense, which is what the filter bar and the summary cards are built for. Adding a real category means a second dimension — another control, another filter, and a decision about whether the list groups or just filters — and it is the first thing I would add if this project were being extended.

**[03-expense-tracker-070] `TransactionService.addTransaction` takes a `NewTransaction` and stores it with no checks at all. What stops a caller passing `{ amount: -50, description: '', type: 'income', date: '' }`?** ⭐⭐⭐

Nothing does — all the validation in this app lives in `TransactionForm`, and the service trusts its caller completely. I decided that is acceptable while the form is the only caller and the whole app runs in one browser tab: duplicating the rules in the service would mean two places to change and a second set of error messages nobody would ever see. What makes it acceptable is precisely what would stop being true with a backend: there the client's validation is a convenience and the server has to re-validate, because the request can arrive from anything, and this service is the layer that would grow those checks.

**[03-expense-tracker-071] Nothing stops the user adding the same transaction twice — same description, same amount, same date. Should there be a rule?** ⭐⭐

No, and it is one of the few places where the absence is the right answer rather than a shortcut: buying the same coffee twice in one day is a real pair of transactions, so a uniqueness rule on those three fields would reject correct data. Each entry gets its own `crypto.randomUUID()`, so two identical-looking rows are still two distinct records that can be deleted independently. If duplicates from double-clicking the submit button became a problem, the fix belongs at the submit — disabling the button for the duration of the save, or debouncing — not in a business rule that says two identical expenses cannot exist.

**[03-expense-tracker-072] A transaction can be added and deleted but never edited. Was that a decision or a missing feature?** ⭐⭐

Both, honestly: the plan scoped the project to forms, routing and persistence, and add-plus-delete exercises all three, so edit was cut on cost rather than on principle. What I would not do is pretend it is free to add — edit means a third route or a modal, seeding the same `FormGroup` from an existing transaction, an `updateTransaction` on the service that replaces by id rather than appending, and a decision about whether the id survives. Delete-and-retype is the workaround the app gives today, and for a four-field record it is a defensible one.

**[03-expense-tracker-073] Deleting a transaction takes one click — no confirmation, no undo — and the `effect` writes the new array to `localStorage` before the user can blink. Defend that.** ⭐⭐⭐

The defence is proportionality: the record is four fields the user typed themselves, and a confirmation dialog on every delete is friction paid on every correct deletion to protect against the rare wrong one. What I would concede is that the persistence makes it irreversible — the effect fires on the signal change, so the row is gone from storage immediately and a page refresh cannot bring it back. The cheap fix I would take before a modal is an undo: keep the deleted transaction in a signal for a few seconds and offer to re-add it, which costs one click only when the user actually made a mistake.

**[03-expense-tracker-074] `deleteTransaction` is a `filter` on id. What happens if the id is not in the list, and what guarantees it removes exactly one row?** ⭐⭐

An unknown id is a silent no-op: `filter` returns an array with the same contents, the signal is set to a new array, the effect rewrites identical JSON and the user sees nothing — which is the behaviour I want, since the only caller is a button rendered from the list itself, so a missing id would mean a bug I would rather not mask with an error. Exactly one row goes because ids come from `crypto.randomUUID()`, which is collision-free for this purpose; I chose it over a `Date.now()`-derived id precisely because two transactions added in the same millisecond would have collided, and then `filter` would have deleted both.

**[03-expense-tracker-075] `loadTransactions` checks `Array.isArray(parsed)` and then returns `parsed` as `Transaction[]`. PLANNING.md says the stored data is "shape-checked" before it enters the signal. Is it?** ⭐⭐⭐

Not per item, no — the guard proves the JSON was an array and nothing about what is inside it, so `["hello"]` or `[{"foo":1}]` passes and enters a signal the compiler believes holds `Transaction[]`. The consequence is visible on the dashboard: `reduce` over an object with no `amount` produces `NaN`, so the balance card renders `NaN€` and the type-based filters silently drop every malformed row. What the check does buy is the failure it was written for — a non-array value, which would make `@for` throw — and the honest description of what is there is a type guard on the container, with the per-item `typeof` guard still owed.

**[03-expense-tracker-076] When `JSON.parse` throws, you `console.error` and return `[]` — and then the constructor's `effect` writes that empty array straight back to `localStorage`. What has the user just lost?** ⭐⭐⭐

Everything that was in that key, and irrecoverably: the effect runs on the initial read of the signal, so the corrupt-but-possibly-repairable blob is overwritten with `[]` on the same page load that failed to read it, and the only trace is a console message the user will never open. I decided that starting empty beats crashing the app on load, and I would keep that; what I got wrong is destroying the evidence. The fix is to move the bad value aside before returning — writing it to a `transactions.corrupt` key — and to tell the user on screen that their data could not be read, rather than showing them an empty dashboard that looks like a clean install.

**[03-expense-tracker-077] The `effect` calls `localStorage.setItem` with no try/catch. What happens in Safari private mode or when the 5 MB quota is full?** ⭐⭐

`setItem` throws a `QuotaExceededError`, and because it is inside an `effect` with no handler the write fails while the signal keeps the new transaction — so the UI shows the row, the totals include it, and the next page load loses it. I decided the read path deserved defence and treated the write as safe, which is inconsistent: the read is guarded because I expected corrupt data, and the write is the one that fails on a condition I do not control at all. The repair is the same shape as the read's — catch it, and surface a "changes are not being saved" state rather than letting the screen quietly lie about what is persisted.

**[03-expense-tracker-078] Amounts render through `number: '1.0-2'`. If the rows are rounded to two decimals but the totals are computed from the raw values, can the column stop adding up to the card?** ⭐⭐

Yes, and that is the real cost of the choice. `'1.0-2'` rounds for display only, so three rows of `0.005` each render as `0.01` while `totalExpense` sums the unrounded values to `0.015` and the card renders `0.02` — the screen shows `0.01 + 0.01 + 0.01 = 0.02`. The reason it is not visible in practice is `Validators.min(0.01)` plus a number input people fill in cents, and the proper fix is to make the rule the model's rather than the pipe's: store integer cents, or round on submit so the stored value and the displayed value are the same number.

**[03-expense-tracker-079] You format money as `{{ amount | number: '1.0-2' }}€` rather than with `CurrencyPipe`. What did that cost?** ⭐

The grouping and the decimal separator come from the app's locale, which is the default `en-US`, so a thousand-euro expense renders as `1,000.00€` — a comma for thousands and a dot for decimals, next to a euro sign, which is not how the number is written in Spain. `CurrencyPipe` with `registerLocaleData(localeEs)` and a `LOCALE_ID` provider would give `1.000,00 €` and put the symbol where the locale puts it. I chose the simpler pipe with a literal `€` because the app has exactly one currency and no i18n setup, and I would call it the right decision made for the wrong reason: the currency is fixed, but the formatting still should not have been.

**[03-expense-tracker-080] The list renders in insertion order — you never sort it. What does a user see when they back-date a transaction to last month?** ⭐⭐

It appears at the bottom of the list, under everything added before it, because `addTransaction` appends with `[...transactions, transaction]` and `filteredTransactions` never reorders. For a ledger that is the wrong default — the expected order is newest first by date — and the fix is cheap precisely because of the model choice made earlier: `YYYY-MM-DD` strings sort chronologically under a plain string comparison, so it is a `toSorted()` inside the existing `computed()` and no date parsing at all. I would put it in the computed rather than in `addTransaction`, so the order is a property of what is displayed and not of how the array was built.

**[03-expense-tracker-081] Filter to "Income" when every transaction you have is an expense. The list says "No transactions yet". What is wrong with that?** ⭐⭐

The message is false — the user has transactions, none of them match the current filter — and it reads as data loss on a screen where the summary cards above are simultaneously showing a non-zero expense total, so the page contradicts itself. The cause is that the `@empty` block sits on `transactions()`, which is already the filtered list, so it cannot tell "nothing exists" from "nothing matches". The fix belongs in the parent, since only the dashboard knows both lists: pass an input that distinguishes the two states, or move the message up to the page where the unfiltered `transactions()` is in scope.

**[03-expense-tracker-082] The user submits the form and is bounced straight to the dashboard. What tells them the transaction was saved?** ⭐⭐

Only the row itself appearing in the list, and the totals changing. There is no toast, no success message and no highlight on the new row, so the confirmation is inferred from a screen the user has to read. I chose the navigation as the feedback because on a two-page app the destination is the proof — the alternative, staying on the form with a message, was worse for the main flow of adding one transaction and going back. What I would add before calling it finished is the cheap half: a transient message on the dashboard, or scrolling and briefly highlighting the row that was just added.

**[03-expense-tracker-083] The description is free text from the user, and it also comes back from `localStorage`, which anyone can edit in devtools. What stops someone storing `<script>alert(1)</script>` as a description?** ⭐⭐

Nothing stops it being stored, and nothing needs to: it is rendered with `{{ transaction.description }}`, and Angular's interpolation escapes the value into text, so the row displays the tag literally instead of executing it. That is the framework's default and it is why I did not write an escaping step of my own — the ways to lose it are the ones I deliberately do not use here, `[innerHTML]` without sanitising or a `bypassSecurityTrustHtml` call. The part worth naming is that the untrusted source in this app is not only the keyboard: `localStorage` is fully under the user's control, which is exactly why the read path parses defensively in the first place.

**[03-expense-tracker-084] Pressing Enter inside the description input submits the form. Where did you code that?** ⭐

I did not — it is the browser's implicit submission: a `<form>` with a submit button fires its submit event when Enter is pressed in a text input, and `(ngSubmit)` is bound to that event through `ReactiveFormsModule`, so `onSubmit()` runs with all its validation intact. That is the reason the button is `type="submit"` inside a real `<form>` rather than a `type="button"` with a click handler, which would have lost keyboard submission and the native semantics with it.

**[03-expense-tracker-085] Nothing caps how many transactions the app holds — no pagination, no virtual scroll. Where does that break?** ⭐

Two places, at different scales. The DOM goes first: `@for` renders every row, so a few thousand transactions is a long, janky page — mitigated by `track transaction.id`, which keeps existing rows on re-render, but not solved by it. The hard wall is `localStorage`'s ~5 MB per origin, which the effect rewrites in full on every single change, so the cost of adding one transaction grows with the size of the whole list. I decided both limits are far past what a personal tracker reaches, and I would name them as the point where this app stops being a `localStorage` app and needs a backend rather than a bigger front end.

**[03-expense-tracker-086] Three of your controls declare their validators inside an options object and `amount` passes them as a positional array. Why two syntaxes in one `FormGroup`?** ⭐

Because the options object is the only form that carries `nonNullable`, and `amount` is the one control I did not want non-nullable — so the other three had to be written as `{ nonNullable: true, validators: … }`, while on `amount` the two-argument shorthand said everything there was to say. I would call the result an inconsistency a reader has to decode rather than a decision worth defending, and the cheap fix is to write all four in the options form, which also takes `updateOn` and an async validator list the shorthand can only reach through a third positional argument. What I would not do is make `amount` non-nullable just to make the four lines rhyme.

**[03-expense-tracker-087] Your amount input is `<input type="number">` with no `min` and no `step`, and the date input has no `max`. Does the browser's own validation forbid anything here?** ⭐⭐

Nothing, and it could not even if I had written those attributes: `ReactiveFormsModule` puts `novalidate` on any `<form>` it manages, so native constraint validation is switched off and my `Validators` are the only rule of record. I decided that is the right default — two sources of truth for one rule is how a form ends up rejecting a value with a browser bubble the app cannot style, cannot translate and cannot read. What I gave up is the input's own affordance: the number spinner steps happily into negatives and the user only learns the rule after pressing the button, so the repair I would take is `[min]` and `step="0.01"` as UI hints beside the validators, never instead of them.

**[03-expense-tracker-088] The template checks `description?.touched`, with an optional chain on every one of the four getters. Why can those controls be `null`?** ⭐⭐

They cannot, at runtime — every getter is `this.transactionForm.get('…')`, and `get()` is typed to return `AbstractControl | null` because the string path it takes is something the compiler cannot verify, so the `?.` answers the type and never a real state of this form. The typed route is `this.transactionForm.controls.description`, which the `FormGroup`'s own generic types as a non-null `FormControl<string>`, and which would let the template read `description.touched` with no chaining and no getters at all. I chose the getters early because they read well in the template, and the `?.` noise across eight checks is exactly the cost that would send me to `controls` on the next form I write.

**[03-expense-tracker-089] `reset({ date: this.today() })` passes the date back explicitly. Given that control was created `nonNullable` with `this.today()` as its initial value, is that argument doing anything?** ⭐⭐

Almost nothing, and the "almost" is the interesting part: `reset()` on a `nonNullable` control restores the `defaultValue` captured when the control was constructed, so `description` and `type` return to `''` and `date` would return to today's date on its own — the explicit argument only differs if the component has been alive across midnight, where it recomputes the day instead of restoring a stale one. The control that genuinely needs the distinction is `amount`, which is not `nonNullable` and so resets to `null`, which is the empty box I want rather than a valid-looking zero. I decided to pass the date anyway because recomputing it is free and the line states the intent, but I would not defend it as necessary.

**[03-expense-tracker-090] The type `<select>` opens on `-- Select a type --` and that option is never disabled. What can the user do that you probably did not intend?** ⭐

Go back to it: the placeholder is an ordinary option with `value=""`, so after choosing Income they can reselect it and put the control back into its invalid state. The outcome is still correct — the submit fails with "Please select a type" — but by a path that exists only because I left the option selectable. I chose `''` as its value deliberately, since that is what makes `Validators.required` fail on the placeholder, and adding `disabled` to the option keeps that while removing the way back; what I would not use is `hidden`, which browsers treat inconsistently and which leaves a `<select>` whose current value is not among the options the user can see.

**[03-expense-tracker-091] When a validation message appears, nothing announces it — the `<p class="error-msg">` is a plain paragraph and the input carries no `aria-describedby` or `aria-invalid`. What does a screen-reader user get on a failed submit?** ⭐

Nothing they can act on: `markAllAsTouched()` makes four paragraphs appear somewhere on the page, and because the `@if` blocks insert them silently and no input is associated with its message, focus stays on the button and the user is never told why it did nothing. I decided accessibility beyond correct `label for` / `id` pairing was out of scope here, and I would rather say that than dress it up as a considered tradeoff. The minimum repair is `role="alert"` on each message so its insertion is announced, plus `[attr.aria-describedby]` and `[attr.aria-invalid]` on the control — the same information the sighted user already gets from the red text.

**[03-expense-tracker-092] Amounts render through `number: '1.0-2'`. Why does a fifty-euro expense show as `50€` and not `50.00€`?** ⭐⭐

Because the `0` after the dot in that format string is the **minimum** number of fraction digits, not a floor I have to live with — so any amount with no cents drops its decimals entirely and the column reads `50€`, `7.5€`, `12.34€`, three different widths in one list with nothing aligning. Money wants `'1.2-2'`, which pads every value to exactly two decimals and lets the column line up on the decimal point. I chose `'1.0-2'` reading it as "up to two decimals" and took in only the upper bound of the format; it is the clearest small thing in this project that I would change, and it is one character.

**[03-expense-tracker-093] Open the app with no transactions. The balance card is green and the expenses card reads `-0€`. Which of those is a rule you wrote?** ⭐⭐

Both, and neither survives the empty state. The green comes from `[tone]="balance() >= 0 ? 'income' : 'expense'"`, where I chose `>=` so that a ledger settled exactly at zero is not painted as a loss — but on a fresh install it paints nothing as income; the `-0€` comes from the static `prefix="-"` on the expenses card, which I decided at the template level because that card always totals expenses, without asking what it should show when the total is nothing. The repair is already half-built: the `Tone` union declares a `neutral` member that no call site ever passes, so exactly zero should take it, and the prefix should be dropped when the amount is `0`.

**[03-expense-tracker-094] `TransactionList` renders one `✕` button per row, with no `aria-label`. What does that control announce?** ⭐

The character itself, which a screen reader reads out as "multiplication sign" or skips entirely — so the user reaches a button with no name and no indication of which row it belongs to, on an action that is immediate and irreversible. I chose the glyph for the visual density of the row and I would keep it on screen, but the name has to come from somewhere: `[attr.aria-label]="'Delete ' + transaction.description"` costs nothing, and it is the only thing that makes the control usable without a mouse.

**[03-expense-tracker-095] Your storage key is the bare string `'transactions'`, with no app prefix and no version. What breaks?** ⭐⭐

Two things, and the first one bit me in development: `localStorage` is keyed per origin, so every Angular project I serve on `localhost:4200` shares one store and one `transactions` key — another project's data is read back as if it were this app's, and `loadTransactions` cannot tell the difference because both are arrays. The second is the one that would matter in production: the key carries no schema version, so the day I add a field to `Transaction` the app reads yesterday's objects back and every row silently lacks it. I chose the short key for readability and would replace it with something like `expense-tracker.transactions.v1`, where the prefix ends the collision and the suffix gives the read path something to branch on.

## Technical Decisions

**[03-expense-tracker-096] Four fields, one submit. Why reactive forms and not template-driven with `[(ngModel)]`?** ⭐⭐⭐

I chose reactive forms because the form's shape is declared in TypeScript, not discovered by reading the template: `transactionForm = new FormGroup({...})` holds the four controls, their initial values, their `nonNullable` flags and their validators in one block, and `getRawValue()` then hands me an object whose type the compiler already knows matches `NewTransaction`. With `ngModel` the model is whatever the template happened to bind, validation lives in HTML attributes, and there is no typed object on the way out. The second reason is control: `markAllAsTouched()` on submit and `hasError('min')` in the template are calls on a form model I own, and template-driven forms give me no equally direct handle on it.

**[03-expense-tracker-097] You build the group with `new FormGroup` and four `new FormControl` calls instead of injecting `FormBuilder`. Why the long way?** ⭐⭐

`FormBuilder` is sugar over exactly these classes, and what it costs is the explicit generic. I decided the generic was the point of this form: `new FormControl<number | null>(null, …)` and `new FormControl<'income' | 'expense' | ''>('', …)` state each control's type where the control is declared, which is what makes `getRawValue()` line up with `NewTransaction` without an `as` assertion. Through `fb.group` I would be relying on inference and remembering `fb.nonNullable.group` for the three controls that need it; on a form of fifteen controls I would take the brevity, at four I preferred the declaration to be readable.

**[03-expense-tracker-098] Every transaction lives in `localStorage` under one key, and there is no server anywhere. What does that decision cost the user?** ⭐⭐⭐

I chose `localStorage` because the objective of this project was forms, routing and persistence in the browser, and it is the smallest thing that makes data survive a refresh: one `getItem` seeding the signal, one `setItem` in an effect, no backend, no auth, no deploy story. The cost is real and I say it out loud in an interview — the data is bound to one browser on one machine, there is no sync, no backup and no sharing, the API is synchronous, string-only and capped around 5 MB, and anyone can rewrite it from devtools, which is exactly why `loadTransactions` treats what comes back as untrusted input. A real expense tracker needs an account and a server behind it, and that is the step project 07 takes.

**[03-expense-tracker-099] `addTransaction` builds `[...transactions, transaction]` and `deleteTransaction` returns a new filtered array. Why not just `push` into the array the signal already holds?** ⭐⭐⭐

Because a signal decides whether to notify by comparing the new value with the old, and for an array that comparison is by reference: `push` mutates in place, the reference is unchanged, and the signal concludes nothing happened — the three `computed()` totals never recompute, `filteredTransactions` keeps its old rows, and the persistence effect never fires, so the transaction is not even saved. I chose to replace the array on every write so the reference always changes and the whole derived graph invalidates. The price is one new array per mutation, which at this size is nothing, and the discipline is the same one I would need under `OnPush` or in any immutable-state system.

**[03-expense-tracker-100] Both mutators use `.update()`. What was wrong with `set([...this.transactionList(), transaction])`?** ⭐

Functionally nothing — same array, same notification. I chose `update` because it hands me the current value as an argument, so the read and the write are one expression and there is no separate read of the signal inside the statement that writes it; the intent, "derive the next list from this one", is what the API says. `set` is what I use for a value that does not depend on the previous one — `currentFilter.set($event)` in the dashboard template is exactly that case, and the two calls read differently on purpose.

**[03-expense-tracker-101] `index.html` carries `<base href="/">` and `provideRouter(routes)` takes the default location strategy. What happens when a user refreshes the browser on `/add`?** ⭐⭐⭐

With `PathLocationStrategy` the router rewrites the address bar through the History API, so `/add` is a genuine path the server is asked for on a reload — and a static host with no file there answers 404, because only the Angular bundle knows `/add` is a route. I chose it anyway for clean URLs, on the condition that the host rewrites unknown paths to `index.html` — on Netlify that is a one-line `/* /index.html 200` redirect. The honest detail about this app, which is live on Netlify, is that the repository carries no `_redirects` and no `netlify.toml`, so that rewrite is not versioned with the project: committing the one-line file is the fix I would make, because the deploy story should travel with the code rather than live only in a host's dashboard. The alternative is `provideRouter(routes, withHashLocation())`, which hides the route after a `#` so the server never sees it — I would take that only where I cannot configure the host.

**[03-expense-tracker-102] `addTransaction` stamps the id with `crypto.randomUUID()`. Why not `Date.now()` or a counter?** ⭐⭐

Because both cheap options break in the two places the id is load-bearing — `track transaction.id` in the `@for`, and the `filter` in `deleteTransaction`. `Date.now()` collides for two transactions added in the same millisecond, and two rows sharing an id means one delete removes both and the loop's tracking is ambiguous; a counter is worse, because it lives in memory and restarts at zero after a refresh, re-issuing ids that are already in storage. I chose `crypto.randomUUID()` because it is stateless, needs nothing persisted alongside the list, and is native — its only condition is a secure context, which `localhost` and any HTTPS deploy satisfy.

**[03-expense-tracker-103] `NewTransaction` is `Omit<Transaction, 'id'>` rather than a second interface with the four fields written out. What does deriving it buy?** ⭐⭐

It encodes who owns the id. The service mints it with `crypto.randomUUID()`, so the form must not supply one, and `Omit<Transaction, 'id'>` says that in the type instead of in a comment — the form component literally cannot emit an id. I decided to derive rather than duplicate because a hand-written twin drifts silently: adding a `category` field to `Transaction` would leave the form's payload type unchanged and the mismatch would only appear at runtime, whereas with `Omit` the compiler flags every place that now has to send it.

**[03-expense-tracker-104] `Filter` is `'all' | 'income' | 'expense'` and `type` is a two-member union. Why string literal unions and not TypeScript `enum`s?** ⭐⭐

Because the union has no runtime footprint — it is erased at compile time, where an `enum` emits a real object into the bundle — and the values are already the strings I want to compare and store. That matters at the two boundaries: `JSON.stringify` round-trips `'income'` through `localStorage` and what comes back is still a valid `Transaction['type']` with no mapping layer, and `<option value="income">` in the template is the same literal the model expects. I chose the union deliberately over an enum, whose only real advantage here would have been a namespace I do not need for three values.

**[03-expense-tracker-105] `Transaction` is an `interface` and `NewTransaction` and `Filter` are `type` aliases, in the same eleven-line file. Deliberate, or just how they came out?** ⭐

Deliberate, and the rule is mechanical: an `interface` is for an object shape, and the other two are not object shapes — `Omit<>` is a mapped type and `Filter` is a union, and neither can be written as an interface at all. I default to `interface` for the model itself because it is the thing that would be extended or implemented if this app grew, and interfaces support declaration merging, which is a feature for a public shape and a hazard for an internal alias. So it is not two conventions, it is one convention plus what the language allows.

**[03-expense-tracker-106] Every input is `input()` or `input.required()` and the templates read them as `label()`, `amount()`, `tone()`. What does that change about how the view updates, compared with `@Input()` fields?** ⭐⭐

A signal input is a signal, so reading it in the template registers a dependency: `{{ amount() | number: '1.0-2' }}` and `[class.income]="tone() === 'income'"` tell Angular exactly which views depend on that input, and when the parent writes a new value only those views are marked. That is what lets this app be correct with no manual notification anywhere — the dependency graph, not a global re-check, is what schedules the update. With `@Input()` fields the value is a plain property and change detection has to re-evaluate the bindings to notice; what I gave up is `ngOnChanges`, and its replacement is a `computed()` or an `effect()` over the input signal, which components this thin never needed.

**[03-expense-tracker-107] `transactionList = signal<Transaction[]>(this.loadTransactions())` reads `localStorage` in a field initializer. When does that read actually run, and what is it blocking?** ⭐⭐

At the moment the service is first injected. It is tree-shakable and constructed lazily rather than at bootstrap, so the first injection is `DashboardPage`'s — during the first render — and `getItem` plus `JSON.parse` are synchronous, so that work sits on the main thread and the first paint waits for it. I chose the synchronous seed on purpose: the signal is never briefly empty, so the dashboard cannot render "No transactions yet" and then flash the real list a tick later. If the store ever grew past a trivial size I would start the signal at `[]` and hydrate after the first paint, accepting the flash.

**[03-expense-tracker-108] All the state in this app is one `signal<Transaction[]>`. What does keeping the whole collection in a single signal cost?** ⭐⭐

Everything downstream invalidates together. One delete replaces the array, and that single notification recomputes `totalIncome`, `totalExpense`, `balance` and `filteredTransactions` — four passes over the list — and re-serializes all N transactions on the way to storage, not just the row that changed. I decided that was the right trade for a personal tracker: the collection is small, the derived values are pure array work, and one signal means there is exactly one place the truth lives and no way for two pieces of state to disagree. The shape I would move to is a `Map<string, Transaction>` or a signal per row, and the trigger would be a long list or rows with independent editable state — neither is this app.

**[03-expense-tracker-109] You generated this app without SSR. If you turned it on tomorrow, what would break first?** ⭐

`TransactionService`, on its very first injection: `loadTransactions` calls `localStorage.getItem` in a field initializer and `localStorage` does not exist in Node, so the render throws before anything paints, and the constructor's `setItem` is the same failure a moment later. The fix is a platform guard — `isPlatformBrowser(inject(PLATFORM_ID))` around both, with `[]` as the server-side value — and the honest consequence is that the server would render an empty dashboard every time. I decided against SSR because this app has nothing to gain from it: there is no content to index and no server-fetched data, its entire state is per-browser, which is precisely the case where pre-rendering buys nothing.

**[03-expense-tracker-110] `app.config.ts` registers no `LOCALE_ID` and no locale data. What does a Spanish user see for a thousand-euro salary?** ⭐⭐

`+1,000€` — the number pipe falls back to the `en-US` locale Angular ships by default, so the thousands separator is a comma where a Spanish reader expects a dot, and the `€` after it is a character I typed into the template rather than anything the pipe placed. I decided formatting was worth fixing at application level rather than per call site: a provider in `app.config.ts` — `{ provide: LOCALE_ID, useValue: 'es-ES' }` with the `es` locale data registered — corrects both templates with no edit to either. It is the same reasoning that puts `provideRouter` there: anything the whole app must agree on belongs in the config, not repeated in components.

**[03-expense-tracker-111] Project 03 is hand-written CSS with no component library, and project 05 is built on Angular Material. Why did this one not take Material?** ⭐⭐

Because Material would have sat between me and the thing this project was for. The learning target was reactive forms, and `formControlName` on a native `<input>` with my own `@if (amount?.touched && amount?.hasError('min'))` block is the mechanism itself — `mat-form-field` and `mat-error` wrap that mechanism and would have let me ship the form without understanding it. I also decided a five-component app does not earn the bundle or the theming setup. Material comes in 05 because that project is about the pieces that are genuinely expensive to hand-build — a sortable table, a dialog — and there the trade goes the other way.

**[03-expense-tracker-112] Component styles are encapsulated per component, yet `summary-card.css` reads `var(--income)`, which is declared in the global `styles.css`. Why does that reach in?** ⭐⭐

Because emulated encapsulation rewrites *selectors*, not values: Angular adds a generated attribute to my rules so `.amount` in `summary-card.css` can only match this component's elements, and it does nothing to the inheritance of custom properties. A property declared on `:root` is inherited by every element in the document, and every component host is a descendant of `<html>`, so `var(--income)` resolves. I chose that split on purpose — the palette is the one thing that must be shared, so `--income`, `--expense`, `--accent` and the neutrals live once in `styles.css`, and everything else stays local to the component that owns it. It also leaves one place to add a dark theme without touching seven CSS files.

**[03-expense-tracker-113] The only media query in the app is `@media (min-width: 576px)` on the dashboard header. Is one breakpoint a responsive strategy?** ⭐⭐

It is the mobile-first form of one, which is the point: the base rules *are* the narrow layout, and the query only adds at wider widths, so nothing has to be undone for a phone. The rest of the app needs no query because it is fluid by construction — both pages use `max-width: 600px; margin: 0 auto`, the summary cards are `flex: 1` and share whatever width there is, and the form is a column flex. I decided to add a breakpoint only where something actually broke, and the one place it did was the header pair: the `h1` and the "+ Add transaction" button crowd each other at 320 px and have room to grow above 576 px. The rule I keep is that a breakpoint answers a specific layout failure, not a device list.

**[03-expense-tracker-114] The delete button is `position: absolute` in the corner of a `position: relative` row, while everything else in that row is flex. Why did that one control leave the flow?** ⭐

Because it is not part of the row's content. `.transaction-item` is a two-column flex — description and date on the left, amount on the right — and putting the `✕` inside that line makes it compete for space with the amount, so a long value pushes the button around. I chose to pin it instead: `position: relative` on the row establishes the containing block and `position: absolute; top: .5rem; right: .5rem` on the button takes it out of the flow entirely, so the row's layout is unaffected by it. The costs are the ones this pattern always has — it can overlap the content at narrow widths, and the parent has to keep its `position: relative` forever or the button escapes to the nearest positioned ancestor.

**[03-expense-tracker-115] You kept the CLI's `strict: true` and `strictTemplates`. Name something in this app that would have compiled without them.** ⭐⭐

`strictTemplates` is what type-checks `[tone]="balance() >= 0 ? 'income' : 'expense'"` against `input<Tone>()` — without it any string satisfies the binding and a typo like `'expence'` renders an unstyled card with no build error; the same flag is what would fail `[transactions]="filteredTransactions()"` the day that computed returns something other than `Transaction[]`. On the TypeScript side, `strict` is what forces the amount control's `number | null` to be narrowed before it can enter a `NewTransaction`. I kept both because the entire reason for choosing a typed stack is to be told at build time rather than by a user, and deleting a default is a decision I would have to defend anyway.

**[03-expense-tracker-116] `angular.json` runs `@angular/build:unit-test` and the devDependencies are `vitest` and `jsdom`, not Karma and Jasmine. What did you choose there?** ⭐

I took the Angular 21 default rather than fighting it: the unit-test builder runs specs on Vitest in a `jsdom` environment, so there is no real browser to launch and no Karma server, which is faster locally and trivial in CI — and Karma is deprecated. What is honest to add is that nothing meaningful runs on it here: all eight spec files are still the CLI scaffolds asserting `toBeTruthy()`, and `app.spec.ts` even asserts a `Hello, 03-expense-tracker` heading that this app's template does not render. The runner is configured, the tests are not written, and real tests begin in project 07.

**[03-expense-tracker-117] The production build keeps the CLI's `budgets` — 500 kB warning, 1 MB error — and `outputHashing: "all"`. What do those buy an app this small?** ⭐

The budget is a tripwire, not a limit I am anywhere near: its value is the day I add a chart library and get a build warning instead of learning about the payload from a slow first load, and the 4 kB `anyComponentStyle` budget does the same for a component stylesheet that grows unnoticed. `outputHashing: "all"` is what makes the emitted `main-<hash>.js` change name whenever its content changes, so the host can cache assets aggressively and a deploy can never be served stale from a browser cache. I kept both because a default I delete is a default I have to justify, and neither costs me anything.

**[03-expense-tracker-118] `.prettierrc` is committed, with `printWidth: 100`, `singleQuote` and a `parser: "angular"` override for HTML. Why is formatting config in the repository at all?** ⭐

Because formatting should be a property of the project, not of whichever editor last touched the file — that is what keeps `filter-bar.html`'s wrapped attribute lists and the multi-line `FormGroup` identical on every machine, and it keeps whitespace-only noise out of diffs so a review is about the change. I decided the `parser: "angular"` override was the part that actually matters here: the plain HTML parser does not understand interpolation, bindings or the `@for` / `@if` control-flow blocks, and it reformats templates into something the compiler and I both read worse. In a team the missing half is a format check in CI, so the file is enforced and not merely available.

**[03-expense-tracker-119] `add-transaction-page.ts` and `transaction-form.ts` write `import type { NewTransaction }`, while `dashboard-page.ts` imports `Filter` and `transaction-list.ts` imports `Transaction` as ordinary imports. Which is right?** ⭐

Both compile, and `import type` is the one that states the intent: it guarantees the import is erased and can never leave a runtime import of the model file behind. That matters under `isolatedModules: true`, which this `tsconfig.json` enables — each file is transpiled on its own, so the compiler cannot always see that an imported name was only ever a type, and the explicit form removes the guess. Here `transaction.model.ts` exports nothing but types, so all four are erased anyway, which is why I did not notice the inconsistency; I would make all four `import type` for the rule rather than for the bytes.

**[03-expense-tracker-120] All the state in this app is one signal in one `@Injectable` service — no NgRx, no signal store, no state library at all. At what point would you have reached for one?** ⭐⭐

I chose a plain root service because everything a store would give me is already free at this size: `TransactionService` is one `signal<Transaction[]>` with two mutators and a persistence `effect`, `DashboardPage` derives four `computed()` values from it, and there is exactly one writer, so there is no action log to reason about and no reconstruction to replay. NgRx would have added actions, reducers, effects and selectors around a forty-line service, which is the whole cost with none of the benefit. What would change my mind is scale, not taste — several features writing the same slice, state that has to survive a route change and be restored, or async flows with cancellation and retries — and a two-page browser-only tracker has none of them.

**[03-expense-tracker-121] `provideRouter(routes)` is called with the routes and nothing else — no `withInMemoryScrolling`, no `withComponentInputBinding`. Which feature would you add first, and what does its absence do today?** ⭐

`withInMemoryScrolling({ scrollPositionRestoration: 'enabled' })`, because Angular's default is `'disabled'` and that means the router leaves the viewport exactly where it was: submit the form from a dashboard scrolled halfway down and you come back to `/` at the old offset instead of the top. I decided against it while the app has two short pages and I could not reproduce the symptom, and the feature I would take second, `withComponentInputBinding()`, only earns its place the day the filter moves into a query parameter and `DashboardPage` wants to read it as an `input()`. The point I keep from it is that `provideRouter` is a list of opt-ins — the router does the minimum until the app asks for more — so an empty feature list is a decision I should be able to defend, not a default I never looked at.

**[03-expense-tracker-122] Every stylesheet here is plain `.css`, and `angular.json` registers `src/styles.css`. Why not take the SCSS the CLI offers?** ⭐

Because the two things I would have used it for are already in the language. The palette is declared as custom properties on `:root` in `styles.css` — `--income`, `--expense`, `--accent`, the neutrals — and a custom property is live in the browser where a `$variable` is compiled away, so the CSS version is the more capable one for theming; and nesting buys little in component files of forty lines that view encapsulation has already scoped. What SCSS costs is a build step and a second syntax in a project whose target was reactive forms and routing. Where I would take it is repeated mixins across many components or a real theming layer — project 05 is exactly that case, and its Material theme is a `material-theme.scss` sitting beside a plain `styles.css`.
