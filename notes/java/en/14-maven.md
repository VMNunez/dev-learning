You have now seen the annotations that drive every Spring class (file 13) — `@Entity`, `@Service`, `@RestController`, `@Transactional`. But annotations are just labels on your code, and code does nothing on its own: none of it compiles, none of it downloads the Spring libraries those annotations come from, and none of it packages into an app you can actually run. Something has to turn a folder of `.java` files into a running application. That something is Maven.

Maven is the standard build tool and dependency manager for Java projects. It handles three things: downloading libraries, compiling code, and packaging the application into a runnable `.jar`. This is the tooling capstone of the Java notes — the language itself (files 00–13, plus the memory model in 15) is now behind you; this file is how that language becomes a project you can build and ship.

**The JavaScript equivalent:** Maven is `npm`. `pom.xml` is `package.json`. Maven Central is the npm registry.

---

## What Maven does for you

When you build a Spring Boot project:

1. Maven reads `pom.xml`
2. Downloads all listed dependencies from Maven Central
3. Compiles your Java source code
4. Runs your tests
5. Packages everything into a single `.jar` file you can deploy

Two of those steps hide the same idea a Node developer never has to think about. "Compile" means turning your human-readable `.java` files into `.class` files — bytecode, the compact instruction format the Java Virtual Machine actually runs (JavaScript is interpreted straight from source, so there is no equivalent step). "Package into a `.jar`" then means zipping all those compiled `.class` files, plus a manifest describing the entry point, into one archive — a JAR is literally a ZIP with a `.class` payload. That single file is what you copy to a server and run with `java -jar`.

> **Why a build step at all, when `npm` has none?** JavaScript ships the same source the browser or Node runs. Java does not: the JVM runs bytecode, not source, so there is always a compile step between "code I wrote" and "code that runs". Maven is what automates that step (and everything around it) instead of you calling `javac` by hand on every file.

## pom.xml structure

Every Maven project has a single `pom.xml` at the root. It has four main sections: the **coordinates** that uniquely identify your project (groupId, artifactId, version), the **parent** that inherits Spring Boot's version management, the **dependencies** block where you list the libraries you need, and the **build** block with the plugin that makes the app runnable. You will spend most of your time in the `<dependencies>` block — the rest is generated by Spring Initializr and rarely touched.

> **What does `-SNAPSHOT` mean in the version?** Your `<version>` is `0.0.1-SNAPSHOT`. The `-SNAPSHOT` suffix is Maven's word for "in development, not yet released". A plain `0.0.1` would be a fixed, published release that never changes; `0.0.1-SNAPSHOT` tells Maven this is a work-in-progress build that you are still changing every day. Practically nobody removes it until they actually cut a release — every project you generate from Spring Initializr starts life as `-SNAPSHOT`, and yours will too.

> **What is a `starter`, and why is everything called `spring-boot-starter-*`?** A starter is a curated bundle of dependencies pulled in by one line. `spring-boot-starter-web` is not a single library — it is an empty "meta" dependency whose only job is to depend on the ~10 libraries you need for a REST API (Spring MVC, an embedded Tomcat server, the Jackson JSON library, validation, and more), all at versions the Spring team has already tested together. Without starters you would list those ten dependencies yourself and hope the versions are compatible. With a starter, one line brings the whole, known-good set. That is why almost every Spring dependency you add is named `spring-boot-starter-<something>`: each one is a themed bundle — `-web` for REST, `-data-jpa` for database access, `-security` for auth, `-test` for testing.

```xml
<?xml version="1.0" encoding="UTF-8"?>
<project>

  <!-- Maven coordinates — uniquely identify this project -->
  <groupId>com.example</groupId>       <!-- your organisation — reversed domain -->
  <artifactId>hr-portal</artifactId>   <!-- the project name -->
  <version>0.0.1-SNAPSHOT</version>    <!-- current version -->
  <packaging>jar</packaging>

  <!-- Parent — inherits Spring Boot defaults and manages dependency versions -->
  <parent>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-parent</artifactId>
    <version>3.3.0</version>
  </parent>

  <!-- Java version -->
  <properties>
    <java.version>21</java.version>
  </properties>

  <!-- Dependencies — the libraries your project uses -->
  <dependencies>

    <!-- Spring Boot Web — REST support, embedded Tomcat -->
    <dependency>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-starter-web</artifactId>
      <!-- no <version> needed — parent manages it -->
    </dependency>

    <!-- Spring Data JPA — database access with Hibernate -->
    <dependency>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-starter-data-jpa</artifactId>
    </dependency>

    <!-- PostgreSQL driver — runtime scope: not needed to compile, only to run -->
    <dependency>
      <groupId>org.postgresql</groupId>
      <artifactId>postgresql</artifactId>
      <scope>runtime</scope>
    </dependency>

    <!-- Spring Security — authentication and authorisation -->
    <dependency>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-starter-security</artifactId>
    </dependency>

    <!-- Bean validation — @NotNull, @Email, @Min, @Max -->
    <dependency>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-starter-validation</artifactId>
    </dependency>

    <!-- Test scope — only packaged for running tests, not in production -->
    <dependency>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-starter-test</artifactId>
      <scope>test</scope>
    </dependency>

  </dependencies>

  <!-- Plugin to run the app as a Spring Boot application -->
  <build>
    <plugins>
      <plugin>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-maven-plugin</artifactId>
      </plugin>
    </plugins>
  </build>

</project>
```

## The parent block and version management

The `spring-boot-starter-parent` in `<parent>` is the key to Spring Boot's "just works" experience. It:

- Manages all Spring library versions so they are compatible with each other
- Provides sensible defaults for the Maven build
- Sets the Java version

This is why most Spring Boot dependencies do not need a `<version>` tag. The parent already knows which version to use.

> **Why can you omit `<version>` on a Spring dependency?** The parent carries a big `<dependencyManagement>` section — a lookup table of "if you use library X, use version Y". When Maven reads a `<dependency>` with no `<version>`, it walks up to the parent, finds that library in the table, and fills in the version for you. So the version is not missing — it is inherited. This is the mechanism behind Spring Boot's "just add the starter and it works": the parent has already chosen a mutually compatible version for every library it knows about, so you never pick versions that clash.

**When you do need `<version>`:** for non-Spring libraries (JWT, MapStruct, Lombok). Search `mvnrepository.com` for the correct version.

## How to add a dependency

1. Go to [mvnrepository.com](https://mvnrepository.com)
2. Search for the library (e.g. "jjwt" for JWT)
3. Click the version you want — copy the `<dependency>` block
4. Paste it inside `<dependencies>` in `pom.xml`
5. IntelliJ detects the change and downloads it automatically (or run `mvn install`)

Example — adding JWT support for project 07:

```xml
<dependency>
  <groupId>io.jsonwebtoken</groupId>
  <artifactId>jjwt-api</artifactId>
  <version>0.12.5</version>
</dependency>
<dependency>
  <groupId>io.jsonwebtoken</groupId>
  <artifactId>jjwt-impl</artifactId>
  <version>0.12.5</version>
  <scope>runtime</scope>
</dependency>
```

## Dependency scopes

Not every library needs to be available at every stage of the build. A database driver only needs to be present when the application is actually running — not when the compiler checks types. A test library should never end up in the production JAR. Maven's scope system controls this: each dependency declares when it is needed, and Maven includes it only in those stages.

| Scope | Available when | Common use |
|-------|---------------|-----------|
| `compile` (default) | Always | Most libraries |
| `runtime` | Run time only, not compile time | Database drivers |
| `test` | Tests only — not in production build | JUnit, Mockito |
| `provided` | Compile time only — provided by the server | Servlet API |

Read the table as: the **Scope** column is the value you write inside `<scope>...</scope>`, and the **Available when** column tells you which build stages that dependency is put on the classpath — everything omitted from that column is where Maven deliberately leaves it out.

> **Why is a database driver `runtime` and not `compile`?** Your own code never mentions the PostgreSQL driver class by name — you write `repository.save(user)` and JPA/Hibernate decide, at run time, which driver to load based on your connection URL. So the compiler has nothing to check against the driver: it is not needed to *compile*, only to *run*. Marking it `runtime` keeps it off the compile classpath (so you cannot accidentally write code that depends on a specific database) while still packaging it into the JAR so the app can connect when it actually starts.

The most important distinction: `test` scope keeps test libraries out of the production `.jar`. Database drivers use `runtime` because you only reference the driver indirectly through JPA.

## Maven lifecycle — common commands

```bash
mvn clean              # delete the target/ folder (compiled output)
mvn compile            # compile the source code
mvn test               # run all tests
mvn package            # create the .jar file in target/
mvn install            # package + install the .jar to the local Maven cache
mvn clean install      # clean + compile + test + package (the standard full build)

mvn spring-boot:run    # run the Spring Boot app directly without packaging
```

The lifecycle phases run **in order** — running `package` automatically runs `compile` and `test` first. Running `install` runs all of the above.

> **Why does running one phase trigger the earlier ones?** Maven's lifecycle is a fixed sequence: `validate → compile → test → package → verify → install → deploy`. When you ask for a phase, Maven runs every phase up to and including it, never just that one in isolation. This is not a convenience feature — it is a guarantee: you cannot `package` a JAR out of stale or untested code, because `compile` and `test` are forced to run and pass first. Ask for a phase and you are really asking for "everything needed to reach this phase, in order".

> **Where does `mvn install` actually put the JAR?** Not on a server — into your **local Maven cache**, a hidden folder at `~/.m2/repository` on your machine. That cache is the same place Maven downloads Central dependencies into. Installing your project there means *another* project on the same machine can list yours as a dependency and Maven will find it locally. For a single Spring Boot app you rarely need this — `mvn install` matters when you split one system into several modules that depend on each other.

## Maven vs Gradle

Gradle is the other popular build tool for Java. Both do the same job — manage dependencies, compile, test, package — but they use different configuration formats and have different adoption patterns. For your projects in Spain, Maven is the safer default.

| | Maven | Gradle |
|---|-------|--------|
| Config format | XML (`pom.xml`) | Groovy or Kotlin (`build.gradle`) |
| Verbosity | More verbose | Shorter |
| Enterprise adoption | Very common in Spain | Growing, common in Android |
| Learning curve | Lower | Higher |
| Spring Initializr | Both supported | Both supported |

Read the table row by row: each row is one dimension you might compare the two tools on, and the two columns are how Maven and Gradle each score on it — scan the **Maven** column top to bottom to get the full picture of the tool you are actually using.

For your projects, **Maven is the safer choice** — it is what most Spanish consultancies use on their existing Java projects, and the `pom.xml` format is easier to read when you are starting out.

## Maven folder structure (generated by Spring Initializr)

Spring Initializr creates this structure for you. You will never create it by hand. The important convention: source code goes in `src/main/java`, tests go in `src/test/java`, and the `target/` folder (where Maven puts compiled output and the JAR) is always in `.gitignore` because it is regenerated on every build.

```
project/
├── pom.xml                    ← build configuration and dependencies
├── src/
│   ├── main/
│   │   ├── java/              ← your Java source code
│   │   └── resources/
│   │       └── application.properties  ← Spring Boot config
│   └── test/
│       └── java/              ← your test files
└── target/                    ← compiled output (generated, not in git)
```

> **Why keep `target/` out of git?** Because it is 100% derived — every `.class` file and the JAR inside it are produced from your source by `mvn compile`/`mvn package`. Committing it would bloat the repo with binaries and cause endless merge conflicts on files nobody edits by hand. Anyone who clones the repo regenerates `target/` with one build, so there is nothing to lose by ignoring it. This is the same reason `node_modules/` is git-ignored in a Node project: never commit what a build step can recreate.
